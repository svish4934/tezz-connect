How the TEZZ CONNECT speed test works

A speed-test result is a measurement between a particular device, browser, network path and test endpoint at a particular time. This page explains what TEZZ CONNECT measures, how the figures are calculated and what the results cannot tell you.

What the test measures

TEZZ CONNECT runs measurement requests from your browser to TEZZ CONNECT speed-test endpoints hosted on its network edge. The test reports download throughput, upload throughput, and browser-measured HTTP response timing and variation. These measurements describe the path used by this test between your device and the TEZZ CONNECT endpoint.

They are not a measurement of every route across the public internet. A result can differ from the performance you experience with a particular game server, video platform, cloud-storage service or website because those services use different destinations and network paths.

HTTP response time and response variation

Before the transfer tests, the browser sends one warm-up request to the TEZZ CONNECT latency endpoint. It then makes seven additional sequential HTTP requests. The browser records the elapsed time for each request using its high-resolution timing clock.

The displayed latency figure is the median of those seven measured request-response times. The response-variation figure is calculated as the mean of the absolute differences between each consecutive pair of measured times. In other words, it describes how much the successive HTTP timings varied during this short test.

Important terminology

These are browser-based HTTP request-and-response timings to the TEZZ CONNECT edge. They are not ICMP echo-request ping measurements, and the variation figure is not a direct packet-level jitter measurement. Browser scheduling, device load, Wi-Fi, routing and endpoint conditions can all influence the timings.

Download throughput

The browser requests a streamed download from the TEZZ CONNECT endpoint. It reads the response body in chunks and counts the bytes received. Throughput is calculated from the number of bits received divided by the elapsed time, then expressed in megabits per second (Mbps).

The current test runs three download samples. Each sample is limited to 2.5 seconds and a maximum response size of 8,333,333 bytes. The final download result is the median of the three sample results. Using the median reduces the influence of one unusually high or low sample, but it does not remove every source of measurement variation.

Upload throughput

The browser first sends a 1,000,000-byte calibration payload. Based on that calibration rate, the test selects the measured upload payload size:

  • Below 25 Mbps: 2 MB
  • From 25 Mbps to below 100 Mbps: 5 MB
  • 100 Mbps or above: 10 MB

The browser creates the payload, sends it to the TEZZ CONNECT upload endpoint and measures the time until the browser reports that the upload has completed. The server response must confirm that it received the full payload. The reported throughput uses the browser's upload-complete timing, not the server's processing duration.

The test runs three measured samples for the 2 MB payload size and two samples for the 5 MB or 10 MB payload sizes. The final upload result is the median of those samples. The calibration and measured payloads are test traffic; actual data transferred can vary if a test fails or is repeated.

How to interpret your results

  • Download Mbps: the rate at which data reached your browser from the test endpoint during the download samples.
  • Upload Mbps: the rate at which your browser sent the test payload to the endpoint, with full receipt confirmed by the server.
  • HTTP latency: the median time for a browser request to receive a response from the TEZZ CONNECT endpoint.
  • HTTP response variation: the average absolute change between consecutive response-time samples in this test.

Mbps means megabits per second, not megabytes per second. To convert a rate in Mbps to an approximate megabytes-per-second rate, divide by eight. This is a unit conversion, not a promise of the exact file-transfer rate you will see in another app.

What the test cannot diagnose by itself

A speed test cannot identify the exact cause of a poor result. It does not independently prove that an internet provider is at fault, measure the quality of every internet route, certify Wi-Fi coverage throughout a home, or guarantee performance for a specific application.

The result can be influenced by your phone or computer, browser, background activity, Wi-Fi signal and interference, router, Ethernet adapter, other people using the connection, local network congestion, ISP routing, endpoint load and wider network conditions. The test is a short sample, not continuous monitoring.

TEZZ CONNECT's HTTP response measurements should not be described as ICMP ping, packet loss or packet-level jitter. Separate diagnostic tools are needed when those specific measurements are required.

How to make a fair comparison

  1. Use the same device and browser for each comparison.
  2. Pause large downloads, uploads, cloud backups and streaming where practical.
  3. Record whether the device is connected by Wi-Fi or Ethernet.
  4. For a Wi-Fi check, test near the router first, then repeat in the room where you notice the problem.
  5. Repeat measurements at different times and compare patterns rather than relying on one result.
  6. If you are investigating a provider issue, keep the dates, times, connection method and results, and follow your provider's published complaint-testing procedure.

Test data and privacy

Speed-test requests are processed by the TEZZ CONNECT network edge to deliver the measurement. Cloudflare processes connection information, including the request IP address, for network delivery and security. Your local test history is stored in your browser and is not automatically synced to an account.

Regional benchmark contribution is a separate optional feature. A completed test is not automatically a public benchmark contribution: the user must explicitly choose to share the limited measurement summary. Read the Privacy Policy for details about processing, browser storage and optional benchmark sharing.
