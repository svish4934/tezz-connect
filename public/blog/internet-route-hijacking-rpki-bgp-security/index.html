Internet Route Hijacking: How RPKI Helps Keep Data on the Right Path

The internet is made up of thousands of independently operated networks. They use a routing system called BGP to tell one another which IP address ranges they can reach. If a network announces a route it is not authorised to originate—or accidentally advertises a route incorrectly—traffic can take an unexpected path. Resource Public Key Infrastructure (RPKI) gives operators a cryptographic way to check who is authorised to originate an IP prefix. It is an important improvement, but not a magic shield for every routing problem.

By Suraj Vishwakarma · Published by TEZZ CONNECT · Published 22 November 2026 · Updated 22 November 2026

When you open a website, your data may cross several internet service providers, backbone networks, exchange points and data centres before it reaches the destination. Your device does not choose that global path. Network routers exchange reachability information and select routes using the Border Gateway Protocol, or BGP.

BGP is essential because the internet has no single central operator. Each independently managed network—often called an Autonomous System (AS)—shares routing information with neighbouring networks. This system is flexible and has scaled remarkably well, but its original design relied heavily on trust and operational coordination between networks.

That creates a weakness: a router can announce that its network can reach an IP address range even when that announcement is mistaken or unauthorised. Other networks may accept and propagate it. Resource Public Key Infrastructure (RPKI) and Route Origin Authorisations (ROAs) help reduce this risk by allowing networks to verify which Autonomous System is authorised to originate a prefix. This article explains what the protection does, what it cannot do, and why internet routing security requires more than one control.

1. How does internet routing work?

Think of the internet as a collection of road systems operated by different organisations. One provider knows how to reach its customers. Another connects data centres. A third carries traffic between countries. To exchange traffic, these networks need to tell one another which destination address ranges they can deliver.

BGP is the standard inter-domain routing protocol used to exchange that reachability information. A network identifies itself with an Autonomous System Number (ASN). When it announces an IP prefix, the announcement includes path information that helps other networks understand which autonomous systems the route has traversed.

A prefix is a block of IP addresses, written in notation such as 203.0.113.0/24. The /24 indicates how many leading bits identify the network portion. A route announcement is effectively a claim: this network can deliver traffic for this address block. Other networks evaluate that claim alongside their routing policies and the paths they already know.

BGP was designed to exchange reachability at global scale, not to cryptographically prove every claim by default. Operators therefore use filters, peer relationships, monitoring and routing policies to reduce mistakes and abuse. RPKI adds a verifiable authorisation signal to one important part of that process.

2. What is a BGP route hijack?

A BGP route hijack occurs when a network announces reachability for an IP prefix in a way that is not authorised by the legitimate holder. The announcement may be deliberate or accidental. If other networks accept it, traffic intended for the real destination can be attracted toward the announcing network.

There are several possible outcomes. Traffic might be dropped, creating an outage. It might be sent along a longer or congested path, causing delays. In a more serious interception scenario, traffic could pass through infrastructure controlled by an attacker before being forwarded—or not forwarded—to its intended destination. Encryption such as HTTPS can protect the content of many application sessions, but it does not guarantee that the network path itself is correct or available.

A route hijack is not the same as hacking a website's server. The website may remain online and its database may be untouched. The problem can occur earlier, at the internet routing layer, when networks disagree about where an IP prefix should be reached.

3. What is a route leak, and how is it different?

A route leak is an incorrect propagation of routing information that violates the intended routing policy between networks. For example, a network may pass along routes learned from one provider to another provider even though the business and technical relationship does not permit that transit. The route may still point toward the legitimate destination, but it can attract traffic onto an unintended path.

A route hijack generally involves an unauthorised origin claim for a prefix. A route leak generally involves a route being propagated in a way that conflicts with routing policy. The terms can overlap in real incidents, but they describe different failure modes.

This distinction matters because RPKI Route Origin Validation focuses on the origin Autonomous System for a prefix. It does not automatically establish whether every network in the AS_PATH is entitled to pass the route to the next network. Preventing route leaks also requires sound BGP relationships, prefix and customer filters, route-policy controls and operational coordination.

4. What is RPKI?

Resource Public Key Infrastructure is a framework that uses cryptographic certificates to associate internet number resources—IP address blocks and Autonomous System Numbers—with their legitimate holders. The certificate hierarchy follows the way these resources are allocated and delegated through the internet number registry system.

RPKI lets a resource holder publish signed statements about routing authorisations. The most familiar statement is a Route Origin Authorisation, or ROA. A ROA says that a particular ASN is authorised to originate a particular IP prefix, optionally with a maximum prefix length.

Network operators can download and validate these signed objects using RPKI relying-party software. The validated information is made available to routers, commonly through a validated cache and the RPKI-to-Router protocol. A BGP router can then compare a received route announcement with the validated authorisations and assign an origin-validation state.

RPKI does not replace BGP, allocate addresses or carry user traffic. It supplies verifiable authorisation data that a network can use when applying its own routing policy.

5. What is a ROA?

A Route Origin Authorisation is a digitally signed object created by the holder of address resources. It identifies the IP prefix that may be announced, the origin ASN authorised to announce it, and optionally the maximum prefix length that the authorisation permits.

For a simplified example, imagine an organisation holds 203.0.113.0/24 and authorises AS64500 to originate it. A ROA can state that AS64500 is permitted to announce 203.0.113.0/24. If the organisation also needs to announce more-specific routes, it must decide deliberately whether and how to authorise those lengths.

The example addresses and ASN are reserved for documentation and illustration; they are not a live network or an actual customer authorisation.

The maximum-length field deserves care. If it is set too broadly, it may authorise more-specific announcements than the operator intended. If it is set too narrowly, legitimate announcements may be marked invalid. IETF operational guidance recommends avoiding maxLength unless there is a specific need and the consequences are understood.

6. How Route Origin Validation works

When a router receives a BGP route, it can compare the route's prefix and origin ASN with the validated ROA information. The result falls into one of three states:

StateMeaningWhat an operator may do
ValidAt least one validated ROA authorises the announced prefix and origin ASN.Usually accept the route under normal routing policy.
InvalidA covering ROA exists, but the announcement conflicts with the authorised origin ASN or permitted prefix length.Many operators choose to reject invalid routes, subject to their policy and operational safeguards.
Not FoundNo validated ROA covers the announced prefix.Apply a local policy; this state does not prove the route is malicious.

Not Found is particularly important. It means the routing system does not have a matching authorisation statement to check. It does not mean that the route is automatically fraudulent. A network may not have published a ROA yet, or the prefix may not be covered by the available authorisations.

RPKI validation is also not a global command that every router must follow identically. Each network decides how to use the states in its import and export policies. Rejecting Invalid routes is a widely used protective policy, but operators must avoid creating outages through incorrect ROAs or stale validation data.

7. What RPKI can stop—and what it cannot

RPKI-based origin validation is designed to help detect announcements whose origin ASN is not authorised for the advertised prefix. When a route is marked Invalid and a network's policy rejects it, that network can avoid selecting or propagating that particular unauthorised origin announcement.

However, origin validation does not verify the entire AS_PATH. A route can have an authorised origin ASN and still travel through an unexpected or policy-violating sequence of networks. RFC 6811 explicitly describes origin validation as partial protection and states that complete path attestation is outside its scope.

RPKI also cannot protect against every operational mistake. Incorrect ROAs, missing authorisations, delayed repository updates, validator outages, misconfigured router policies and compromised resource-management accounts can all affect the result. It does not stop denial-of-service attacks against a destination, repair a broken fibre route, or guarantee that the selected path has enough capacity.

The accurate way to describe RPKI is that it improves the verifiability of route-origin claims. It is an important layer of routing security, not a guarantee that every route across the internet is safe.

8. What about path validation and newer protections?

Because origin validation does not check every autonomous system along a route, the routing community is working on complementary ways to improve path security. One example is Autonomous System Provider Authorization (ASPA), which allows resource holders to publish information about their authorised provider relationships. This can help validators assess aspects of an AS path and identify certain route leaks.

ASPA is not the same as a ROA. A ROA answers which ASN may originate this prefix. ASPA-related validation asks whether provider relationships represented by parts of a route path are consistent with published authorisations. APNIC's RPKI guidance describes how ROAs and ASPAs can complement one another.

Other BGP security work and operational practices remain important, including prefix filtering, customer-cone controls, route-leak prevention, monitoring and careful peering policy. The internet is not protected by a single cryptographic switch; resilience comes from several mechanisms working together.

9. What should an ISP or network operator do?

For operators, RPKI deployment is a process rather than a checkbox. A sensible implementation plan includes:

  • Inventory address resources: confirm which organisation controls each prefix and which ASN or ASNs legitimately originate it.
  • Create accurate ROAs: authorise the correct origins and avoid unnecessarily broad maximum-length settings.
  • Validate the data: operate reliable relying-party software or use a trusted validated cache, and monitor repository and validator health.
  • Apply clear router policy: decide how Valid, Invalid and Not Found routes are handled on ingress and, where appropriate, egress.
  • Filter customer announcements: accept only the prefixes customers are authorised to announce and prevent accidental transit or route leaks.
  • Monitor and rehearse: track invalid announcements, route changes, ROA expiry or removal, and the impact of policy updates.
  • Coordinate with peers: maintain accurate routing contacts and escalation procedures so mistakes can be corrected quickly.

Before changing a ROA, operators should understand every legitimate origin and traffic-engineering arrangement for the prefix. A valid route can become Invalid if an organisation changes providers or origin ASNs without updating the authorisation. Equally, an overly broad ROA can weaken the protection it is meant to provide.

10. What does this mean for internet users in India?

For a home broadband or mobile user in India, RPKI is usually invisible. You do not enable it in Android settings or on a home Wi-Fi password screen. It is implemented by organisations that manage IP resources and by the networks that exchange internet routes.

Its value is in the background. Better route-origin validation can help networks avoid certain unauthorised route announcements, which may reduce the risk of some traffic redirection and reachability incidents. But your experience still depends on the ISP's routing policies, upstream providers, peering, international capacity, fibre paths, data-centre availability and many other factors.

If a website becomes unreachable from one provider but works from another, the cause could be DNS, routing, a provider outage, filtering, a destination problem or a temporary network change. A single failed connection does not prove that a BGP hijack has occurred. Operators use route collectors, looking glasses, traceroutes and routing telemetry to investigate these events.

Customers can report persistent reachability problems to their ISP with the destination, time, access network and diagnostic details. Avoid sharing private account information or assuming that a speed-test result alone can diagnose global routing security.

11. How routing security may evolve

The long-term direction is toward stronger, more automated validation of routing information. Wider ROA coverage and more consistent rejection of Invalid announcements can reduce the opportunity for unauthorised origin claims to influence networks. Work on path-oriented mechanisms, including ASPA, aims to address some limitations that origin validation cannot cover.

Progress depends on more than publishing signed objects. Resource holders need accurate authorisations, network operators need reliable validators and carefully tested policies, and the wider ecosystem needs operational coordination. The design must also account for the fact that routing changes happen continuously and that stale or inconsistent data can cause real connectivity problems.

As cloud services, mobile networks, satellite systems and edge infrastructure grow, dependable interconnection becomes even more important. A secure route is not necessarily the shortest or fastest route, but knowing that its origin is authorised gives operators a stronger basis for making routing decisions.

12. The practical takeaway

BGP lets independently operated networks tell one another where internet destinations can be reached. That openness makes the global internet scalable, but it also means incorrect or unauthorised announcements can affect traffic. RPKI and ROAs help networks verify which Autonomous System is authorised to originate an IP prefix.

Route Origin Validation is a meaningful improvement, but it does not authenticate every network hop, prevent all route leaks or guarantee uninterrupted service. Accurate ROAs, sensible maxLength choices, router filtering, monitoring and operational cooperation are all part of the solution.

For most users, the protection happens behind the scenes. For network operators, it is a practical responsibility: make route announcements more verifiable so the internet can keep finding the right way home.

Frequently asked questions

What is BGP route hijacking?

It is an unauthorised or incorrect announcement that claims reachability for an IP prefix. If other networks accept it, traffic may be redirected, intercepted or dropped.

What is RPKI in simple terms?

RPKI is a cryptographic framework that links IP address and ASN resources to their holders and supports signed routing authorisations.

What is a Route Origin Authorisation (ROA)?

A ROA is a digitally signed statement that authorises an Autonomous System to originate a particular IP prefix, optionally with a maximum prefix length.

What do Valid, Invalid and Not Found mean?

Valid means a ROA authorises the origin and prefix. Invalid means a covering ROA exists but the announcement conflicts with it. Not Found means no validated ROA covers the route.

Does RPKI stop all BGP route hijacks?

No. It checks the authorised origin ASN for a prefix. It does not validate every hop in the AS path or prevent all routing attacks and mistakes.

Is a route leak the same as a route hijack?

No. A hijack involves an unauthorised origin claim. A route leak involves a route being propagated contrary to intended routing policy. Real incidents can involve aspects of both.

What is the difference between a ROA and ASPA?

A ROA authorises an ASN to originate a prefix. ASPA information describes authorised provider relationships and can help assess aspects of the AS path and route leaks.

Can I enable RPKI on my home router?

Usually not. RPKI origin validation is generally configured by internet service providers, backbone operators and other networks that run BGP routers.

Does RPKI make my internet faster?

Not directly. It improves the ability to detect certain unauthorised route origins. Speed and latency still depend on routing choices, congestion, capacity, peering and the destination.
