HTTP/3 Explained: How QUIC Makes Web Connections Work

Understand HTTP/3, QUIC, TLS 1.3, multiplexed streams, connection migration, packet loss, UDP and why the latest web protocol does not make every connection faster. This guide explains the protocol stack, performance trade-offs, security model, network compatibility and practical deployment considerations.

By Suraj Vishwakarma · Published by TEZZ CONNECT

The next step in how the web moves data

Every time a browser loads a website, it uses HTTP to request resources and receive responses. Images, scripts, stylesheets, API results and page documents all rely on this family of application protocols. HTTP has evolved over decades. HTTP/1.1 made persistent connections practical for everyday browsing. HTTP/2 introduced binary framing and multiplexed streams over a single TCP connection. HTTP/3 changes the transport beneath HTTP: it maps HTTP semantics onto QUIC, a secure transport protocol that runs over UDP rather than TCP. This is more than a new version number. QUIC combines transport functions, encryption setup and independent streams in a design intended to reduce some delays and improve behaviour when packets are lost or a device changes networks. HTTP/3 is specified by the Internet Engineering Task Force in RFC 9114, while QUIC is specified in RFC 9000. Understanding the relationship between the two explains what the protocol can improve—and what it cannot.

What is HTTP/3?

HTTP/3 is the third major version of HTTP to be standardised for modern web use. It carries familiar HTTP concepts—methods, status codes, headers, request and response semantics—over QUIC instead of using TCP as HTTP/1.1 and HTTP/2 commonly do. The browser still asks for a resource such as a page, image or API endpoint, and the server still responds with HTTP metadata and content. What changes is how the connection is established, how data is transported, how streams are isolated and how encryption is integrated. HTTP/3 uses QUIC version 1 and negotiates the application protocol using the ALPN identifier “h3”. QUIC version 1 uses TLS 1.3 or a later compatible version for its handshake and cryptographic protection. A website does not become HTTP/3 simply because it uses HTTPS; the server, client and network path must support and successfully negotiate the protocol. When HTTP/3 cannot be used, browsers can fall back to an available TCP-based HTTP version.

What is QUIC, and why does HTTP/3 use it?

QUIC is a general-purpose, secure transport protocol designed to provide reliable delivery, congestion control, flow control and multiplexed streams. It runs over UDP, which is a simpler datagram transport available across existing operating systems and network equipment. QUIC implements transport behaviour in the endpoints rather than relying on the TCP implementation built into the operating system kernel. That gives protocol developers room to evolve transport features and integrate TLS more directly. QUIC was designed to address several limitations that become visible when a web page needs many resources or when the connection experiences packet loss. It supports multiple independent streams within one connection, connection identifiers that can help a session survive address changes, and a handshake that combines transport and cryptographic negotiation. QUIC does not replace IP, and it is not itself a web page protocol. HTTP/3 is one application protocol built on top of QUIC; other protocols can also use QUIC.

HTTP/1.1, HTTP/2 and HTTP/3 compared

HTTP/1.1 typically uses TCP connections and can keep them open for multiple requests. Browsers historically opened several connections to a host to fetch resources concurrently, but each connection has its own setup and congestion state. HTTP/2 introduced binary frames and multiplexing, allowing multiple request and response streams to share a single TCP connection. That reduces the need for multiple connections and enables header compression, but all TCP bytes still belong to one ordered byte stream. If a TCP segment is lost, later bytes on that connection cannot be delivered to the HTTP/2 layer until the missing bytes are recovered. This can delay otherwise independent HTTP/2 streams. HTTP/3 maps HTTP streams onto QUIC streams. QUIC can deliver data from one stream while another stream is waiting for retransmission, because ordering and recovery are handled per stream rather than by one shared TCP byte sequence. The difference is important under packet loss, but it does not mean HTTP/3 is always faster in every network or for every page.

How a browser establishes an HTTP/3 connection

A browser first needs to know that the server supports HTTP/3. Servers and CDNs can advertise alternative services, and clients may remember successful protocol support for a host. Once the browser selects an HTTP/3 endpoint, it resolves the host name, opens a QUIC connection to the server over UDP and performs the QUIC and TLS handshake. The client and server negotiate HTTP/3 using the “h3” ALPN identifier. TLS 1.3 provides authentication and encryption, while QUIC integrates the TLS handshake with transport setup. The connection carries HTTP/3 control streams and request streams, and each endpoint sends HTTP/3 settings that describe supported protocol behaviour. After setup, the browser can reuse the connection for further requests to the same origin and, where certificate and protocol rules permit, other origins. The exact discovery and reuse process is governed by the HTTP and HTTP/3 specifications; it is not a special browser preference that users normally need to configure manually.

Why QUIC runs over UDP

UDP provides datagrams without the built-in connection management, ordering or retransmission mechanisms that TCP supplies. QUIC uses UDP as a carrier, then implements its own secure connection, loss detection, retransmission, congestion control and stream management above it. This approach avoids requiring a new transport protocol number to pass through every network and allows QUIC implementations to evolve in user space. UDP also makes it possible for an application to manage connection behaviour without waiting for every operating system to update its TCP stack. The trade-off is that some networks block, rate-limit or interfere with UDP traffic, particularly on paths where firewalls or middleboxes have restrictive policies. QUIC therefore needs sensible fallback behaviour. If a client cannot establish QUIC, it should be able to use a TCP-based HTTP version when the server offers one. UDP is not inherently faster than TCP; the performance characteristics come from the protocol layered over it and how the network treats the traffic.

Multiplexed streams and head-of-line blocking

A stream is an independent sequence of bytes within a QUIC connection. HTTP/3 uses streams for requests, responses and control information. Because each stream has its own ordering and flow-control state, losing a packet that carries data for one stream does not automatically prevent the application from receiving already-arrived data for another stream. This reduces transport-level head-of-line blocking compared with multiple HTTP/2 streams sharing one TCP byte stream. The distinction is sometimes oversimplified. HTTP/3 does not eliminate all blocking: a particular stream still needs its missing data before later data on that same stream can be delivered in order. Application dependencies can also create delays—for example, a script may need a stylesheet or API response before the page can continue. Congestion control is still applied to the connection path, so packet loss and congestion can affect the overall rate at which data is sent. QUIC improves stream isolation; it does not make network capacity unlimited or remove every dependency in a website.

Packet loss, congestion control and real-world performance

Networks lose packets for many reasons: wireless interference, overloaded queues, faulty equipment, congested links, radio handovers and routing changes. Reliable transports detect missing data and arrange for it to be sent again. TCP provides reliability for its byte stream, while QUIC provides reliability at the stream level. QUIC also uses congestion control so a sender does not overwhelm the path. It measures acknowledgements, detects loss and adjusts sending behaviour. Different implementations may use different congestion-control algorithms and recovery details within the protocol's rules. HTTP/3 can perform better than HTTP/2 in some lossy conditions because a missing packet does not hold back unrelated streams in the same way. But if the access link is severely congested, the radio signal is weak or the server is slow, HTTP/3 cannot create capacity. A speed test measures throughput to a particular test endpoint; a page load depends on many separate requests, application work and network paths. Protocol choice is one factor among many.

TLS 1.3, encryption and privacy

QUIC integrates TLS 1.3 into its connection establishment. This means QUIC connections are encrypted by design, and the handshake establishes cryptographic keys while negotiating transport parameters. HTTP/3 therefore does not offer a normal unencrypted mode comparable to plain HTTP over TCP. Encryption protects application data in transit and authenticates the server through certificates, but it does not make a website trustworthy or protect a device from malware. It also does not hide every piece of metadata. Network observers can still see information such as IP addresses, packet sizes and timing, and the initial connection setup has protocol-specific metadata considerations. DNS privacy, encrypted client hello and other mechanisms are separate technologies with their own deployment status and limitations. Website owners still need valid certificates, secure application code, careful cookie settings and appropriate access controls. HTTP/3's security model is a strong transport foundation, not a replacement for broader web security.

Connection migration: moving between Wi-Fi and mobile data

A phone can change its network while a user is browsing: a person may walk out of Wi-Fi coverage and continue over cellular data, or move between access points. With TCP, a change in the endpoint's IP address or port generally breaks the existing connection, requiring the application to establish a new one. QUIC uses connection IDs so a connection is not identified solely by the IP address and port pair. This can allow a client to migrate a connection to a new network path after validating that path. The feature can reduce interruptions for applications that maintain active sessions while a device changes networks. Migration is not automatic magic. The client and server must support it, the new path must be reachable and validated, and network policy may prevent it. Some servers can disable active migration, and NAT rebinding or path changes require validation procedures. If the new network has poor coverage or blocks UDP, the connection may still stall or be replaced by a fallback connection.

0-RTT and faster repeat connections

TLS 1.3 and QUIC support a mechanism commonly called 0-RTT for certain repeat connections. A client that has previously connected to a server may be able to send eligible application data before completing a full new handshake. This can reduce waiting time for repeat visits under suitable conditions. Early data has security and replay considerations: an attacker may be able to cause eligible early data to be replayed, so applications must not use it for operations where replay could cause harm. HTTP methods and application semantics matter. A safe read request may be suitable in circumstances where a state-changing purchase, payment or account operation is not. Servers can reject early data, and clients may need to retry after handshake completion. 0-RTT is an optimisation, not a guarantee that every page opens with zero delay. First-time visitors do not have the prior connection state required, and DNS lookup, server processing, content generation and network congestion can still dominate the experience.

HTTP/3 and HTTP/2: does the newer version always win?

No. HTTP/3 is designed to improve transport behaviour, especially where loss, connection setup and network changes matter, but measured results vary. On a clean, low-latency wired network, HTTP/2 may already perform very well. A CDN may terminate HTTP/3 at its edge and use HTTP/2 or HTTP/1.1 to communicate with the origin, so the browser-facing protocol does not necessarily describe every hop behind the scenes. Some devices, enterprise proxies and network security products handle TCP more efficiently or inspect it more easily than UDP-based QUIC. A UDP path may be blocked or rate-limited, triggering fallback. Server implementation quality, CPU use, congestion-control algorithm, page structure, cache hit rate and origin response time all influence outcomes. Website operators should compare real user metrics and controlled tests across regions and networks rather than assuming a higher protocol number automatically produces a faster site.

What happens when UDP or QUIC is blocked?

Some organisations restrict UDP to reduce attack surface, enforce inspection policies or simplify network management. A restrictive firewall may block the UDP traffic used by QUIC, or a network may allow it but perform poorly with large datagrams or certain paths. When QUIC cannot be established, HTTP/3 clients should attempt a TCP-based HTTP version if one is available. This fallback is important for compatibility: users should not lose access to a website merely because HTTP/3 is unavailable on their current network. Network administrators who want to inspect HTTP/3 traffic need tools that understand QUIC and UDP; a proxy that only handles TCP cannot inspect the same traffic in the same way without additional support or a deliberate downgrade path. Blocking UDP/443 may force many browsers to use HTTP/2, but it can also affect other UDP services if the rule is too broad. Troubleshooting should identify the specific destination, port, protocol and policy rather than disabling UDP globally.

How to tell whether a website uses HTTP/3

Most users do not need to check the protocol manually. Modern browsers negotiate an available protocol automatically. For technical verification, browser developer tools can show the protocol used for individual network requests; the protocol column may display h3, h2 or http/1.1. Some command-line clients can report supported HTTP versions, but the installed version and build options matter. A website's server configuration or CDN dashboard may also show whether HTTP/3 is enabled and how many requests use it. Testing from one browser on one network does not prove that every visitor uses HTTP/3. A visitor may use HTTP/2 because of a firewall, an older browser, a proxy or a fallback after a failed QUIC attempt. If you are diagnosing a slow page, record the protocol along with DNS time, connection time, TLS/QUIC setup, time to first byte, content download and resource dependencies. This gives a more complete picture than looking at the protocol label alone.

What website owners should consider before enabling HTTP/3

First, confirm that the hosting platform, reverse proxy or CDN supports HTTP/3 and has a valid TLS certificate at the point where the connection terminates. Check whether HTTP/3 is enabled for visitors only or also for connections to the origin; providers differ. Review firewall rules and make sure the required UDP service is reachable. Keep HTTP/2 or another compatible TCP-based version available so users on restricted networks can fall back. Monitor protocol negotiation, handshake failures, response times, error rates and traffic volume across different regions and access networks. Test login, checkout, uploads, downloads, APIs and long-lived requests rather than checking only the home page. Confirm that observability and security tools can interpret QUIC traffic or that the architecture accounts for where encryption terminates. Roll out gradually if possible and compare real user metrics before and after. HTTP/3 is a transport improvement, but its value depends on end-to-end deployment and operational readiness.

Common myths about HTTP/3

HTTP/3 does not mean a website has three times the speed of HTTP/1. It does not increase the bandwidth purchased from an ISP, repair Wi-Fi interference or shorten the physical route to a server. QUIC uses UDP, but UDP itself is not a speed booster; QUIC supplies reliability, security and congestion control above it. HTTP/3 reduces a particular form of transport-level head-of-line blocking, but it does not remove application dependencies or all waiting. Connection migration can help preserve a session during a network change, but it cannot guarantee uninterrupted connectivity. TLS 1.3 encryption protects traffic in transit, but it does not prove that the website is honest or safe. Finally, HTTP/3 does not require users to install a special browser extension or change their router settings. Compatible browsers and servers negotiate it when available, and use a fallback when it is not.

The practical takeaway

HTTP/3 is an evolution in how the web transports data. By using QUIC, it combines secure connection establishment, independent streams, transport recovery and connection identifiers in a modern design. These features can reduce setup delays, improve behaviour when packets are lost and help a connection survive certain network changes. The strongest benefits appear when the client, CDN or server and network path all support the protocol well. It is not a substitute for a reliable access connection, a responsive application, efficient page assets or a healthy origin. For everyday users, the best approach is to keep browsers updated and use a stable network; protocol negotiation normally happens in the background. For site operators, enablement should be accompanied by compatibility testing, monitoring and fallback. HTTP/3 is important because it improves the foundation beneath web requests—not because it makes every website instantly fast.

Frequently asked questions

What does HTTP/3 use instead of TCP?

HTTP/3 uses QUIC version 1 as its transport, and QUIC runs over UDP. QUIC provides reliability, congestion control, encryption integration and multiplexed streams.

Is HTTP/3 faster than HTTP/2?

It can be faster in some conditions, especially where packet loss or connection setup delays matter. Results vary with the network, server, browser, CDN and page design.

Is HTTP/3 secure?

HTTP/3 uses QUIC, which integrates TLS 1.3 or later for connection security. Encryption protects data in transit but does not guarantee that a website or application is trustworthy.

Does HTTP/3 require HTTPS?

HTTP/3 is specified for secure HTTPS origins and uses QUIC's TLS handshake. Browsers negotiate the protocol when the server advertises or otherwise makes HTTP/3 available.

What is QUIC in simple terms?

QUIC is a secure transport protocol that runs over UDP and manages connections, streams, loss recovery and congestion control. HTTP/3 uses it to carry web requests and responses.

What is head-of-line blocking in HTTP/3?

QUIC's independent streams prevent a lost packet for one stream from holding back delivery of unrelated streams in the same way that TCP can for HTTP/2. A stream still needs its missing data.

Can HTTP/3 work if UDP is blocked?

No QUIC connection can be established if the required UDP traffic is blocked. A compatible browser should fall back to a TCP-based HTTP version when available.

Does HTTP/3 work when switching from Wi-Fi to mobile data?

QUIC connection migration can preserve a connection across some network-address changes, but it depends on client and server support and successful validation of the new network path.

How can I check if my browser is using HTTP/3?

Open the browser's developer tools, inspect the Network panel and display the Protocol column. Requests using HTTP/3 are commonly shown as h3.

Should every website owner enable HTTP/3?

Owners should evaluate platform support, UDP reachability, fallback, monitoring and real-user performance. Enabling it can help, but testing is needed to confirm benefits and avoid compatibility issues.
