Ethernet Flow Control Explained: PAUSE Frames, PFC and Congestion

Why do Ethernet switches send PAUSE frames? Learn how link-level flow control protects buffers, how PFC pauses selected priorities, and why congestion can spread through a network.

By Suraj Vishwakarma · Published by TEZZ CONNECT · Published 27 November 2026 · Updated 27 November 2026

A network switch can receive Ethernet frames faster than it can forward them. A server may send a burst of traffic, several input ports may compete for one output link, or a downstream device may temporarily stop accepting data. If the receiving buffer fills, frames can be dropped. Ethernet flow control provides a link-level way for a receiver to ask its directly connected peer to pause transmission temporarily.

The best-known mechanism is the IEEE 802.3x PAUSE frame. It pauses all data traffic in the affected direction on a full-duplex Ethernet link for a specified interval. Priority-based Flow Control (PFC), standardised in IEEE 802.1Q, makes the idea more selective: it can pause particular traffic priorities while other priorities continue.

These mechanisms are useful in some environments, especially carefully engineered data-centre fabrics, but they are not universal speed boosters and they do not solve every congestion problem. A pause can move congestion upstream, create head-of-line blocking, increase latency or contribute to a pause storm. Understanding where the pause originates and which traffic it affects is essential before enabling it.

1. What is Ethernet flow control?

Flow control is a feedback mechanism between two directly connected Ethernet devices. The receiver monitors its ability to accept incoming frames. When available buffering becomes scarce, it can send a control frame asking the transmitting peer to stop sending for a short time. When the receiver is ready again, it can allow transmission to resume.

Think of a loading bay with a limited storage area. If deliveries arrive faster than workers can unload them, the bay fills. The receiver can signal the next truck to wait briefly. The signal does not make the unloading process faster; it temporarily reduces the arrival rate so the limited buffer does not overflow.

In Ethernet, flow control is implemented at the link layer and is local to a link. It does not travel through routers as an end-to-end instruction. A switch that receives a PAUSE frame responds on the relevant port; it does not simply forward that control frame across the network to the original source.

Flow control is distinct from TCP flow control and congestion control. TCP uses transport-layer mechanisms between endpoints to regulate a byte stream and respond to network congestion. Ethernet PAUSE and PFC act between adjacent link partners, independently of whether the payload carries TCP, UDP, storage traffic or another protocol.

2. Why Ethernet buffers overflow

A switch commonly has multiple ingress ports feeding queues associated with egress ports. If several input links send traffic toward one slower or busy output, the switch must temporarily buffer frames. Congestion occurs when the offered traffic exceeds the capacity available on that output or queue.

For example, four 10-gigabit-per-second ports may simultaneously send traffic toward one 10-gigabit-per-second egress port. The switch cannot transmit all four inputs at their combined 40 Gbit/s rate through a 10 Gbit/s output. It queues frames while it can. If the burst lasts long enough or the buffer is insufficient, frames are discarded.

Other causes include microbursts, an oversubscribed uplink, a slow receiver, storage traffic bursts, incast patterns in distributed applications, and congestion created by multiple flows sharing a queue. Average utilisation can look modest while short bursts still exceed buffer capacity.

Packet loss is not always a failure. In many networks, queues use active queue management or drop policies to signal congestion and protect latency. TCP can retransmit lost data and reduce its sending rate. But some workloads are sensitive to loss or retransmission, which is one reason specialised data-centre designs use link-level flow control.

3. How IEEE 802.3x PAUSE frames work

IEEE 802.3x defines MAC Control PAUSE operation for full-duplex Ethernet. A receiving device sends a PAUSE control frame to its directly connected peer. The frame includes a pause-time value that tells the peer how long to suspend ordinary data-frame transmission on that link direction.

The pause timer is expressed in quanta. One quantum represents the time needed to transmit 512 bit-times at the operating link rate. The 16-bit pause-time field can represent values from zero through 65,535 quanta. A zero value is used to cancel a previously requested pause. The timer is a link-layer timing unit, not a count of milliseconds that is identical at every Ethernet speed.

When a transmitter receives a valid PAUSE frame and flow control is enabled for that direction, it temporarily stops sending data frames. It can still transmit required control traffic according to the MAC Control rules. When the pause interval expires, transmission can resume unless another pause request has extended the interval.

PAUSE frames use a reserved multicast destination address and a MAC Control EtherType/opcode combination. They are consumed by the directly connected MAC control function rather than forwarded as ordinary user data. This is why the mechanism is hop-by-hop.

Flow control configuration is directional. A device may be configured to honour received PAUSE frames, to transmit PAUSE frames when its receive buffers are congested, or both, depending on hardware and operating-system support. Vendor terminology such as send, receive, transmit, and honor can differ, so check the device's documentation rather than assuming a single toggle has the same meaning everywhere.

4. What does a PAUSE frame actually stop?

Traditional 802.3x PAUSE applies to the data transmission of the physical link in the affected direction. It does not identify an application, TCP connection, VLAN, IP address or traffic class. A sender that receives the pause request must hold back data frames for that link, even if some of those frames are unrelated to the congestion that triggered the request.

This all-traffic behaviour is simple, but it can be blunt. Imagine a server link carrying a latency-sensitive database flow and a bulk backup transfer. If a receive buffer fills because of the backup burst, a PAUSE request can stop both categories. The database flow may be delayed even though it did not cause the congestion.

PAUSE is not a bandwidth reservation or a guarantee that no packet will ever be dropped. It is a request to temporarily stop sending so the receiver can recover. If congestion persists, if pause frames arrive too late, if the buffer headroom is insufficient, or if traffic is arriving through another path, loss can still occur.

5. Priority-based Flow Control (PFC)

Priority-based Flow Control addresses the all-or-nothing limitation of classic PAUSE. PFC is standardised by IEEE 802.1Q, originally through amendment 802.1Qbb. It extends link-level pause behaviour so that a receiver can request a pause for selected traffic priorities rather than stopping every data frame on the link.

Ethernet VLAN priority information uses a three-bit Priority Code Point (PCP), giving eight priority values from 0 through 7. PFC uses an enable vector to identify which priorities should be paused and provides a pause timer for each priority. A peer can therefore stop sending frames in a selected priority class while continuing to transmit frames in other classes, subject to the configured mappings and implementation.

For example, a data-centre network may map a loss-sensitive RDMA traffic class to one priority and best-effort application traffic to another. If the receive queue for the RDMA class approaches its buffer threshold, PFC can pause that priority without automatically stopping every other class on the physical link.

PFC is often discussed alongside Data Center Bridging (DCB), including Enhanced Transmission Selection (ETS) and DCBX. These technologies address related aspects of traffic classification, bandwidth allocation and configuration exchange. PFC itself is not a complete congestion-control architecture and does not decide how applications should be prioritised.

Priority mapping must be consistent across endpoints, NICs and switches. If one device classifies traffic differently from another, the pause may affect the wrong queue or fail to protect the intended traffic class. Network operators must verify VLAN PCP, traffic-class mapping, queue assignment and DCB settings across the complete path.

Neither mechanism should be confused with IEEE 802.1Qbb's broader data-centre context or with end-to-end congestion signalling such as Explicit Congestion Notification (ECN). PAUSE and PFC are link-level backpressure tools. ECN marks packets to signal congestion to endpoints or transport protocols, where supported, rather than asking an adjacent Ethernet transmitter to stop an entire link or priority.

7. What is head-of-line blocking?

Head-of-line blocking occurs when traffic waiting at the front of a queue prevents other traffic behind it from moving, even if that other traffic could otherwise make progress. Link-wide PAUSE can create a related effect because all data traffic on the paused link direction is held, including traffic that is not responsible for the congested destination.

Suppose a switch port receives frames for several destinations. One downstream path is congested and triggers a pause condition. If the port's transmission is stopped as a whole, frames destined for uncongested paths may also wait. This can reduce throughput and increase latency beyond the original bottleneck.

PFC improves granularity by pausing selected priorities, but it does not eliminate every form of head-of-line blocking. If multiple unrelated flows share the same paused priority and queue, they can still be held together. Queue design, traffic classification and buffer architecture remain important.

8. Congestion spreading and pause storms

Flow control can move congestion rather than remove it. A switch that cannot drain a queue may pause its upstream neighbour. That neighbour may then fill its own buffers and send a pause request farther upstream. Congestion can spread across several links, potentially affecting traffic that was not initially congested.

With PFC, this is sometimes described as congestion spreading or a PFC storm. A priority can remain paused or repeatedly pause across multiple hops. If the network has cyclic dependencies between queues, backpressure can contribute to deadlock-like conditions where traffic cannot make progress.

Data-centre operators use design controls to reduce these risks. Examples include careful topology and routing, buffer and headroom calculations, queue isolation, congestion monitoring, PFC watchdogs, and end-to-end congestion control. The precise safeguards depend on the switch ASIC, NIC, topology and traffic workload.

A PFC watchdog can detect a queue or priority that remains paused for an abnormal period and take a configured protective action. Such actions may include dropping traffic or disabling PFC for the affected queue, depending on platform support. A watchdog is not a substitute for correct design, but it can limit the impact of a stuck pause condition.

9. Buffer headroom: why pause must arrive early enough

Sending a pause frame does not instantly stop the peer. The peer must receive and process the control frame, stop scheduling the affected traffic, and allow frames already in flight to finish arriving. The receiver therefore needs enough buffer space—often called headroom—to absorb traffic during this reaction interval.

Headroom depends on factors such as link speed, physical distance, cable and transceiver delay, switch and NIC processing latency, scheduling behaviour, frame size and the time required to propagate pause control. Faster links can deliver more data during the same reaction interval, so a headroom calculation that is safe at one speed may be inadequate at another.

If the pause threshold is configured too close to the buffer limit, frames can arrive after the buffer is full and still be dropped. If thresholds are too conservative, the usable buffer may be reduced and throughput can suffer. Buffer thresholds must be engineered for the actual device and topology, not copied blindly from another switch model.

Some platforms support automatic or measured headroom configuration, while others require explicit profiles or vendor-specific calculations. Operators should use the manufacturer's design guidance and validate with counters and controlled testing.

10. PFC, RDMA and loss-sensitive data-centre traffic

Remote Direct Memory Access (RDMA) allows systems to transfer data between memory regions with low CPU overhead and low latency under supported configurations. RoCE (RDMA over Converged Ethernet) carries RDMA traffic over Ethernet and has historically been deployed in fabrics designed to minimise packet loss.

PFC can be used to protect a designated RoCE traffic priority from congestion-related drops on individual links. But describing an entire network as lossless because PFC is enabled is misleading. PFC is hop-by-hop, depends on consistent configuration and adequate buffering, and does not prevent every possible loss cause. Errors, congestion outside the protected class, misclassification, buffer exhaustion and failures elsewhere can still affect delivery.

Modern data-centre designs often combine PFC with ECN and transport-level congestion control. PFC can provide a local safety mechanism, while ECN can signal congestion to endpoints so senders reduce their rates. The balance is implementation- and workload-specific; neither PFC nor ECN should be enabled without a clear design and monitoring plan.

11. How PAUSE quanta relate to time

The PAUSE timer is measured in units called quanta, with each quantum equal to 512 bit-times at the link rate. Therefore the actual duration represented by a fixed number of quanta depends on Ethernet speed.

As a simplified calculation, one quantum at 1 Gbit/s corresponds to 512 bits divided by 1,000,000,000 bits per second, or 512 nanoseconds. At 10 Gbit/s, it corresponds to 51.2 nanoseconds. The same timer value therefore represents a shorter wall-clock interval on a faster link.

The maximum 16-bit value is 65,535 quanta. The field is not an arbitrary number of milliseconds and should not be interpreted without considering link speed. Implementations may also refresh or extend pause behaviour through subsequent control frames.

For PFC, the pause time is represented separately for each priority in the PFC control information. This lets a peer pause different priorities for different durations, within the protocol's defined encoding and device capabilities.

12. How to troubleshoot Ethernet flow control

When a network experiences unexplained latency, packet drops or throughput collapse, check whether PAUSE or PFC is active before changing settings. A pause counter can reveal that a port is being asked to stop transmitting or that it is generating pause requests because its receive buffers are filling.

Useful checks

  • Inspect interface configuration: determine whether transmit and receive flow control are enabled and whether the platform supports symmetric or asymmetric settings.
  • Read counters: check transmitted and received PAUSE frames, PFC frames per priority, queue drops, buffer occupancy and interface errors.
  • Identify the affected direction: a received PAUSE frame affects the local device's transmit direction toward its peer; a transmitted PAUSE frame indicates the local receiver is asking the peer to pause.
  • Check priority mapping: for PFC, verify VLAN PCP, traffic-class mapping, queue selection and the priorities enabled on every relevant link.
  • Trace upstream: repeated pause events may show congestion moving toward the source. Inspect adjacent ports rather than looking only at the first port with drops.
  • Look for persistent pauses: unusually high or continuous PFC pause counters may indicate congestion, a stuck queue, a misbehaving peer or a configuration mismatch.
  • Correlate with application symptoms: compare pause events with latency, retransmissions, RDMA completion behaviour, throughput and queue occupancy.

Example Linux checks

On supported Linux systems, ethtool can display link settings and driver statistics. The exact names depend on the NIC driver:

ethtool -a eth0
ethtool -S eth0
ethtool eth0

The first command may show pause parameters supported by the interface. The statistics command can expose driver-specific counters such as pause frames or priority pause events. A switch CLI or telemetry system is usually needed to see queue-level buffer behaviour across the fabric.

Do not assume a command or counter exists on every device. Some NICs expose PFC counters only through driver-specific statistics, firmware tools or vendor utilities. Record the baseline before changing settings so that counter increments can be interpreted correctly.

13. Should you enable Ethernet flow control at home or in an office?

For most home internet users, Ethernet PAUSE is not a setting that needs to be changed to improve broadband speed. A slow speed test, high Wi-Fi latency or a congested internet connection is usually not fixed by enabling link-level PAUSE on a random router or PC port.

In small office networks, the correct setting depends on the switch, NIC, topology and traffic. Enabling flow control on one side only may not produce the intended behaviour. Enabling it everywhere without understanding the consequences can create unnecessary pauses and make congestion harder to diagnose.

For data-centre or storage networks, PFC may be appropriate for specific traffic classes when the design calls for it. That decision should include end-to-end priority mapping, buffer headroom, congestion control, watchdogs and operational monitoring. Follow platform-specific validated designs rather than a generic internet tutorial.

14. Flow control is not the same as congestion control

Flow control protects a receiver from being overwhelmed. Congestion control responds to a network path whose capacity is insufficient for the offered traffic. The distinction matters because a receiver can be protected locally while congestion remains elsewhere.

TCP uses receiver-advertised windows to prevent a sender from exceeding the receiver's ability to accept data, and congestion-control algorithms to adapt to network conditions. ECN can mark congestion without dropping a packet when endpoints and network devices support it. Queue management and traffic shaping can smooth bursts or manage bottlenecks. Ethernet PAUSE and PFC instead send a direct link-level request to stop transmission.

These mechanisms can coexist, but they operate at different layers and have different failure modes. A good design selects the mechanism that addresses the actual problem instead of treating every form of backpressure as interchangeable.

15. Common Ethernet flow-control myths

Myth: PAUSE frames make Ethernet faster.

They do not increase link capacity. They temporarily stop transmission to reduce the chance of receiver-buffer overflow.

Myth: PFC makes an entire network lossless.

PFC is a hop-by-hop pause mechanism for selected priorities. It cannot prevent every source of packet or frame loss.

Myth: A PAUSE frame is forwarded through switches to the original sender.

PAUSE and PFC operate between directly connected link partners. Each hop handles its own control frames.

Myth: PFC eliminates head-of-line blocking.

It provides per-priority granularity, but traffic sharing a paused priority or queue can still be blocked together.

Myth: If pause counters increase, the link is faulty.

Pause counters indicate flow-control activity. They may reflect congestion or configured behaviour, not necessarily a physical fault.

Myth: Enabling PAUSE on every interface is safest.

Broad deployment can spread congestion and affect unrelated traffic. Configuration should follow the network design and hardware guidance.

16. A deployment checklist

  • Identify the exact congestion or buffer-overrun problem before enabling flow control.
  • Confirm support and configuration semantics on both link partners.
  • Choose link-wide PAUSE or per-priority PFC based on the traffic design.
  • Verify full-duplex operation and compatible link settings.
  • Map priorities consistently across NICs, switches and endpoints.
  • Calculate or validate receive-buffer headroom for link speed and round-trip delay.
  • Consider head-of-line blocking, congestion spreading and cyclic dependencies.
  • Use PFC watchdog and congestion telemetry where supported and appropriate.
  • Combine link-level backpressure with suitable end-to-end congestion control for the workload.
  • Measure pause counters, queue drops, latency and throughput before and after changes.
  • Document rollback steps and test failure scenarios in a controlled environment.

17. The practical takeaway

Ethernet flow control is a precise tool for managing short-term receive-buffer pressure between adjacent devices. IEEE 802.3x PAUSE stops all data traffic in the affected link direction, while PFC extends pause behaviour to selected priority classes. Both can reduce drops when correctly designed, but neither creates extra bandwidth or removes the underlying bottleneck.

The same backpressure that protects one buffer can move congestion upstream. That is why buffer headroom, traffic classification, queue design, watchdogs and end-to-end congestion management matter as much as the pause frame itself. For home and ordinary office networks, leave these controls to the device defaults unless there is a measured reason to change them. For data-centre fabrics, use a validated design and monitor the complete path.

Frequently asked questions

1. What is Ethernet flow control?

Ethernet flow control lets a receiving device ask its directly connected peer to pause transmitting data frames temporarily when receive buffers are under pressure. It is a link-layer mechanism, not an end-to-end congestion-control protocol.

2. What is an IEEE 802.3x PAUSE frame?

A PAUSE frame is a MAC Control frame used on full-duplex Ethernet to request that the peer stop sending data frames for a specified interval. Traditional PAUSE applies to all data traffic in the affected link direction.

3. What is the difference between Ethernet PAUSE and PFC?

IEEE 802.3x PAUSE stops all data traffic on the link direction. Priority-based Flow Control (PFC), defined by IEEE 802.1Q, can pause selected traffic priorities while other priorities continue.

4. What does PFC stand for in networking?

PFC stands for Priority-based Flow Control. It provides per-priority link-level pause behaviour and is commonly associated with Data Center Bridging and selected loss-sensitive traffic classes.

5. Does Ethernet flow control increase network speed?

No. Flow control does not increase link capacity. It temporarily reduces transmission to help prevent receive-buffer overflow and frame drops. It can also increase latency when traffic is paused.

6. What is a PAUSE quantum?

A pause quantum represents 512 bit-times at the Ethernet link rate. The same pause-time field therefore represents a shorter duration on a faster link than on a slower link.

7. Can PAUSE frames cause network congestion?

They can move congestion upstream. A paused device may build queues of its own and send pause requests to its upstream peer. This can spread congestion and affect traffic beyond the original bottleneck.

8. What is a PFC storm?

A PFC storm is a condition in which pause requests persist or spread across a fabric, potentially preventing a traffic priority from making progress. Monitoring, correct buffer design and PFC watchdogs can help manage the risk.

9. Is PFC required for RoCE?

PFC is used in many loss-sensitive RoCE Ethernet designs, but it is not a universal guarantee of lossless delivery. RoCE network design may also use ECN, transport congestion control, queue management and validated vendor-specific configurations.

10. Should I enable Ethernet flow control on my home router?

Usually not just to improve internet speed. Flow control is a link-level buffer-protection mechanism and is not a general broadband performance fix. Change it only when the device documentation and a measured network issue justify doing so.
