What Is TLS? HTTPS, Certificates and the TLS Handshake Explained

Every time you see HTTPS in a browser, a security protocol is working behind the scenes. Learn how TLS protects data, how digital certificates help establish website identity, what happens during a TLS 1.3 handshake and how to diagnose common certificate problems.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Why secure connections matter

A normal web request can carry far more than the name of a page. It may include account credentials, session cookies, personal information, payment details, search terms, private messages or data returned by an application. If that information travels across an unprotected connection, a person or system with access to the network path may be able to observe or alter it. Public Wi-Fi, shared networks, compromised routers and misconfigured infrastructure all make transport security important.

Transport Layer Security, usually called TLS, is the cryptographic protocol that helps protect data exchanged between two endpoints. On the web, it is most familiar as the security layer used by HTTPS. TLS can provide confidentiality, integrity and authentication: confidentiality helps keep content unreadable to outsiders, integrity helps detect modification, and authentication helps a client verify that it is communicating with the intended server.

These protections are powerful, but they have a defined scope. TLS protects a connection; it does not certify that a website is honest, that a user has permission to access a record, or that a device is free from malware. Understanding what TLS does—and what it does not do—makes the browser's security indicators easier to interpret.

What is TLS?

TLS stands for Transport Layer Security. It is a standard protocol that allows two communicating endpoints to negotiate security parameters, authenticate one another when required, establish shared cryptographic keys and protect application data. A browser can use TLS to connect securely to a web server, but TLS is not limited to websites. It is also used by email protocols, messaging systems, APIs and other network applications.

The protocol has two closely related jobs. The handshake protocol negotiates the connection's cryptographic settings and establishes key material. The record protocol uses the negotiated keys to protect application data as it is sent. In a typical HTTPS connection, HTTP messages are carried inside the protected TLS channel. The browser and server do not need to invent a new encryption system for every page; they follow the shared protocol and cryptographic algorithms they support.

TLS is application-protocol independent. HTTP is one protocol that can run over it, while other application protocols can also use TLS according to their own specifications. The current widely deployed major version is TLS 1.3, defined in IETF RFC 8446. TLS 1.2 remains supported by some systems for compatibility, while obsolete SSL versions and older TLS versions should not be enabled for modern public services.

SSL versus TLS: why people still say “SSL certificate”

SSL stands for Secure Sockets Layer, an older family of protocols that preceded TLS. SSL is obsolete and should not be used to secure modern connections. TLS evolved from the same broad design lineage, but it is a distinct protocol with updated cryptographic mechanisms and security requirements. When people refer to an “SSL certificate,” they usually mean the digital certificate installed for a website that uses HTTPS with TLS.

The certificate itself is not an SSL or TLS protocol. It is a digitally signed data structure, commonly using the X.509 format, that binds information such as a domain name to a public key. A browser checks that certificate as part of authenticating the server during a TLS connection. The informal phrase “SSL certificate” remains common in hosting dashboards, support conversations and product descriptions, but “TLS certificate” or “HTTPS certificate” is more technically accurate.

Do not assume that a vendor's use of the word SSL means it is offering an obsolete protocol. Check the actual server configuration and supported protocol versions. Conversely, a product that advertises an SSL certificate does not automatically guarantee that TLS is configured correctly. Certificate issuance and protocol configuration are related but separate tasks.

What is HTTPS?

HTTPS means HTTP Secure: HTTP carried over a secure connection, normally TLS. When a browser opens an HTTPS URL, it establishes a TLS connection to the server before exchanging the protected HTTP request and response. The familiar padlock or connection information in browser interfaces indicates that the connection meets the browser's security checks; it is not a review of the website's reputation or business practices.

HTTPS protects the contents of the HTTP exchange while it travels between the browser and the TLS endpoint. This includes page content, form submissions, cookies and most request metadata carried inside the encrypted application data. It also helps prevent an on-path attacker from silently changing the protected response. Modern browsers treat HTTPS as a secure context for many web platform features, which is one reason all pages and subresources should be served securely.

HTTPS does not make every detail invisible. Network observers can still see the destination IP address, connection timing, approximate traffic volume and some metadata associated with establishing a connection. DNS lookups may also reveal domain names unless encrypted DNS is used, and encryption of DNS does not hide all other network metadata. HTTPS is essential, but it is one component of a broader privacy and security strategy.

How digital certificates establish website identity

A digital certificate helps a browser associate a public key with a domain name. The server presents its certificate during the TLS handshake. The browser checks whether the certificate is valid for the requested hostname, whether it is within its validity period, whether the certificate chain leads to a trusted root and whether the signatures and usage constraints are acceptable under its validation rules.

The public key in the certificate is not a password and is not secret. It can be shared openly. The corresponding private key must remain under the control of the legitimate server operator or the service that terminates TLS. During certificate-based authentication, the server proves possession of the matching private key through the handshake. An attacker who copies only the public certificate cannot impersonate the server without the private key, assuming the cryptographic and operational controls remain sound.

Certificates can contain several identity and policy fields, including subject information, subject alternative names, issuer, serial number, public key, validity dates, key usage and extended key usage. Modern browser hostname verification relies on the appropriate DNS names in the Subject Alternative Name extension. A certificate issued for one hostname does not automatically cover every other domain on the same server.

Certificate Authorities, root certificates and trust chains

A Certificate Authority (CA) is an organisation or service trusted to issue certificates under defined policies. A CA validates that the applicant is authorised to request a certificate for a domain, then signs the certificate or has an intermediate CA sign it. Browsers and operating systems maintain trust stores containing root certificates or other trust anchors. The browser can validate a server's certificate by following a chain of signatures from the server certificate through intermediate certificates to a trusted root.

The server commonly sends its own certificate and one or more intermediate certificates. The root certificate is usually already present in the client's trust store and is not normally sent as part of the server's chain. The client verifies the signatures and constraints along the path, checks the hostname and validity period, and applies its trust policy. The exact trust-store contents and validation behaviour can differ between browsers, operating systems and managed enterprise devices.

A certificate chain can fail even when the leaf certificate itself has not expired. The server may omit an intermediate, send an incorrect chain, use an issuer that the client does not trust or present a certificate that does not match the requested hostname. This explains why installing a certificate file alone may not be enough: the server must present the correct chain and the client must be able to build a valid path to a trust anchor.

For a practical example, Let's Encrypt explains its issuance process, including domain validation and certificate requests. Its Chains of Trust page describes root and intermediate certificates and why chain selection affects compatibility with clients.

Public keys, private keys and encryption

Public-key cryptography uses a mathematically related key pair. The public key can be distributed, while the private key must be protected. In TLS, public-key cryptography supports authentication and key establishment, but modern TLS does not normally encrypt every application byte directly with a public key. Instead, the handshake establishes shared secret material from which symmetric traffic keys are derived.

Symmetric encryption uses the same secret key for encryption and decryption. It is efficient for protecting large amounts of data, which makes it suitable for the application traffic that follows the handshake. TLS also uses authenticated encryption so that a recipient can detect if protected data has been modified. The handshake itself is cryptographically protected and verified so that an active attacker cannot silently alter the negotiated parameters.

Private-key protection is therefore critical. If a server's private key is stolen, an attacker may be able to impersonate that server in some circumstances, depending on the key type, protocol configuration, certificate status and other controls. Operators should restrict access to private-key files, use secure key storage where appropriate, monitor access, rotate compromised keys and automate renewal without exposing secrets in source repositories or public logs.

What happens during a TLS 1.3 handshake?

The handshake is the initial negotiation that creates a secure session. At a high level, the client sends a ClientHello message containing the TLS versions, cipher suites, key shares and extensions it supports. The server responds with its selected parameters and key share. Both sides derive shared secrets, and the server sends authentication information when certificate-based authentication is used. The client validates the certificate and verifies the server's proof of private-key possession. The endpoints then confirm the handshake and derive traffic keys for encrypted application data.

The process is more precise than a simple “browser asks for encryption” exchange. The client and server must agree on compatible cryptographic options. The certificate must authenticate the intended server name, and the handshake transcript is protected so that negotiation tampering can be detected. TLS 1.3 removed several older and less secure options, simplified the handshake and generally reduces the number of round trips needed before protected application data can be sent compared with older configurations.

In a common full TLS 1.3 handshake using certificate authentication, the browser sends ClientHello, the server replies with ServerHello and encrypted handshake messages including its certificate and proof, and the client validates and completes the exchange. The endpoints then exchange application data under the negotiated traffic keys. The exact message sequence can vary with extensions, resumption, client authentication and the application protocol. For the normative details, see RFC 8446.

How TLS 1.3 improves connection setup

TLS 1.3 was designed to simplify and strengthen the handshake while reducing setup latency. A typical full handshake can complete in one round trip after the initial ClientHello and server response, rather than requiring the additional round trip associated with older full-handshake patterns. This matters on high-latency networks because each round trip adds waiting time before an application can exchange useful data.

TLS 1.3 also supports session resumption. After a successful connection, the server can provide a ticket that allows the client to resume a later session with less negotiation. With 0-RTT data, a client may send certain application data in its first flight when resuming a session. This can reduce latency, but early data has replay considerations. Applications must not use 0-RTT for operations where replaying a request could cause harm, such as a non-idempotent payment or account action. Support and policy vary, and the application must understand the security trade-off.

Performance depends on more than TLS version. DNS resolution, network routing, server processing, certificate-chain size, connection reuse, content delivery and the page's own resource dependencies all affect how quickly a site becomes usable. TLS 1.3 can reduce handshake overhead, but it cannot compensate for a slow origin or an overloaded connection. For more on the web transport layer, see our guide to HTTP/3 and QUIC.

Certificate types and what they prove

Publicly trusted web certificates are often described by their validation level. Domain Validation (DV) certificates confirm control over a domain under the CA's validation process. Organization Validation (OV) certificates include additional checks about the requesting organisation. Extended Validation (EV) certificates involve a more extensive identity verification process under applicable CA and browser policies. These labels describe validation procedures; they do not change the basic encryption strength of TLS by themselves.

A DV certificate can provide strong transport encryption and domain authentication when correctly issued and configured. A paid certificate is not automatically more secure than a free certificate for the same cryptographic purpose. Organisations may choose OV or EV for policy, compliance, procurement or identity-assurance reasons, but users should not interpret a certificate's validation category as proof that a website's products, offers or content are safe.

Wildcard certificates can cover a domain and its eligible subdomains according to the certificate's name constraints, while multi-domain certificates can list several names. The correct choice depends on how services are hosted and separated. A wildcard can simplify certificate management but may increase the impact if its private key is compromised across multiple services. Separate certificates and keys can reduce that blast radius.

Certificate issuance, renewal and revocation

To issue a public certificate, a CA needs evidence that the applicant controls the domain or meets the relevant identity-validation policy. Automated Certificate Management Environment (ACME) is a protocol that allows compatible clients to request, renew and revoke certificates automatically. Let's Encrypt uses ACME to make browser-trusted certificates available without requiring a manual human exchange for every renewal.

Common domain-validation methods include placing a specific token at a well-known HTTP path, publishing a DNS record or responding to a TLS-based challenge. The CA checks the challenge, authorises the account for the domain and issues the certificate request if the requirements are met. The certificate is then installed on the server or service that terminates TLS. Automated renewal reduces the chance of an expired certificate interrupting a website, but automation must be monitored: failed DNS updates, firewall changes, expired API credentials or incorrect deployment hooks can still prevent renewal.

Revocation is the process of withdrawing trust in a certificate before its scheduled expiry, for example after a private key is compromised or a certificate was issued incorrectly. Certificate Revocation Lists (CRLs) and Online Certificate Status Protocol (OCSP) are mechanisms used to distribute status information, though browser behaviour and ecosystem practices vary. Operators should follow their CA's revocation procedure after a confirmed compromise and replace the affected certificate and key.

Let's Encrypt's FAQ explains that its default certificates have a 90-day lifetime and that private keys are generated and managed by subscribers, not stored by Let's Encrypt. Shorter certificate lifetimes make reliable automation and monitoring increasingly important.

Common HTTPS and certificate errors

A “certificate expired” warning means the certificate's validity period has ended according to the client's clock. The operator should renew and deploy a valid certificate. A “name mismatch” warning means the certificate does not cover the hostname in the address bar. This can happen when a site is configured for the apex domain but not the www hostname, when a reverse proxy sends the wrong certificate or when a server uses a default certificate for an unknown host.

An “untrusted issuer” or chain error can mean the client cannot build a valid chain to a trusted root. The server may be missing an intermediate certificate, the certificate may have been issued by a private CA that the device does not trust, or the local trust store may be outdated. A “not yet valid” warning may indicate that the certificate was issued with a future start time or that the device clock is incorrect. Captive portals and enterprise TLS inspection can also cause unexpected certificate warnings.

For website owners, check the hostname, certificate dates, complete chain, server configuration and renewal logs. Test from more than one browser and network to separate server problems from local device or network issues. For visitors, do not bypass a certificate warning on a site where you would enter passwords, payment information or personal data. Check the URL carefully, update the browser and operating system, verify device date and time, and try a trusted network if interception is suspected.

Mixed content: when an HTTPS page loads insecure resources

A page may be delivered over HTTPS but still request an image, script, stylesheet, font or API from an insecure HTTP URL. This is called mixed content. Some browsers automatically upgrade certain resource requests, while active mixed content such as scripts may be blocked because it can undermine the security of the page. A site that has migrated its main URL to HTTPS should update all internal resource references and third-party integrations to secure URLs.

Mixed content can cause missing images, broken scripts, incomplete styling or browser console warnings. Developers should inspect the browser's developer tools, search source code and content databases for old HTTP references, update external integrations and configure redirects where appropriate. A Content Security Policy can help identify or restrict insecure resource loading, but it should be tested carefully to avoid breaking legitimate functionality.

HTTPS deployment should also include secure cookies, appropriate redirect behaviour, correct canonical URLs, valid subresource references and a deliberate policy for HTTP-to-HTTPS upgrades. HSTS can instruct browsers to use HTTPS for a domain in future visits, but it should be enabled only after HTTPS is consistently working across the intended hostnames.

Does HTTPS mean a website is trustworthy?

No. HTTPS means the browser has established a connection that passed its TLS and certificate checks for the domain. It does not mean that the domain belongs to a reputable business, that the site is free from malware, or that the person operating it will treat information responsibly. Phishing sites, scam stores and malware distribution pages can all use valid HTTPS certificates.

Before entering sensitive information, check the domain name carefully, use bookmarks for important services, avoid unexpected links and consider whether the requested information makes sense. A valid certificate is necessary for secure transport, but it is not a substitute for fraud detection, safe browsing habits, account security or trustworthy business practices. Password managers can also help identify domain mismatches because they generally do not autofill credentials on a lookalike domain.

Practical checklist for website owners

  • Use modern TLS configurations and disable obsolete SSL and deprecated TLS versions.
  • Serve every page and subresource over HTTPS, with correct redirects from HTTP.
  • Install the complete certificate chain and confirm all required hostnames are covered.
  • Protect private keys, restrict access and never commit them to public source repositories.
  • Automate certificate renewal and alert on failures and approaching expiry.
  • Monitor certificate transparency and CA notifications where relevant to your risk model.
  • Use secure cookies, review HSTS carefully and avoid mixed content.
  • Test from multiple browsers, operating systems and networks after certificate changes.
  • Document certificate ownership, renewal responsibility and emergency revocation steps.

Frequently asked questions

1. What does TLS stand for?

TLS stands for Transport Layer Security. It is a cryptographic protocol that helps authenticate endpoints and protect data exchanged over a network from eavesdropping and tampering.

2. Is TLS the same as HTTPS?

No. HTTPS is HTTP carried over a secure connection, normally using TLS. TLS is the security protocol; HTTPS is the web protocol combination that uses it.

3. What is an SSL certificate?

The term SSL certificate is commonly used for a digital certificate used with HTTPS, but modern websites use TLS rather than the obsolete SSL protocols. The certificate helps a client authenticate the server's domain and public key.

4. How does a browser know a certificate is trusted?

The browser or operating system checks the certificate's name, validity period, signatures and chain to a trusted root, along with applicable usage and policy requirements. Trust depends on the client's trust store and validation rules.

5. What happens during a TLS 1.3 handshake?

The client and server negotiate cryptographic parameters, establish shared secrets, authenticate the server with its certificate when certificate authentication is used, verify the handshake and derive traffic keys for encrypted communication.

6. Does HTTPS encrypt everything about a website visit?

HTTPS protects HTTP content in transit, but it does not hide every network detail. Observers may still learn IP addresses, timing, traffic volume and some connection metadata.

7. Why does a website show a certificate warning?

A warning can appear when a certificate is expired, does not match the domain, has an incomplete or untrusted chain, is not yet valid, or cannot be validated because of device time or network interception problems.

8. Are free HTTPS certificates secure?

A properly issued and configured domain-validation certificate can provide the same basic TLS encryption and server authentication regardless of whether it was free or paid. Security depends on correct issuance, private-key protection and server configuration.

9. How often should an HTTPS certificate be renewed?

Renewal timing depends on the certificate authority and certificate lifetime. Operators should automate renewal where possible and monitor expiry so a failed renewal does not interrupt service.

10. Can TLS make a malicious website safe?

No. TLS protects the connection to the authenticated domain, but it does not prove that the site's content, business, downloads or requests are honest. A phishing or malicious website can also use HTTPS.
