Why Is DNS Slow? How to Diagnose Website Lookup Delays

Learn why DNS lookups can delay websites, how caching and resolvers work, how to test DNS response time, and how to troubleshoot slow or failed domain resolution.

By Suraj Vishwakarma · Published by TEZZ CONNECT

When a website pauses before it starts loading, DNS may be part of the delay. This guide explains how domain lookups work, how to measure them and how to distinguish a resolver problem from slow Wi-Fi, a slow website or a wider connection issue.

Why can a website take time to open even when your internet is fast?

You tap a link, the browser waits, and then the page suddenly appears. A speed test run a moment later reports a strong download rate. It is tempting to assume the website or internet connection is simply slow, but the delay may happen before the browser has even started downloading the page: the device may be waiting for DNS to find the address associated with the domain name.

DNS, the Domain Name System, is often described as the internet's address book. It helps a device discover the network address for a name such as example.com. If the lookup is delayed, the browser cannot begin connecting to the destination as quickly. This can make the first visit to a site feel slow even when the connection can transfer data quickly once the connection is established.

DNS is only one part of website loading. The browser may also need to establish a transport connection, negotiate encryption, contact a content delivery network, download resources, run scripts and render the page. A slow first paint is not proof of a DNS problem. The useful question is whether name resolution itself is taking an unusually long time, failing, or returning an answer that sends the browser to a distant or unreachable service.

What DNS does before a browser connects

When an application needs to reach a domain, it asks a DNS resolver for the relevant record. The record may contain an IPv4 address (an A record), an IPv6 address (an AAAA record), or other information used by the application. The device usually starts with a local DNS client or stub resolver, which sends the question to a configured recursive resolver.

A recursive resolver can answer from its cache if it already has a valid record. If it does not, it performs the work needed to find the answer, querying the DNS hierarchy and following referrals until it reaches the authoritative information for the name. The resolver then returns the answer and may cache it for the period permitted by the record's time to live.

This process is designed to avoid repeating the entire lookup for every visit. A popular domain may already be in the resolver cache, so the answer can be returned quickly. A cache miss can require additional network exchanges and may take longer, especially if authoritative servers are distant, overloaded or temporarily unreachable.

What people mean by a slow DNS lookup

A slow DNS lookup means the time between requesting a name and receiving a usable DNS response is longer than expected. It can affect the initial connection to a site or application. The delay may be intermittent: one domain may be slow while another opens immediately, or the first visit may be slow while repeat visits are faster because an answer has been cached.

A failed lookup is different from a slow successful lookup. Errors such as NXDOMAIN indicate that the queried name does not exist in the DNS view being used. A timeout means the client did not receive a response in time. SERVFAIL indicates that the resolver could not complete the resolution. These errors have different causes and should not all be treated as a reason to switch DNS providers.

DNS response time also differs from ping time to a DNS server. A ping measures network round-trip time for ICMP packets to a host. It does not measure the full process of resolving a domain. A resolver can have a relatively high ping but answer from a nearby cache quickly; another can have a low ping but take longer to resolve uncached names. Measure actual DNS queries when diagnosing lookup performance.

The most common reasons DNS becomes slow

A resolver cache miss is one reason a lookup can take longer. If the resolver has no fresh answer, it must contact other DNS servers. The number of exchanges and the network distance to authoritative infrastructure can affect the result. A domain with complicated delegation, unreliable authoritative servers or geographically distant DNS infrastructure may take longer to resolve.

An overloaded recursive resolver can also introduce delay. If a resolver is processing more requests than its resources comfortably support, queries may wait, be retried or time out. This can happen with an ISP resolver, a public resolver, a router acting as a local forwarder, or a DNS service configured by an organisation.

Network conditions matter. Packet loss, unstable Wi-Fi, routing problems, firewall rules and captive portals can interrupt DNS requests or cause retries. Traditional DNS commonly uses UDP and can also use TCP; encrypted DNS uses additional connection and encryption steps. A blocked transport or broken middlebox can make one resolver appear unavailable even while ordinary browsing partly works.

Local software can be responsible too. A VPN, security suite, parental-control filter, browser secure-DNS setting or custom DNS application may redirect queries. If multiple components try to control DNS at once, the device may use a different resolver than the one expected. Incorrect device time can also interfere with encrypted connections that rely on certificate validation.

Finally, the DNS answer may be valid but not ideal for the user's route. Many websites use content delivery networks and DNS-based traffic steering. The resolver's location and the information available to the authoritative service can influence which server address is returned. A resolver that answers quickly is not automatically the one that produces the best end-to-end route for every website.

DNS caching: why the second visit can be faster

DNS caching stores answers for a limited period so a resolver does not need to repeat the full lookup every time. The time to live, or TTL, indicates how long a record may be cached. A cache hit can reduce the number of network exchanges and make repeat lookups faster. The operating system, browser, local router or recursive resolver may each maintain a cache, depending on the platform and configuration.

Caching is not a permanent copy of the internet's address book. When a record expires, the resolver may need to fetch a fresh answer. A site owner can change DNS records, and caching rules determine when different resolvers stop using an older answer. This is why DNS changes can appear at different times for different users.

There is also negative caching. A resolver can temporarily cache information that a name does not exist or that a resolution attempt failed, under the rules defined by DNS standards. If a record is created immediately after a resolver cached an earlier negative answer, the device may continue to see the old result until that cached entry expires. Lowering the new record's TTL does not necessarily erase an already cached negative response.

Clearing the local DNS cache affects only the cache on that device. It does not automatically clear the cache on the ISP's recursive resolver, a public DNS provider or an authoritative nameserver. Repeatedly flushing a local cache is therefore not a universal way to speed up DNS. It can even make the next lookup slower because the device must ask upstream again.

How to tell DNS delay from general internet slowness

Start with a simple comparison. If a page takes a long time before any connection begins but downloads quickly once it starts, DNS may be worth investigating. If the browser connects promptly but images and files download slowly, throughput or the website's server may be the issue. If pages pause at many different stages and other applications also struggle, inspect the broader connection.

Compare several unrelated domains. If only one domain fails, the problem may be its DNS records, authoritative service, domain status or hosting. If many unrelated domains fail together, consider the configured resolver, local network, VPN, firewall or ISP. A single site can also fail because its CDN or origin is unhealthy even when DNS is working normally.

Try the same device on another network, such as a trusted mobile hotspot, and compare the result. If the domain resolves normally on the alternate network but not on the home connection, the issue may be specific to the home router, configured resolver or ISP path. Do not use an unknown public Wi-Fi network for sensitive troubleshooting.

A browser developer tools Network panel can help separate phases of page loading. Timing details may show DNS lookup, connection setup, TLS negotiation, waiting for the first byte and content download. The labels and availability vary by browser. This breakdown is more useful than assuming every pause before a page appears is a DNS problem.

How to measure DNS lookup time

Use a DNS-specific diagnostic rather than relying only on a speed test or ping. On Windows, macOS and Linux, command-line tools such as nslookup and dig can query a resolver and display the response. The exact output differs by operating system and tool version. The key information is which server was queried, whether a response arrived, which answer was returned and how long the query took.

On systems with dig installed, a basic query can be run with dig example.com. The output includes a Query time field on many versions. To ask a particular resolver, use dig @1.1.1.1 example.com or dig @8.8.8.8 example.com. These examples use public resolver addresses; availability, privacy policy and suitability should be considered before changing a device's normal configuration.

On Windows, open Command Prompt and run nslookup example.com. The output identifies the DNS server used and displays the returned address. You can query a particular resolver by specifying its address after the command, for example nslookup example.com 1.1.1.1. Not every Windows installation includes dig by default, so nslookup is a practical built-in starting point.

Run repeated queries against a mix of popular and less frequently used domains. The first response may be a cache miss and later responses may be cache hits. Do not compare one cached lookup with another resolver's uncached lookup and conclude that the first provider is inherently faster. A fair comparison uses the same set of names, multiple runs and similar network conditions.

Record results rather than relying on memory. Note the date, time, device, network type, resolver address, query name, response code and query time. Repeat at different times of day. If only one resolver shows timeouts or much longer response times, that is useful evidence. If all resolvers are slow, inspect the local network and route as well.

How to compare your ISP DNS with a public resolver

A comparison can help determine whether the configured recursive resolver is contributing to the delay. First identify the resolver currently in use. It may be set on the router, supplied automatically by the ISP, assigned by a VPN, or configured in the operating system or browser. A device may not use the resolver shown in the router settings if an application has its own secure-DNS configuration.

Choose a small set of resolvers you trust and test the same domains against each one. Public services such as Cloudflare 1.1.1.1 and Google Public DNS 8.8.8.8 publish information about their services and configuration. Check the provider's current documentation for addresses, privacy practices, supported transports and troubleshooting guidance. Do not assume that a well-known resolver is automatically the fastest from every location.

Measure more than one domain and repeat the tests. Resolver performance depends on cache state, the route from your network, authoritative server behaviour and CDN steering. A provider can be quicker for one name and slower for another. A difference of a few milliseconds may not be noticeable in everyday use, while repeated timeouts or large delays are more important.

If you decide to change DNS, record the original setting first so you can restore it. Change one place at a time: router, operating system or browser. If a VPN or managed network supplies DNS, a manual override may be blocked or may break internal services. Some ISPs and workplaces require their own DNS for local hostnames, filtering or authentication.

What changing DNS can and cannot improve

A different recursive resolver may improve the time needed to look up a domain if the current resolver is slow, unreliable or poorly routed from your network. It may also provide different filtering, security features or privacy policies. These are separate considerations and should be evaluated using the provider's documentation.

Changing DNS does not increase the physical bandwidth of a broadband plan. It does not repair weak Wi-Fi, remove packet loss, lower the geographic distance to a game server, or make a slow website's database respond faster. Once the browser has resolved the domain and established the connection, most of the page transfer is no longer a DNS lookup.

The benefit is often most visible at the beginning of a new connection or when applications repeatedly need to resolve names that are not cached. For a page that is already connected and transferring a large video, changing DNS is unlikely to make the video download faster. DNS can influence which CDN endpoint is selected, but that is a more complex interaction than simply choosing the resolver with the lowest ping.

Do not change DNS settings just because an online post claims one address is the fastest. Measure from your own network, consider privacy and filtering, and make sure the service supports the protocols your devices use. A stable resolver that returns suitable answers may be a better choice than one that wins a single latency test.

DNS over HTTPS and DNS over TLS: does encryption make lookups slower?

Traditional DNS queries are commonly sent over UDP or TCP without transport encryption. DNS over HTTPS (DoH) sends DNS messages through HTTPS, while DNS over TLS (DoT) protects DNS traffic using TLS. Both approaches can help protect DNS queries from being read or modified by some observers on the network path, but they also change how the client connects to its resolver.

Encrypted DNS requires a secure connection to the chosen resolver. That can add connection setup work, especially when a connection is not already established. Reusing connections and caching can reduce repeated overhead. In practice, performance depends on the device, browser, resolver, network path, connection reuse and whether the resolver is reachable reliably.

Encrypted DNS is not automatically faster or slower in every situation. A nearby, well-provisioned resolver may respond quickly. A distant or blocked service may perform poorly. Some networks intercept or restrict DNS traffic, and some enterprise or parental-control systems rely on local DNS policies. Enabling encrypted DNS without understanding the network can bypass expected filtering or cause internal names to stop resolving.

Browsers and operating systems may offer different secure-DNS settings. If the browser uses DoH while the operating system uses the router's DNS, command-line tests may not reflect the browser's actual path. For a fair diagnosis, identify which resolver and transport the application is using.

Why DNS sometimes fails only on one device

If a phone cannot open a domain but a laptop on the same Wi-Fi can, begin with the phone's own settings. Check whether a VPN, Private DNS mode, security app or browser-specific resolver is enabled. Android versions may expose a Private DNS setting; the wording and location can vary by manufacturer. iOS and desktop systems have their own network and profile settings.

Forget and reconnect to the Wi-Fi network only if you know the password and understand any custom settings. Check that the device has received a valid IP address, gateway and DNS server. A wrong static DNS entry or stale network profile can cause one device to behave differently from others.

If the issue affects only one browser, compare another browser and inspect its secure-DNS configuration, extensions and proxy settings. Browser extensions that block or redirect requests can create symptoms that look like DNS failures. Avoid disabling security software permanently; use a controlled temporary test only when you understand the risk and can restore the protection immediately.

If all devices on the network fail for the same names, look beyond the individual device. The router may be forwarding queries incorrectly, its upstream DNS server may be unreachable, or the ISP resolver may be having a problem. Testing with a known resolver can help isolate the layer, but keep a record of the original configuration.

How to troubleshoot common DNS errors

For NXDOMAIN, first check the spelling of the domain and whether the hostname is supposed to exist. If you manage the domain, verify the required records at the authoritative DNS provider. If a record was recently created, consider negative caching and the zone's SOA settings. Query the authoritative nameserver directly when you need to distinguish a missing record from a cached response.

For SERVFAIL, the recursive resolver could not complete the resolution. Possible causes include unavailable authoritative servers, DNSSEC validation problems, delegation errors or other upstream failures. If you manage the domain, inspect the DNS zone, delegation and DNSSEC configuration. If you are an end user, compare another resolver and report persistent failures to the domain owner or ISP with the query name and time.

For timeouts, check connectivity to the configured resolver and whether the network blocks the required DNS transport. A firewall, VPN, captive portal or router rule can interfere. Try another trusted network and compare. Do not conclude that the resolver is down solely because ping does not respond; ICMP may be filtered even when DNS queries work.

For a newly changed record that resolves differently across networks, remember that caches are distributed. The authoritative server may already have the new value while a recursive resolver still has an older cached response. Check the record's TTL and any negative cache interval. Repeatedly clearing the browser cache will not clear upstream recursive caches.

Router and ISP checks when every device is affected

Restarting a router can clear a temporary software state, but it is not a diagnostic by itself. Before rebooting, note whether the router's management interface shows the expected WAN connection, DNS server and firmware version. Check whether the issue began after a firmware update, configuration change, power interruption or ISP maintenance.

If the router provides DNS forwarding or filtering, check whether it is enabled and whether upstream resolver addresses are valid. Some routers cache DNS locally; others simply forward requests. A faulty forwarding service can affect every device even when the WAN connection itself is healthy. Use the manufacturer's documentation rather than guessing at advanced settings.

Contact the ISP if several devices experience repeated DNS timeouts or failures and the issue persists across restarts and controlled tests. Provide timestamps, affected domains, response codes, the resolver address and whether a trusted alternate network works. Ask the provider to check recursive DNS availability and any known routing or service incidents.

If the ISP's resolver is fast and reliable for most names but one website fails, the problem may belong to that domain's DNS operator or hosting provider. If only one device is affected, the ISP may not be able to fix a local configuration issue. Clear evidence helps route the problem to the right support team.

Privacy, security and choosing a resolver

A recursive resolver can observe the domain names your devices ask it to resolve, subject to the provider's logging and privacy practices. Before choosing a service, read its current privacy policy, retention statements, security documentation and terms. Do not select a resolver only because a benchmark places it first.

Encrypted DNS protects queries in transit between the client and the resolver, but it does not make browsing anonymous. The resolver still receives the query, websites can see connections to their services, and other signals may reveal activity. DoH or DoT should be understood as one layer of transport protection, not a replacement for all privacy and security controls.

Some resolvers provide malware blocking, family filtering or threat protection. These services can be useful, but filtering may also block legitimate domains or alter expected answers. If a site stops resolving after enabling a filter, check the provider's block logs or test policy settings before assuming the domain has disappeared.

For work, school or managed devices, follow the organisation's network policy. Internal services may rely on private DNS zones, split-horizon resolution or security monitoring. Manually overriding those settings can break access or violate policy.

A practical DNS troubleshooting checklist

First, confirm the exact domain and error message. Test more than one unrelated website and note whether the problem is limited to one name, one device or the whole network. Check whether the browser reports a DNS error or whether it connects and then stalls later in page loading.

Second, identify the resolver actually being used. Check the operating system, router, VPN and browser secure-DNS settings. Run a direct DNS query with nslookup or dig and record the server, response code and query time. Compare the ISP resolver with one or two trusted alternatives using the same domain list.

Third, repeat the test. Compare first and subsequent lookups, and test at different times. A first lookup may be a cache miss; later queries may be answered from cache. Avoid comparing tests with different domains or different network paths.

Fourth, isolate the network. Compare Ethernet with Wi-Fi if available, then compare the home network with a trusted alternate connection. If one device is affected, inspect its DNS and VPN settings. If all devices are affected, inspect the router and ISP resolver.

Finally, change only one setting at a time and preserve the original configuration. If the problem remains, share measured results with the ISP, domain owner or network administrator. DNS troubleshooting is most effective when the evidence shows which resolver was asked, what response it returned and how long the lookup took.

Frequently asked questions

Can DNS make my internet feel slow?

Yes. A delayed or failed lookup can delay the start of a website or application connection. DNS does not normally determine the transfer speed after a connection is established, so slow downloads may have another cause.

Does changing DNS increase download speed?

Usually not. A different resolver may improve name lookup time or reliability, but it does not increase the bandwidth of your broadband connection. It can sometimes influence CDN server selection, which may affect the route to content.

How do I test DNS response time?

Use a DNS query tool such as dig or nslookup and compare repeated queries to the same domain across resolvers. Record response time, response code and resolver address. Ping time alone is not a DNS performance test.

Why does a website open faster the second time?

The browser, operating system or recursive resolver may have cached DNS information, reducing the need for another full lookup. The browser may also have cached page resources or reused an existing connection.

What is the difference between NXDOMAIN and SERVFAIL?

NXDOMAIN means the queried name does not exist in the DNS view that answered. SERVFAIL means the resolver could not complete the resolution. They have different causes and require different troubleshooting.

Will flushing DNS fix slow browsing?

It can help when a local device has a stale or incorrect cache entry, but it does not clear the ISP or public resolver cache. Flushing the cache can make the next lookup slower because it must be resolved again.

Is Google DNS or Cloudflare DNS faster?

There is no universal winner for every location, domain and network. Compare both from your own connection using multiple domains and repeated DNS queries, and consider privacy, filtering and reliability as well as speed.

Is encrypted DNS slower?

Not necessarily. DoH and DoT add secure connection handling, but connection reuse and caching can reduce overhead. Performance depends on the client, resolver and network path.

Why does DNS fail on one device but work on another?

The affected device may use a different resolver, VPN, Private DNS setting, browser secure-DNS configuration or stale network profile. Compare the actual DNS server and settings on both devices.

How long does DNS propagation take?

There is no single universal propagation timer. Recursive resolvers cache records according to TTLs, and negative answers can also be cached. Different resolvers may therefore begin returning a changed record at different times.
