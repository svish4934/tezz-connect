Encrypted DNS Explained: DoH vs DoT vs DoQ, Privacy and Setup

DNS helps devices find online services, but traditional DNS queries can be visible on the network. Learn how DNS over HTTPS, TLS and QUIC protect the connection—and what they do not hide.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Before a device can connect to many websites and online services, it needs to translate a domain name into network information. The Domain Name System (DNS) performs that lookup. For much of the internet's history, DNS queries commonly travelled over unencrypted UDP or TCP. That made the contents observable to parties able to monitor the path between a device and its resolver.

Encrypted DNS changes how that query travels. DNS over TLS (DoT), DNS over HTTPS (DoH) and DNS over QUIC (DoQ) protect the connection between a DNS client and a resolver. They can reduce passive observation and on-path tampering, but they do not make a person anonymous, conceal every destination or guarantee that a resolver handles data responsibly.

This guide explains the protocols, how they differ, what privacy they provide, how resolver choice affects trust, and how to configure encrypted DNS without breaking local services. It also separates encrypted DNS from DNSSEC, VPNs, private browsing and content filtering—terms that are often mixed together.

1. First, what happens during a DNS lookup?

When a user enters a domain such as example.com, the device or application needs an answer that helps it connect to the service. A DNS stub resolver on the device usually sends a question to a recursive resolver. The recursive resolver may answer from cache or query other DNS servers until it obtains the required information.

A DNS response can contain different record types. An A record provides an IPv4 address; an AAAA record provides an IPv6 address; a CNAME identifies an alias; MX records identify mail exchangers; and TXT records carry text data used by many services. The client uses the response appropriate to its task.

In a common home setup, the router advertises itself as the DNS server through DHCP. The router may forward queries to an ISP resolver or another configured recursive service. In other configurations, the device itself selects a public resolver, a browser uses its own secure DNS setting, or an organisation operates an internal resolver for private domains.

The DNS lookup is separate from the later connection to the website. A device can successfully resolve a name and still fail to connect because of routing, firewall, server, TLS or application problems. Conversely, cached DNS data may let a service connect temporarily even when a new lookup would fail.

2. Why traditional DNS can expose queries

Traditional DNS commonly uses UDP port 53 and can also use TCP port 53. The DNS message itself is not encrypted by those transports. A network operator or another on-path observer may therefore be able to read the domain names being queried, subject to the observer's position and the network path.

That visibility can be used for legitimate network operations, such as malware detection, troubleshooting, parental controls and enterprise policy enforcement. It can also create privacy risks if query data is collected or inspected without a user's understanding. DNS queries may reveal interests, software services, work systems and patterns of online activity.

Unencrypted DNS also gives an on-path attacker opportunities to interfere with responses. If an attacker can alter a query or response in transit, the client might receive an incorrect address. DNSSEC can help validate signed DNS data, but it does not encrypt the query itself. Transport encryption addresses a different part of the problem.

DNS privacy is not all-or-nothing. A resolver may know which names a client asks for. A local network may observe the resolver's IP address and traffic timing. The destination service may see the client's connection. Encrypted DNS narrows what an ordinary observer on the DNS path can read; it does not erase every source of metadata.

3. What is encrypted DNS?

Encrypted DNS protects DNS messages while they travel between a client and a resolver. The client establishes an authenticated encrypted connection to a resolver endpoint, then sends DNS queries and receives responses through that connection.

Three widely discussed protocols are:

  • DNS over TLS (DoT): DNS messages are carried over a TLS connection, conventionally using TCP port 853.
  • DNS over HTTPS (DoH): DNS messages are exchanged using HTTPS, commonly on TCP port 443 or HTTP/3 over QUIC.
  • DNS over QUIC (DoQ): DNS messages are carried directly over QUIC, using its encrypted transport and stream model.

These protocols share a broad goal but are not interchangeable in every implementation. Clients need a compatible resolver, a way to authenticate it, and configuration that matches the network environment. A protocol being encrypted does not prove the selected server is the one the user intended to trust.

The IETF specifications define protocol behaviour. RFC 7858 describes DNS over TLS, RFC 8484 defines DNS Queries over HTTPS, and RFC 9250 specifies DNS over QUIC.

4. DNS over TLS (DoT): a dedicated encrypted DNS channel

DoT places DNS messages inside a TLS connection. The standard port is TCP 853, which gives network administrators a recognisable destination for encrypted DNS traffic. Once the TLS session is established and the server is authenticated according to the client's configuration, DNS messages are sent over that protected channel.

The dedicated port makes DoT relatively straightforward to identify and manage at a network boundary. A firewall can allow or block outbound TCP 853 according to policy. That can be useful in managed environments where devices should use a designated resolver, although a port rule alone is not a complete policy mechanism.

DoT can reuse a persistent TLS connection for multiple DNS requests. Reusing a connection avoids performing a fresh TLS handshake for every query. Actual performance depends on resolver distance, connection management, caching, server load and network quality.

DoT's dedicated transport is also a limitation in some networks. A captive portal, restrictive firewall or public hotspot may block port 853. In that situation, a client may need to use a permitted resolver path or temporarily fall back according to its policy. Users should understand whether their device fails closed, falls back to plaintext DNS or switches to another configured resolver.

5. DNS over HTTPS (DoH): DNS inside ordinary HTTPS

DoH maps DNS query-response exchanges into HTTPS requests. The protocol specification defines media types and HTTP behaviour for carrying DNS wire-format messages. Because HTTPS commonly uses port 443, DoH can travel through networks that already permit ordinary web traffic.

DoH can use HTTP features such as connection reuse, caching, proxying and HTTP content negotiation. Browser implementations may integrate it directly, allowing the browser to use a chosen resolver independently of the operating system's normal DNS configuration.

That browser integration creates an important distinction: enabling secure DNS in a browser may protect only lookups made by that browser. Other applications, system services, games, messaging clients and background processes may continue using the operating system's configured resolver. A device-wide secure DNS setting and a browser-only setting are not the same thing.

Because DoH shares the HTTPS ecosystem, it can be harder for a network observer to distinguish DNS exchanges from other HTTPS traffic based only on port number. That can improve resistance to some forms of interference, but it can also make enterprise monitoring and local DNS-based controls more complicated. Network administrators should use documented endpoint and gateway policies rather than assuming all DNS uses port 53.

DoH is not simply “DNS hidden in a web page.” It is a defined protocol with specified request and response formats. Implementations should use the expected endpoint configuration and validate the TLS identity of the resolver. A random HTTPS website is not automatically a trusted DNS service.

6. DNS over QUIC (DoQ): DNS using QUIC transport

DoQ carries DNS messages over QUIC, a secure transport protocol built on UDP. QUIC integrates TLS 1.3 security into its handshake and provides independent streams, connection migration features and transport behaviour designed for modern internet paths.

DoQ uses a dedicated application protocol rather than wrapping DNS messages in HTTP semantics. Its specification defines how DNS queries and responses are mapped to QUIC streams. This can provide useful transport properties, including reduced connection setup costs in suitable circumstances and avoiding TCP-level head-of-line blocking between independent QUIC streams.

DoQ is not a universal speed upgrade. The client and resolver both need support, UDP traffic must be permitted, and actual latency depends on network conditions and implementation quality. Some networks restrict UDP or handle it differently from TCP. A client may therefore need another supported encrypted DNS protocol.

DoQ also does not remove the need for resolver authentication, sound privacy policy or correct endpoint configuration. Encryption protects the channel to the endpoint; it does not determine what the operator does with the query after receiving it.

For a home user, the best choice is usually the secure protocol supported reliably by the device and a resolver the user has deliberately selected. For an enterprise, the choice must also consider internal name resolution, policy enforcement, logging requirements, endpoint management and supportability.

8. What encrypted DNS protects—and what it does not

When correctly configured with authenticated encryption, DoH, DoT and DoQ protect DNS messages from ordinary passive observers on the path between the client and resolver. They also make it harder for an on-path attacker to alter those messages without detection.

However, the resolver receives the query in order to answer it. The resolver operator may be able to associate queries with a source IP address, account, device or connection metadata depending on its service design. Its retention, sharing and security practices therefore matter. Choosing an encrypted protocol does not remove the need to evaluate the resolver provider.

Encrypted DNS does not necessarily hide the IP address of the website or service the device later contacts. The access network can often observe destination IP addresses, timing and data volume. Other metadata, including some TLS handshake information, may also be visible depending on protocol features and deployment.

Encrypted DNS does not make a user anonymous. Websites can still identify users through logins, cookies, browser characteristics and other signals. A VPN, proxy or privacy-focused browser addresses different parts of the network and application stack, and each has its own trust model.

Encrypted DNS also does not guarantee that an answer is authentic in the DNSSEC sense. TLS authenticates the connection to a resolver, not necessarily the origin and integrity of every DNS record in the global DNS hierarchy. DNSSEC validation provides a separate mechanism for validating signed DNS data.

9. Encrypted DNS is not DNSSEC

DNSSEC and encrypted DNS are often confused because both are described as DNS security. They solve different problems:

  • Encrypted DNS: protects the communication channel between a client and a resolver against on-path observation and tampering.
  • DNSSEC: allows validating resolvers and clients to verify cryptographic signatures and authenticated denial-of-existence data for signed DNS zones.

A DoH connection can be encrypted while the resolver returns data that is not DNSSEC-validated. Conversely, a DNSSEC-validating resolver can retrieve signed data using an unencrypted transport, although the query itself remains visible on the path. Using both protections can provide transport privacy and DNS data-origin validation.

DNSSEC does not encrypt domain names or hide DNS queries. Its signatures are designed to be publicly verifiable. It helps detect forged or altered DNS data within the chain of trust, but it does not conceal the query from an observer.

For further background, TEZZ CONNECT's existing DNSSEC guide explains signed DNS data and the chain of trust. Keep the distinction clear when choosing privacy and security controls.

10. Encrypted DNS and VPNs: do they replace each other?

A VPN creates an encrypted tunnel between a device and a VPN endpoint. If DNS queries are routed through that tunnel to a trusted resolver, the local access network generally cannot read those queries inside the tunnel. The VPN provider or its chosen resolver may still see them.

Encrypted DNS creates a protected channel between the client and a DNS resolver. It can be used without a VPN, or it may operate through a VPN tunnel depending on the routing and application configuration. The two technologies protect different connections and can complement one another.

Problems arise when DNS and application traffic take inconsistent paths. For example, a VPN may route ordinary traffic through the tunnel while a browser's DoH setting sends DNS directly to an external resolver. This can reveal DNS queries to the local network or create policy conflicts. Conversely, a secure DNS client may be configured to use an internal resolver that is reachable only through the VPN.

Users should check for DNS leaks using trusted diagnostic methods and confirm which resolver actually receives queries. A VPN logo or a browser secure-DNS toggle is not proof that every application uses the intended route.

11. Who should you trust as a DNS resolver?

Resolver selection is a privacy decision as well as a technical one. The operator can see the queries it receives and may apply filtering, logging, caching, threat protection or other services. Different resolvers can return different answers because of filtering policy, geographic routing, DNS64, split-horizon configurations or service-specific behaviour.

Before choosing a provider, review its privacy notice and operational documentation. Look for clear statements about query logging, retention periods, data sharing, security practices, jurisdiction, account requirements and how the service handles abuse reports. Marketing claims such as “private” or “fast” are not substitutes for a transparent policy.

Consider whether the resolver supports the protocol your device can use, whether it offers reliable IPv4 and IPv6 reachability, and whether it supports DNSSEC validation. If you need malware or adult-content filtering, understand how those categories are maintained and how false positives can be reported or corrected.

For a workplace, school or family network, a central resolver may be important for internal hostnames, security monitoring and policy. Replacing it with an unrelated public resolver can break access to printers, file shares, internal applications or managed security controls. Check with the administrator before changing DNS on a managed device.

12. How encrypted DNS is configured on common devices

Exact menu names and availability vary by operating-system version, device manufacturer, region and administrator policy. The safe principle is to use the operating system's built-in secure DNS feature or a reputable client, then select a provider using its documented configuration details.

Android

Many recent Android versions provide a Private DNS setting under Network and Internet or Connections. Depending on the version, users can select automatic mode or enter a provider hostname for strict mode. This feature generally uses DNS over TLS, not a browser-specific DoH setting. If the hostname is wrong or the provider is unreachable, name resolution may fail in strict mode.

Windows

Supported Windows versions expose encrypted DNS options for compatible DNS servers in network settings. The available protocol options depend on the Windows release and the resolver. On managed work devices, Group Policy, mobile-device management or security software may control the setting.

Apple devices

Apple platforms can use encrypted DNS through supported configuration profiles, managed settings or compatible applications. Availability and exact controls differ across iOS, iPadOS and macOS releases. Users should use a profile from a provider or organisation they trust and understand what other network settings the profile changes.

Web browsers

Some browsers offer a Secure DNS or DNS over HTTPS setting. A browser may use a selected provider, a provider chosen from a built-in list or an automatic upgrade mechanism. This setting can affect only browser lookups, leaving other device applications on the system resolver. Managed browsers may have the feature disabled or centrally configured.

After configuration, test more than one application. Check ordinary websites, local devices and any work or school services that rely on internal DNS. Keep a note of the original setting so you can restore it if the new resolver causes compatibility problems.

13. Automatic discovery: DDR and network-designated resolvers

Manual configuration is not the only model. Modern standards describe ways for clients to discover encrypted resolver services associated with a network's existing DNS configuration.

RFC 9462 defines Discovery of Designated Resolvers (DDR). It allows a client that knows an unencrypted resolver's IP address to discover encrypted DNS configuration associated with that resolver, using DNS service-binding information. The design is intended for resolvers operated by the same entity or cooperating entities, with verification steps for discovered identities.

RFC 9463 defines DHCP and IPv6 Router Advertisement options for Discovery of Network-designated Resolvers (DNR). It enables a network to provide information such as an authentication domain name, IP addresses and service parameters for encrypted resolvers.

These standards matter because encrypted DNS is not only a public-resolver feature. A company, university, hotel or broadband provider may want clients to use its own encrypted resolver while preserving local names and network policy. Discovery mechanisms can help combine automatic configuration with authenticated encrypted transport.

Support varies across operating systems, network equipment and resolver deployments. Do not assume that a device automatically discovers an encrypted resolver just because the network advertises a DNS server. The client and network must implement compatible mechanisms.

14. Can encrypted DNS break local networks?

Yes, if the chosen resolver does not know about the local network's private domains or if the device bypasses a resolver that provides internal records. A company may use names such as files.internal.example or short hostnames that are resolvable only through its own DNS servers. A public resolver will not normally have those private records.

Split DNS is another consideration. A device may need one resolver for internal corporate names and another for public internet names. VPN clients often install DNS settings and search domains when the tunnel connects. A browser-only DoH configuration that ignores those settings can cause internal services to fail or leak queries to an external provider.

Captive portals can also be affected. A hotel or public Wi-Fi network may require a browser sign-in before full internet access is available. If strict encrypted DNS tries to reach a resolver that is blocked until sign-in, the device may struggle to load the portal. Some operating systems detect captive portals and temporarily adjust connectivity checks, but behaviour varies.

Filtering systems can be affected too. A home router's parental controls may rely on seeing DNS queries. If a phone sends queries directly to an external DoH resolver, those router-level controls may not work as expected. A network that requires managed DNS should configure endpoints and gateways accordingly rather than relying only on traditional port-53 visibility.

15. Troubleshooting encrypted DNS problems

Websites show a DNS error after enabling secure DNS

Check the resolver hostname, internet connectivity, system date and time, and whether the network permits the required protocol. In strict mode, an unreachable resolver may prevent lookups instead of falling back to plaintext. Temporarily restore the previous setting to confirm whether the new configuration is the cause.

Some apps work but others cannot connect

Determine whether secure DNS is configured only in a browser or system-wide. Check whether the affected app uses the operating system resolver, a built-in resolver or hard-coded endpoints. Also check for VPN profiles, private DNS settings and device-management policies that may conflict.

Internal company or school websites stop resolving

Check whether the device needs an organisation-managed resolver or VPN-provided search domain. Do not replace managed DNS with a public provider without approval. Split-DNS requirements should be solved through the network's supported configuration.

Secure DNS works at home but not on public Wi-Fi

The network may block the selected protocol, require captive-portal authentication or intercept connectivity checks. Complete the authorised sign-in process and review the network's terms. Do not bypass access controls on networks you do not administer.

DNS is encrypted but a website still appears unsafe

Encrypted DNS does not certify that a website is legitimate or safe. It protects the resolver connection. Continue to check the domain carefully, use HTTPS, keep software updated and rely on endpoint security and browser protections where appropriate.

16. Does encrypted DNS affect speed?

Encrypted DNS is primarily a privacy and integrity improvement for the resolver connection, not a broadband acceleration technology. The effect on lookup time depends on several variables: resolver location, network path, caching, connection reuse, handshake costs, server load and whether the device can reuse a secure session.

A nearby, well-operated resolver may answer quickly. A distant resolver or congested path may add delay. A browser that opens a new secure connection frequently may have different performance from a system resolver that maintains a connection. DNS caching can reduce the number of queries that need to reach the resolver at all.

Do not judge encrypted DNS by a single speed-test result. A broadband speed test measures throughput to a test server; DNS lookup latency is a different measurement. If a page loads slowly, the cause may be server response time, content delivery, TLS setup, device performance or network congestion rather than DNS.

To compare resolvers fairly, repeat tests over the same network, use the same device and test domains, account for caching, and measure multiple trials. Avoid changing several network settings at once, because that makes the result difficult to interpret.

17. Practical checklist before switching

  • Identify whether you need browser-only or device-wide encrypted DNS.
  • Choose a resolver whose operator and privacy policy you trust.
  • Confirm which encrypted protocols and endpoints the provider supports.
  • Check whether your router, VPN, workplace or school requires a particular resolver.
  • Understand whether the device will fail closed or fall back when the resolver is unreachable.
  • Test local devices, internal websites, captive portals and important apps after the change.
  • Keep a record of the previous DNS configuration so you can revert safely.
  • Do not assume encrypted DNS replaces DNSSEC, a VPN, endpoint security or HTTPS.
  • Review the resolver's filtering behaviour if you rely on parental controls or malware blocking.
  • Recheck settings after operating-system, browser or VPN updates.

18. Key takeaways

  • Traditional DNS queries can be visible to observers on the path between a client and resolver.
  • DoT uses TLS, DoH uses HTTPS and DoQ uses QUIC to protect DNS transport.
  • Encrypted DNS protects the client-to-resolver channel, not every part of browsing activity.
  • The resolver still receives queries, so provider trust and data-retention policy matter.
  • DNSSEC validates DNS data; encrypted DNS protects transport. They are complementary.
  • VPNs and encrypted DNS protect different network paths and can interact in complex ways.
  • Browser secure-DNS settings may not apply to every application on a device.
  • Internal names, captive portals and network filtering should be tested after configuration.

The practical goal is not to turn DNS into an invisible service. It is to make a deliberate choice about who receives your queries and to protect those queries while they travel. Understanding the protocol and its limits is more useful than switching on a privacy setting without checking how the rest of the network behaves.

Frequently asked questions

1. What is encrypted DNS?

Encrypted DNS protects the connection between a DNS client and resolver using a secure transport such as TLS or HTTPS. Common protocols include DNS over TLS (DoT), DNS over HTTPS (DoH) and DNS over QUIC (DoQ).

2. What is the difference between DoH and DoT?

DoH carries DNS messages inside HTTPS exchanges, usually over port 443. DoT carries DNS over TLS on a dedicated transport, conventionally port 853. Both encrypt the client-to-resolver connection but integrate differently with networks and applications.

3. Is DNS over QUIC better than DoH or DoT?

DoQ carries DNS messages over QUIC, combining encryption with QUIC transport features. It is not universally better; compatibility, resolver support, network policy and client implementation determine which protocol is practical.

4. Does encrypted DNS hide my browsing history?

Encrypted DNS hides DNS queries from ordinary observers on the path between the client and its chosen resolver, but the resolver can still see queries. Destination IP addresses, traffic timing and other metadata may remain visible to network operators and websites.

5. Is encrypted DNS the same as DNSSEC?

No. Encrypted DNS protects the transport between a client and resolver. DNSSEC adds cryptographic validation of DNS data origin and integrity. They address different risks and can be used together.

6. Does a VPN make encrypted DNS unnecessary?

A VPN can protect DNS traffic when the device sends queries through the VPN tunnel to a trusted resolver, but configuration matters. Encrypted DNS can protect the client-to-resolver connection outside or inside a VPN, depending on the chosen resolver and routing.

7. Can my internet provider still see websites I visit when I use DoH?

DoH hides DNS query contents from the access network when the connection is correctly encrypted, but an ISP may still observe destination IP addresses, traffic volume and timing. Other encrypted connection metadata may also reveal information.

8. Will encrypted DNS make my internet faster?

Not necessarily. It may change lookup latency depending on resolver distance, caching, connection reuse and network conditions. Its primary purpose is to protect DNS transport, not increase broadband speed.

9. Can encrypted DNS bypass parental controls or workplace filters?

It can prevent network controls that rely only on observing ordinary unencrypted DNS queries. Managed devices and networks may enforce policy through endpoint configuration, approved resolvers, gateways or other controls. Follow applicable rules and administrator instructions.

10. How do I check whether my device uses encrypted DNS?

Check the operating system, browser or DNS client settings for a named secure DNS provider or encrypted DNS mode. Then verify the configured resolver and test from an authorised diagnostic environment; a browser setting may apply only to browser traffic, not every app.
