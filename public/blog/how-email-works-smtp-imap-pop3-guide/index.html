How Email Works: SMTP, IMAP and POP3 Explained

Sending an email looks simple: type a message, tap Send and wait for a reply. Behind that action, several systems work together to find the recipient's mail server, transfer the message, apply security and filtering checks, store it and synchronise it to the recipient's devices. This guide follows the full journey and explains the different jobs performed by SMTP, IMAP and POP3.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Email is a network of cooperating mail systems

Email is one of the internet's most widely used services, but it is not a single application or one central computer. A message may begin in a phone app, travel to a provider's submission server, pass through one or more mail transfer agents, reach the recipient's provider, undergo filtering, and finally appear in a browser or desktop client. Each system has a defined role and communicates using standard protocols.

The three names users most often encounter are SMTP, IMAP and POP3. They are not competing versions of the same protocol. SMTP moves outgoing mail from a client to a submission server and between mail servers. IMAP lets a client access and synchronise a mailbox stored on a server. POP3 retrieves messages from a mailbox using a simpler download-oriented model.

Understanding the difference helps solve common problems. If you can receive mail but cannot send it, the outgoing SMTP configuration may be wrong. If messages appear on a laptop but not a phone, the account's IMAP or POP3 settings may be responsible. If a message is sent but never arrives, the issue may involve DNS, remote server policy, filtering, reputation or a delivery failure after submission.

The main components behind an email message

Mail user agent (MUA): The application used to compose, send, read and organise email. It may be a browser-based mailbox, a desktop program or a mobile app. The MUA communicates with mail servers using submission and mailbox-access protocols.

Mail submission agent (MSA): The service that accepts outgoing messages from authenticated users or applications. It commonly uses SMTP submission and applies rules such as sender authorisation, message-size limits and abuse controls.

Mail transfer agent (MTA): The software that transfers email between mail systems. It uses SMTP to route messages toward the recipient's domain and may queue messages when a destination is temporarily unavailable.

Mail delivery agent (MDA) or local delivery system: The component that places a message into the recipient's mailbox or storage system after the receiving mail server has accepted it.

Mail access server: The service that allows a user to view and manage stored messages, commonly through IMAP or POP3. Webmail may use internal APIs rather than exposing these protocols directly to the browser, but the underlying mailbox still has to be stored and managed.

DNS: The Domain Name System helps the sending mail server discover which mail servers accept email for the recipient's domain. MX records provide this routing information.

Step by step: what happens when you press Send?

Imagine that a person using alex@example.net sends a message to sam@sample.org. The email application first prepares the message, including the sender and recipient addresses, subject, body, attachments and message headers. It then connects to the configured submission service, usually using SMTP with authentication and TLS.

The submission server checks whether the client is allowed to send the message. It may apply size limits, rate limits, malware scanning, policy checks and sender controls. If accepted, the server queues the message for delivery. A successful submission response means the service has accepted responsibility for processing the message; it does not mean the recipient has read it or that it has already reached the inbox.

The sending mail system examines the recipient domain, in this example sample.org, and queries DNS for its MX records. The records identify the mail exchangers that accept mail for that domain. The sending MTA selects an appropriate destination according to MX preference and attempts an SMTP connection.

The receiving server can accept or reject the message based on its policies. It may inspect sender authentication, reputation, content, attachments, links and other signals. If it accepts the message, it routes it into the recipient's mailbox system. The recipient later opens a webmail interface or email client, which retrieves the message through the provider's mailbox access system.

This process can involve more than one intermediate server. A message can be relayed through security gateways, filtering services or hosted mail platforms before final delivery. The Received headers added along the route provide a trace of the systems that handled the message, although interpreting them requires care because not every header is equally trustworthy.

SMTP: the protocol that sends and transfers email

Simple Mail Transfer Protocol (SMTP) is the foundation for sending and relaying internet email. It defines a command-and-response conversation between a client and server. The client identifies itself, specifies the envelope sender and recipient, transfers the message data and then ends the transaction. The main current base specification is IETF RFC 5321.

SMTP is used in two closely related settings. A user's email application submits outgoing mail to its provider's submission service. Mail transfer agents then use SMTP to relay the message between domains. The submission service commonly requires user authentication, while server-to-server relay follows different trust and policy rules.

An SMTP conversation includes commands such as EHLO, MAIL FROM, RCPT TO and DATA. The envelope sender and recipient used during transport are distinct from the message's visible From and To headers. This distinction matters for delivery, bounce handling and email authentication.

SMTP is a store-and-forward system. A sending server can accept a message, place it in a queue and retry later if a remote server is temporarily unavailable. The sending system may eventually generate a non-delivery report if delivery cannot be completed. Temporary and permanent errors are treated differently, and exact retry schedules depend on the mail system's policy.

SMTP does not provide the recipient's mailbox interface. It is not the protocol normally used by a phone to browse folders, mark a message as read or search the inbox. Those tasks are handled by IMAP, POP3 or a provider-specific web interface.

IMAP: keeping messages synchronised across devices

Internet Message Access Protocol (IMAP) lets a client access and manipulate messages that remain stored on a mail server. It supports server-side mailboxes or folders, message flags, searching and selective fetching. It also allows an offline client to resynchronise with the server later. The current IMAP4rev2 specification is IETF RFC 9051.

IMAP is particularly useful when a person checks the same account from a phone, laptop and webmail. When the user reads a message on one device, the read status can be reflected on the others. When a folder is created or a message is moved, the mailbox state can be synchronised instead of maintaining separate independent copies on each device.

IMAP clients can fetch only the information they need. They may download message headers first, retrieve a body when opened, or fetch selected attachment parts. This can reduce unnecessary transfers when a mailbox contains large attachments or many messages. The server remains the primary mailbox store, although clients may keep local caches for offline access and performance.

IMAP does not send outgoing mail. A mail application generally uses SMTP submission to send a message and IMAP to access the received mailbox. A provider may offer a proprietary API or webmail interface instead, but the roles remain conceptually separate.

IMAP synchronisation also requires care with multiple devices and offline edits. Clients may queue local changes and apply them when connectivity returns. If the same message is moved or deleted from different devices while offline, the client and server need to reconcile the resulting state. Modern clients usually handle this automatically, but synchronisation is not identical to keeping every local file permanently independent.

POP3: a simpler download-oriented mailbox protocol

Post Office Protocol version 3 (POP3) is another protocol for retrieving email from a server. It was designed around a simpler model in which a client connects to a mailbox, lists messages, downloads them and may delete them from the server. The standard is documented in IETF RFC 1939.

Historically, POP3 was useful when people used one primary computer and wanted messages downloaded for local storage. Some clients offer an option to leave a copy of downloaded messages on the server, but behaviour varies and can become confusing when several devices access the same account.

POP3 provides fewer mailbox-management and synchronisation capabilities than IMAP. It does not offer the same general model of server folders, shared flags and multi-device state. A message downloaded and marked as read in one POP3 client may not appear as read on another device, depending on the provider and client implementation.

POP3 can still be useful for specialised workflows, legacy systems or users who deliberately want a download-oriented setup. For most people who use more than one device, IMAP is usually easier to manage. The right choice depends on the mail provider, the client's capabilities, storage requirements and whether central synchronisation is important.

The most important point is that SMTP is for sending, while IMAP and POP3 are for receiving or accessing stored mail. Choosing IMAP instead of POP3 does not change how your outgoing messages are transferred. A typical account configuration therefore has one outgoing submission server and one incoming mailbox-access server.

DNS MX records: finding the recipient's mail server

Email addresses contain a domain after the at sign. When a sending mail server needs to deliver a message to person@company.example, it looks up the mail exchanger records for company.example. An MX record names a mail server and includes a preference value. Lower preference values are preferred before higher values, although actual delivery attempts also depend on server availability and routing policy.

A simplified DNS zone might contain:

company.example.  MX  10  mail1.company.example.
company.example.  MX  20  mail2.company.example.

This example says that mail1 has a higher preference than mail2. The second server may be used when the first is unavailable or when delivery policy requires it. The names in MX records must resolve to address records, and administrators should avoid configuration patterns that create mail-routing loops.

MX records are not the same as the A or AAAA record for a website. A domain's website may be hosted on one platform while its email is handled by a completely different provider. Changing website hosting does not necessarily require changing mail routing, and changing MX records can interrupt email even when the website remains online.

DNS caching also affects changes. Recursive resolvers may keep MX answers until their TTL expires. During a provider migration, administrators should plan record changes, mailbox migration, routing overlap and rollback carefully. A DNS update does not automatically move old messages from one provider to another.

Common email ports and secure connections

Port numbers help distinguish the services a mail client or server is trying to reach. Commonly encountered ports include SMTP relay on TCP 25, message submission on TCP 587, implicit-TLS submission on TCP 465, IMAP with implicit TLS on TCP 993 and POP3 with implicit TLS on TCP 995.

SMTP submission with STARTTLS587Authenticated outgoing mail from clients and applications
SMTP submission with implicit TLS465Encrypted submission connection from the start
IMAP with implicit TLS993Encrypted mailbox access and synchronisation
POP3 with implicit TLS995Encrypted mailbox retrieval

These are common standard service assignments, not a guarantee that every provider uses the same hostname or configuration. Always follow the mail provider's current setup instructions. Some organisations restrict outbound port 25 from residential or cloud networks to reduce spam abuse, while allowing authenticated submission through 587 or 465.

Transport Layer Security (TLS) protects the connection between a mail client and server or between mail systems when negotiated. IETF RFC 8314 recommends TLS for mail submission and access, and describes implicit TLS as a preferred approach for these client-to-provider connections. STARTTLS can also upgrade a connection when correctly configured and required.

TLS on a connection is not the same as end-to-end message encryption. A message may be decrypted at a mail server, scanned, stored and then encrypted again for the next network hop. If the content must remain readable only by intended recipients, separate end-to-end encryption mechanisms are needed.

How attachments and rich email content are carried

Email began as text-oriented communication, but modern messages can contain images, documents, audio, calendar invitations and formatted HTML. The Multipurpose Internet Mail Extensions (MIME) framework allows a message to carry different content types and multiple parts. A message can include a plain-text alternative, an HTML body and attachments in a multipart structure.

Attachments are commonly encoded so that binary data can be transported through mail systems designed around text-compatible message formats. Base64 encoding increases the size of binary data, so a large file can become noticeably larger when attached to email. Providers also impose message-size limits, and the total size can include message headers, body text, attachments and encoding overhead.

For large files, a secure file-sharing link may be more reliable than attaching the file directly. However, links create their own security and access-control questions. Verify the destination, set appropriate permissions and avoid exposing sensitive documents through publicly accessible links.

HTML email can display layout, images and styled text, but mail clients restrict scripts and other active content for security. A well-formed message should remain understandable in plain text and should not rely on remote images or complex formatting to communicate essential information.

Why email delivery can be delayed

Email is asynchronous. The sending server does not need the recipient's device to be online at the moment the message is sent. It transfers the message toward the recipient's mail system, which stores it until the user checks the mailbox. This design is resilient, but it means delivery is not always instantaneous.

A receiving server may temporarily defer a message because it is busy, undergoing maintenance, applying rate limits or experiencing a network problem. The sending server can queue and retry later. A temporary SMTP response generally means “try again,” while a permanent failure indicates that the message cannot be accepted in its current form. The sender may eventually receive a bounce or non-delivery report.

Large attachments, slow content scanning, DNS problems, greylisting, reputation checks and overloaded mail queues can also affect delivery time. If a message is delayed, check the sender's outbox, any non-delivery report, the recipient's spam folder and the provider's service status. For business-critical email, maintain an alternative communication route rather than assuming that every message will arrive immediately.

Why messages go to spam or are rejected

Successful SMTP transfer does not guarantee inbox placement. The receiving provider evaluates whether the message is wanted and whether the sender appears trustworthy. It may consider domain and IP reputation, SPF and DKIM results, DMARC alignment, complaint rates, recipient engagement, message volume, content patterns, URLs, attachments and historical behaviour.

Authentication is one important part of this evaluation. SPF identifies authorised sending infrastructure, DKIM provides a cryptographic signature, and DMARC checks alignment with the visible From domain and publishes a policy. These mechanisms help receivers assess domain identity, but they do not prove that a message is harmless or that a recipient consented to receive it.

For an overview of those standards, see the SPF, DKIM and DMARC email authentication guide. A sender should also maintain accurate recipient lists, honour unsubscribe requests, avoid deceptive subjects, secure sending accounts and monitor bounces and complaints.

Common email setup problems

Can receive but cannot send: Check the outgoing SMTP hostname, port, encryption mode, authentication method and account credentials. Some providers require an app password or modern authentication rather than the normal account password.

Can send but cannot receive: Check MX records, mailbox status, storage quota, spam filtering and the provider's inbound routing. If the domain was recently moved, verify that the old and new MX records are not conflicting with the migration plan.

Messages missing from one device: Confirm whether the account uses IMAP or POP3. Check folder subscriptions, filters, synchronisation settings and whether the message was moved or deleted on another device.

Repeated password prompts: The provider may have disabled basic authentication, revoked an app password or require a modern sign-in flow. Confirm the account's security settings and use the provider's supported authentication method.

Certificate or TLS error: Verify the server hostname, system date, certificate validity and configured port/encryption combination. Do not bypass certificate warnings to make mail work; doing so can expose credentials and messages to interception.

Outgoing messages stuck in the outbox: Check network access, provider status, attachment size, SMTP response codes and account limits. A message can remain queued locally if the client cannot connect to the submission server.

Practical security habits for email users

Use TLS-enabled settings for incoming and outgoing connections, and verify the server certificate rather than accepting arbitrary certificate warnings. Protect the mailbox account with a unique password and multi-factor authentication where available. Keep devices and mail applications updated, and be cautious about unexpected attachments, links and requests to change payment details.

Do not assume that a familiar display name proves the sender's identity. Check the full address and context, especially for urgent financial or account requests. A compromised legitimate account can send malicious mail that passes domain authentication, so technical checks do not replace careful verification.

For organisations, limit who can send from shared addresses, protect administrator accounts, review forwarding rules and monitor unusual login or sending activity. Configure SPF, DKIM and DMARC for domains used to send mail. Maintain a clear process for compromised accounts and suspicious messages.

Frequently asked questions

1. What is the difference between SMTP, IMAP and POP3?

SMTP is used to submit and transfer outgoing email. IMAP lets an email client access and synchronise messages and folders stored on a mail server. POP3 is a simpler protocol for retrieving messages from a mailbox, often downloading them to a client.

2. Does SMTP receive email?

SMTP is used for sending and transferring messages between mail systems, including submission by a user's email client. Mail clients normally use IMAP or POP3 to access received messages.

3. What does an MX record do?

A DNS MX record identifies the mail servers responsible for accepting email for a domain and provides preference values used to select among them.

4. What are the standard email ports?

Common ports include SMTP relay on 25, message submission with STARTTLS commonly on 587, implicit-TLS submission on 465, IMAP with implicit TLS on 993, and POP3 with implicit TLS on 995. Provider settings and current standards should always be checked.

5. Is IMAP better than POP3?

IMAP is generally more convenient when using multiple devices because messages, folders and flags are synchronised with the server. POP3 can suit simpler download-oriented workflows, but its behaviour depends on client settings and provider support.

6. Can I use SMTP without a mail app?

Yes. Websites, applications, printers and monitoring systems can submit email through an authorised SMTP submission service or an appropriate provider API, using authentication and encryption required by the provider.

7. Does TLS encrypt the entire email from sender to recipient?

No. TLS commonly protects each network connection between a mail client and server or between mail servers, but the message may be stored or relayed in plaintext at intermediate systems. End-to-end encryption is a separate capability.

8. Why does an email sometimes go to spam?

Spam filtering can consider sender reputation, authentication, message content, links, attachments, recipient engagement, complaint rates and sending behaviour. Correct SMTP delivery alone does not guarantee inbox placement.

9. What happens when a recipient's mail server is unavailable?

A sending mail server may queue the message and retry delivery according to its retry policy. If delivery remains unsuccessful beyond the relevant period, it may generate a non-delivery report or bounce message.

10. What is the difference between email delivery and email synchronisation?

Delivery moves a message through mail transfer systems to the recipient's mailbox. Synchronisation lets devices access and keep their local view of mailbox messages, folders and status aligned with the server, commonly using IMAP.
