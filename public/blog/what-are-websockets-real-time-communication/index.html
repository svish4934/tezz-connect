What Are WebSockets? How Real-Time Internet Communication Works

From live chat messages to multiplayer games and monitoring dashboards, many websites need information to move in both directions without repeatedly refreshing a page. WebSockets make that possible with a persistent, two-way connection. This guide explains the protocol, how it compares with HTTP polling and Server-Sent Events, and what developers need to consider for security, reliability and scale.

By Suraj Vishwakarma · Published by TEZZ CONNECT

The internet is no longer only a page you request

Traditional web browsing often looks like a simple exchange. A browser requests a page, the server returns it, and the browser displays the result. When the user needs new information, the browser makes another request. This model works extremely well for documents, product pages, images, search results and many application operations. But it is less convenient when information changes continuously and the user expects the screen to update immediately.

Think about a support chat. A visitor sends a message and expects the support agent's reply to appear without pressing refresh. A multiplayer game needs players' actions to reach the game server and updates to travel back to everyone in the session. A live operations dashboard may receive thousands of small status changes while an operator watches the screen. Repeatedly opening a new HTTP request for every tiny update can add overhead and complexity.

WebSocket is a standard protocol designed for this kind of two-way communication. It starts with an HTTP-based opening handshake, then changes the connection into a persistent channel where both client and server can send messages. The connection remains available until one side closes it or the underlying network path fails. This makes WebSockets useful when an application needs frequent, low-latency messages in both directions.

What is a WebSocket?

A WebSocket is a communication protocol that enables full-duplex messaging between a client and a server over a single long-lived connection. Full-duplex means both endpoints can send data independently; the client does not have to wait for a new request opportunity before the server can send an update. The protocol is defined by IETF RFC 6455.

In a browser, JavaScript can create a WebSocket object, register event handlers and send or receive text and binary messages. The server must also implement the protocol and accept the opening handshake. Once the handshake succeeds, application messages are carried in WebSocket frames rather than ordinary HTTP request and response bodies. The browser and server can exchange many messages without repeating the HTTP setup for every message.

WebSocket is not a database, messaging queue or complete real-time application architecture. It is a transport-level application protocol for exchanging messages. Developers still need to decide what a message means, how users authenticate, which rooms or channels exist, how events are stored, what happens when a client reconnects and how messages are delivered to multiple server instances.

How a WebSocket connection is established

The connection begins with a client opening a network connection to the server. For the classic WebSocket protocol, the client sends an HTTP Upgrade request. The request includes headers such as Upgrade: websocket, Connection: Upgrade, a WebSocket key, the protocol version and—when the client is a browser—the page's Origin. The browser can also propose one or more subprotocols that describe the application message format.

If the server accepts the request, it responds with HTTP status 101 Switching Protocols and the required WebSocket response headers. The response confirms that the server has accepted the upgrade. After this point, the connection is no longer used as an ordinary HTTP request-response exchange; both sides send and receive WebSocket frames over the established connection.

The handshake is important for compatibility and security. It allows HTTP servers and intermediaries to recognise a protocol upgrade, and it gives the server a chance to validate the requested host, path, origin, authentication and supported subprotocol. A failed handshake remains an HTTP response, which is why developers can often inspect a status code and response headers when a WebSocket connection does not open.

The RFC 6455 opening-handshake section describes the required request and response fields. The exact header sequence is not a general-purpose way to authenticate a user; application authentication must be designed separately.

What happens after the handshake: frames and messages

After the upgrade, data is carried in frames. Frames have an opcode that identifies their purpose. Text frames carry UTF-8 text, binary frames carry application-defined binary data, and control frames help manage the connection. A message can be sent in one frame or fragmented across multiple frames. This framing lets the protocol distinguish application content from control information.

Most applications begin with text messages containing JSON because they are easy to inspect and work with across programming languages. A chat event might include a message type, conversation identifier, sender identifier, timestamp and text. A game may prefer compact binary messages to reduce bandwidth and parsing costs. The protocol does not require JSON or prescribe a single application schema; the client and server must agree on the format.

Control frames include Close, Ping and Pong. A Ping can be used as a keepalive or to check whether the remote endpoint is responsive. The recipient responds with a Pong unless the connection is already closing. Close frames allow endpoints to begin a coordinated shutdown and may include a status code and reason. These control messages are useful for connection health, but application-level heartbeats may still be needed to detect stalled sessions or verify that a user session remains valid.

WebSocket URLs: ws and wss

WebSocket URIs use the ws and wss schemes. A ws URL identifies a WebSocket connection without TLS, while wss identifies a connection protected by TLS. In public browser applications, a page served over HTTPS should normally connect to a secure wss endpoint. Browsers restrict insecure active content on secure pages, and an unencrypted WebSocket could expose messages to network observers or allow them to be altered.

WSS provides transport encryption and server authentication through TLS, but it does not automatically authenticate the end user or authorise every message. A server must still check the session or token and verify that the connected user is allowed to subscribe to a room, read a record or perform an action. Secure transport protects the path; application security determines what the user is permitted to do.

Certificate configuration matters just as it does for HTTPS. The server's certificate must be valid for the hostname, trusted by the client and correctly deployed. For background, read our guide to TLS, HTTPS and digital certificates.

WebSockets compared with HTTP polling

With ordinary polling, the browser sends a request at regular intervals to ask whether new information is available. If a dashboard polls every five seconds, it may wait almost five seconds to discover a new event. Polling is simple and works with standard HTTP infrastructure, but it can create many requests that return no new data. Short intervals improve apparent freshness at the cost of more requests, while long intervals reduce traffic but increase update delay.

Long polling is a variation. The browser sends a request, and the server keeps it open until an event is available or a timeout occurs. The server returns the event, after which the client immediately opens another request. This can reduce empty responses and provide near-real-time updates, but each event still involves an HTTP response and a new request. Long polling remains useful where WebSockets are unavailable or where an existing HTTP architecture makes it the practical choice.

WebSockets keep one connection open and allow messages in either direction. This can reduce repeated request overhead when an application exchanges many small updates. However, each open connection consumes server and network resources, and the application must handle reconnects, heartbeats, backpressure and state recovery. A WebSocket is not automatically cheaper or faster for every workload; the pattern of communication determines which design fits best.

WebSockets compared with Server-Sent Events

Server-Sent Events (SSE) provide a simpler way for a server to stream events to a browser over HTTP. The browser creates an EventSource connection, and the server sends a sequence of text events as they become available. The browser can receive updates continuously, and the API includes reconnection behaviour and event identifiers that can help resume a stream.

SSE is one-way: data flows from the server to the browser on that event stream. If the browser needs to send a command or form submission, it normally uses a separate HTTP request. This is often exactly what an application needs. A news feed, status monitor or notification list may mostly push updates to users, while user actions can be sent through regular HTTP endpoints.

WebSockets are better suited when both directions need to exchange frequent messages over the same connection, such as collaborative editing, interactive games or a two-way chat session. SSE can be simpler for one-way updates and can work naturally with HTTP caching and infrastructure patterns. The right choice depends on message direction, frequency, client support, operational complexity and the application's recovery requirements.

Where WebSockets are used

Live chat is a familiar example. When a user sends a message, the browser transmits it to the server. The server checks authentication and conversation membership, stores the message if required, then publishes an event to connected participants. Their browsers receive the event and update the conversation view. A robust chat system also handles offline users, message history, duplicate sends, delivery indicators and reconnect recovery; WebSocket is only the live transport part.

Multiplayer games use real-time channels to send player input and state updates. The server may receive movement or action messages and distribute authoritative game-state changes to participants. Game systems often need careful control over message frequency, payload size, latency, fairness and cheating. A WebSocket connection does not guarantee that every update arrives on time, nor does it replace server-side validation of player actions.

Trading and monitoring dashboards can use WebSockets to stream price changes, system metrics, alerts or job status. Collaborative editors can broadcast document operations or cursor presence. Delivery tracking, customer-support tools, collaborative whiteboards and live sports interfaces are other possible uses. For each case, developers should decide whether every event must be delivered, whether older updates can be replaced by newer state, and how to recover after a connection gap.

Latency, bandwidth and connection overhead

One benefit of a persistent connection is that the application does not need to repeat the full HTTP request setup for every message. Once established, a small WebSocket frame can carry an event without sending a new set of HTTP headers and creating a separate request-response cycle. This can be useful for applications that exchange many small messages at a high frequency.

But the initial connection still takes time. DNS lookup, TCP connection establishment, TLS negotiation for WSS and the WebSocket handshake all contribute to setup delay. The first message cannot be exchanged until the connection is ready. If a user opens a page, performs one action and leaves, a WebSocket may add more overhead than a normal HTTP request.

Latency also depends on the network path, server location, congestion, Wi-Fi quality, device scheduling and application processing. A WebSocket cannot overcome a slow mobile radio link or a congested access network. A persistent connection can reduce application-layer overhead, but the time for data to travel between endpoints remains affected by propagation, routing and queueing. Learn more about these factors in our guide to latency, ping and jitter.

Connection lifecycle: open, active, interrupted and closed

A browser WebSocket has a lifecycle. It begins in a connecting state, becomes open when the handshake succeeds, remains open while messages are exchanged, and eventually closes. The JavaScript API exposes events such as open, message, error and close. A client should register handlers for these events and update the user interface when the connection state changes.

Networks are not permanent. A phone can move between Wi-Fi and mobile data, a laptop can sleep, a router can restart, a proxy can close an idle connection, or a server can deploy a new version. The WebSocket connection may then close without the application receiving the event it expected. A robust client treats disconnects as normal operating conditions rather than exceptional events that never happen.

Reconnection should use controlled retry. Immediate repeated attempts from thousands of clients can create a reconnect storm after a regional outage. Exponential backoff with random jitter spreads retries over time. The application should also decide whether to resume from a last-seen event identifier, reload current state from an HTTP API, rejoin rooms and reconcile messages that may have been missed. A connection being open does not prove that the application state is current.

Heartbeats, Ping/Pong and idle timeouts

Some network intermediaries close connections that remain idle for too long. A server or proxy may have an idle timeout, and a mobile network can discard state after a device changes radio conditions. WebSocket Ping and Pong control frames can help an endpoint check whether its peer is responsive. Some browser APIs do not expose direct control over protocol Ping frames to JavaScript, so applications may implement a small application-level heartbeat message when needed.

Heartbeat frequency should be chosen carefully. Sending messages too often wastes bandwidth and battery, especially on mobile devices. Sending them too rarely may allow a proxy to close the connection before the next heartbeat. A server should also account for expected network delays and avoid treating one missed heartbeat as proof of malicious behaviour. Cloud providers publish their own connection limits and idle-timeout behaviour; developers must read the documentation for the actual service in use.

Cloudflare's WebSockets documentation explains its proxy support, idle timeout behaviour and the use of heartbeat messages to keep connections active. It also discusses session affinity for load-balanced origins, which can matter when a reconnect needs to return to a server that holds session state.

Security: authentication, Origin checks and authorisation

WebSocket security starts before the connection opens. A browser sends an Origin header in the opening handshake. The server should validate it against an explicit allowlist of trusted web origins. This helps defend against cross-site WebSocket hijacking, where a malicious website attempts to use a victim's browser and existing credentials to open a connection to another service. Origin validation is important, but it is not a substitute for authentication, and non-browser clients can supply arbitrary Origin values.

Authenticate the connection using a carefully designed mechanism. Depending on the architecture, this may involve secure cookies, a short-lived token or an authenticated session established through HTTPS. Avoid placing long-lived secrets in URL query strings because URLs can appear in logs, monitoring systems and browser history. If tokens are used, define how they expire, refresh and revoke, and ensure that the server does not trust a token merely because the client sent it.

Authorise every meaningful action and subscription. A user who can connect to the WebSocket endpoint is not automatically allowed to join every room or receive every event. Check access when a client subscribes, when it sends a command and when permissions change. Validate message types and fields, impose message-size limits, rate-limit expensive operations and avoid exposing internal error details. Use WSS in production to protect messages in transit.

The OWASP WebSocket Security Cheat Sheet provides implementation guidance on Origin validation, authentication, authorisation, input validation, denial-of-service risks and logging. The RFC also explains the browser origin security model and the importance of server-side checks.

Scaling WebSockets across many users

Traditional request-response servers can often handle each request independently. WebSocket servers maintain long-lived connections, so the infrastructure must track which users are connected to which process or server. A single server may be sufficient for a small application, but larger deployments need connection distribution, resource monitoring, graceful restarts and a way to deliver events to users connected to different instances.

A common design uses a shared message broker or publish-subscribe system. When an application event occurs, the server publishes it to a channel. Each WebSocket server instance subscribed to that channel can deliver the event to its locally connected clients. The broker may be Redis, NATS, Kafka or another system selected for the delivery guarantees and scale required. The WebSocket protocol itself does not provide a global broadcast mechanism across server machines.

Load balancers and reverse proxies must support connection upgrades and long-lived traffic. Session affinity can be useful when the application stores connection-specific state in memory, but it does not replace shared state or event distribution. If a server restarts, connected clients must reconnect and restore their subscriptions. Design for graceful draining so deployments do not abruptly disconnect every user at once.

Capacity planning should consider concurrent connections, messages per second, average message size, fan-out, TLS overhead, memory per connection, heartbeat traffic and peak reconnect rates. A service with 100,000 mostly idle connections has a different resource profile from one with 10,000 connections exchanging hundreds of messages each second. Measure the actual workload rather than estimating capacity from the number of registered users.

Backpressure and message queues

Backpressure occurs when data arrives faster than an application can process or transmit it. The standard browser WebSocket API does not provide automatic backpressure. If a server sends messages faster than the browser can handle them, the browser may buffer large amounts of data, consume memory and become unresponsive. The client can inspect properties such as bufferedAmount to understand how much outgoing data is queued, but application-level flow control is still important.

Not every update needs to be delivered individually. A live dashboard may receive 100 changes to the same metric in a short interval; it may be more useful to send the latest value than to queue every intermediate value. A collaborative editor, financial ledger or chat system may need stronger ordering and durability. The application should classify messages as replaceable state, transient notifications or durable events, then define what to do when the consumer falls behind.

Possible techniques include limiting message rates, batching updates, coalescing repeated state changes, dropping obsolete telemetry, applying per-client queue limits and disconnecting clients that cannot keep up. For workloads that require reliable processing, persist events or use a message broker rather than treating an open socket as durable storage. The browser's WebSocket API has no built-in backpressure mechanism, as noted in the MDN WebSockets guide.

WebSockets through CDNs, proxies and firewalls

Because WebSockets begin with an HTTP Upgrade request, they can often pass through web infrastructure that supports the upgrade. However, not every proxy, firewall, CDN or hosting platform handles long-lived connections in the same way. Some services impose maximum connection duration, idle timeouts, concurrency limits, message-size restrictions or plan-specific constraints. A connection may work in a local development environment but fail behind a production load balancer.

Check that the reverse proxy forwards the required Upgrade and Connection headers, preserves the correct host and scheme information, and allows the connection to remain open for the intended duration. Confirm that TLS terminates at the expected point and that origin routing remains consistent. If the application uses multiple origins or subdomains, validate that browser security and cross-origin policies match the actual deployment.

Cloudflare supports proxied WebSocket connections and documents its network settings, idle timeouts and load-balancer considerations. Other providers have different behaviour. Never assume that a feature supported by one CDN or hosting plan is automatically supported by another. Read the current provider documentation and test reconnects, server restarts and idle periods before launch.

Common WebSocket problems and how to troubleshoot them

If the browser reports that the WebSocket handshake failed, inspect the Network panel in developer tools. Look for the connection request and its HTTP status. A successful classic handshake should return status 101. A 400 or 403 may indicate malformed handshake headers, authentication failure or a rejected Origin. A 404 may indicate the wrong path or a server route that does not handle upgrades. A 5xx response can point to an origin or proxy problem.

If the connection opens and then closes repeatedly, check idle timeouts, heartbeat configuration, proxy logs, server restarts and mobile network transitions. Confirm whether the client is reconnecting too aggressively. If messages arrive late, measure server processing time, queue depth, event-loop delays and network round-trip time separately. If only some users fail, compare browser versions, corporate proxies, VPNs, network policies and geographic routes.

Use a small diagnostic client such as wscat to test a WebSocket endpoint independently of the full user interface. This can help determine whether the issue lies in the browser application or in the server and network path. Do not expose production secrets or send sensitive messages while testing. Log connection lifecycle events, close codes, rule decisions and timing data, but avoid recording private message content unless there is a justified and carefully controlled need.

When should you choose WebSockets?

Choose WebSockets when the application needs frequent communication in both directions, wants to send server events without waiting for a new client request, and can operate persistent connections reliably. Examples include collaborative editing, interactive support chat, multiplayer games, live control interfaces and bidirectional telemetry. The benefit becomes more compelling as message frequency and interactivity increase.

Choose ordinary HTTP when interactions are discrete, request-response is sufficient, and the client does not need continuous updates. Choose SSE when the server needs to push events to a browser but the browser can send commands separately using HTTP. Long polling can be a compatibility option where a persistent bidirectional protocol is not practical. A simpler design is often easier to secure, observe and scale.

There is no requirement to use WebSockets simply because an application is described as real-time. Define the maximum acceptable update delay, message direction, event rate, delivery guarantees, client environment and operational capacity. Prototype with realistic traffic and measure the full experience, including reconnect behaviour and battery use on mobile devices.

WebSockets and newer real-time technologies

WebSockets remain widely supported and useful, but they are not the only modern option. WebTransport is a newer web platform technology designed to provide more flexible transport capabilities, including streams and datagrams over HTTP/3. It can support use cases that need different delivery and ordering characteristics. Browser support, server availability, network compatibility and application requirements should be evaluated before choosing it.

WebRTC data channels are another option, particularly for peer-to-peer communication and interactive media applications. They can use secure datagram transport and are often combined with signalling services to establish sessions. They solve a different set of problems from a conventional browser-to-server WebSocket connection. A chat application might use WebSockets for signalling or server-mediated messages while WebRTC handles peer media or data.

Newer technologies do not automatically make WebSockets obsolete. Mature browser support, straightforward programming models and broad infrastructure compatibility make WebSockets a practical choice for many products. The right architecture may also combine technologies: HTTP for initial data and commands, SSE for one-way updates, WebSockets for interactive sessions and a durable message system behind the application.

Frequently asked questions

1. What is a WebSocket in simple terms?

A WebSocket is a protocol that keeps a connection open between a client and server so both sides can send messages to each other without creating a new HTTP request for every update.

2. How is WebSocket different from HTTP?

HTTP usually follows a request-and-response pattern, while WebSocket establishes a connection that stays open for two-way messaging. The initial WebSocket handshake uses HTTP, then communication switches to WebSocket frames.

3. What is the difference between WebSocket and Server-Sent Events?

WebSocket supports two-way communication over one connection. Server-Sent Events provide a one-way stream of events from server to browser over HTTP, while the browser sends data separately using ordinary requests.

4. Does WebSocket use TCP or UDP?

The WebSocket protocol defined by RFC 6455 is layered over TCP. Secure WebSockets use TLS over the connection and are commonly identified by the wss scheme.

5. What do ws and wss mean?

ws identifies a WebSocket URI without TLS, while wss identifies a WebSocket connection protected by TLS. Public browser applications should generally use wss when the page is served over HTTPS.

6. Are WebSocket connections always faster?

No. WebSockets can reduce repeated request overhead for frequent two-way updates, but they add connection management and server resource costs. For infrequent or one-way updates, ordinary HTTP or Server-Sent Events may be simpler and more efficient.

7. How do WebSockets stay connected?

The client and server keep the connection open and may exchange heartbeat messages. Ping and Pong control frames can help check responsiveness, while applications must handle idle timeouts, network changes and reconnects.

8. Are WebSockets secure?

WebSockets can use TLS through wss, but applications still need authentication, authorization, Origin validation, input validation, message limits, rate controls and careful session handling.

9. Can a WebSocket connection disconnect when I switch networks?

Yes. A change from Wi-Fi to mobile data, a lost signal, a proxy timeout or a server restart can break the underlying connection. A robust client detects closure and reconnects with controlled retry and state recovery.

10. What are WebSockets commonly used for?

Common uses include live chat, collaborative editing, multiplayer games, trading interfaces, monitoring dashboards, notifications and other applications that need frequent updates in both directions.
