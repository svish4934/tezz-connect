What Is a Network Firewall? Stateful Inspection, Rules, Zones and DMZs

Understand how network firewalls filter traffic, track connections, use ACLs and security zones, protect DMZs, and support network segmentation.

By Suraj Vishwakarma · Published by TEZZ CONNECT

A network firewall is a control point that decides which communications may cross a network boundary. It can filter packets, track active sessions, separate security zones and record traffic for investigation. Used well, it reduces unnecessary reachability and helps contain the impact of a compromised device.

Firewalls are often confused with routers, NAT devices and Web Application Firewalls. Those technologies can work together, but they do different jobs. This guide explains the core concepts, practical designs and common mistakes in language for students, home-network owners and IT teams.

1. What is a network firewall?

A network firewall controls which traffic is allowed to pass between networks or security zones. It can be a dedicated appliance, a virtual machine, a cloud service or a function built into a router or security platform. Its central job is to enforce a policy at a boundary: allow some communications, deny others, and record or inspect traffic where required.

A typical organisation has systems with different levels of exposure and sensitivity. Public internet users may need to reach a company's website, but they should not automatically be able to connect to employee laptops, databases or network-management interfaces. A firewall creates controlled paths between those environments.

Firewalls operate at different levels. A basic packet-filtering firewall can evaluate source and destination IP addresses, protocols and port numbers. A stateful firewall also tracks connection state. More advanced products may identify applications, users, devices or threat patterns. A host firewall protects an individual computer or server, while a network firewall commonly protects a group of systems or a boundary between segments.

The word firewall does not describe one universal feature set. Two products carrying that label may differ substantially in throughput, inspection capabilities, VPN support, logging, high availability and licensing. A useful design begins with the communication that must be protected, not with a product name.

2. Why networks need firewalls

IP networks are designed to exchange data. Without access controls, a reachable service may accept connections from devices that have no legitimate reason to communicate with it. A firewall reduces that exposure by making traffic subject to explicit policy.

Consider a small business network with employee computers, a file server, guest Wi-Fi, security cameras and a public-facing website. These systems do not all need the same access. Guest devices may need internet access but not access to employee file shares. Cameras may need to communicate with a recorder but not browse the internet freely. Administrators may need management access to switches and servers, but ordinary users do not.

A flat network treats many devices as if they belong to one broad trust zone. If one endpoint is compromised, an attacker may be able to probe other systems and move laterally. Segmentation divides the environment into smaller areas and places policy controls between them. Firewalls can enforce those boundaries, while VLANs, routers, host controls and identity systems provide complementary separation.

Firewalls also help reduce accidental exposure. A service may be listening on a port because of a default configuration or an installation process. A restrictive policy can prevent unapproved sources from reaching it. However, firewall policy cannot replace secure application configuration, software updates or authentication.

3. How packet filtering works

A packet-filtering firewall evaluates fields in network packets and compares them with configured rules. Common match criteria include source IP address, destination IP address, IP protocol, source port, destination port, ingress interface and egress interface. Depending on the platform, rules may also match direction, packet flags, ICMP types or other metadata.

For example, a rule might allow TCP traffic from a public load balancer address to a web server on destination port 443. Another rule might deny unsolicited inbound connections to an employee subnet. A third might permit DNS queries from an internal resolver to approved upstream resolvers. The policy describes the permitted communication rather than simply opening every port on a device.

Rules are evaluated according to the firewall's processing model. Many systems use an ordered rule list in which the first matching rule determines the action. Others use zones, objects, policy sections or compiled policy structures. Administrators must understand the specific product's rule ordering, implicit defaults and interaction between NAT and filtering.

Port numbers are not proof of application identity. TCP port 443 is commonly used for HTTPS, but other applications can use that port, and encrypted traffic may hide the application payload. Port-based rules are useful but should not be mistaken for deep application validation. Where application-aware controls are needed, confirm what the firewall can identify and what visibility remains when traffic is encrypted.

4. Stateful inspection: tracking conversations

Stateful inspection adds awareness of communication sessions. When a client initiates an allowed TCP connection, a stateful firewall records information about the flow, such as source and destination addresses, ports, protocol and connection state. Return packets that match the established session can be allowed without requiring a separate broad rule for every reverse direction.

For example, an employee device may initiate a connection to a permitted website. The firewall evaluates the outbound request against policy and creates connection state. When the website sends response packets back, the firewall checks that they correspond to the expected connection. It can reject unrelated unsolicited packets that do not match a permitted state.

State tracking differs by protocol. TCP has flags and a connection-establishment process that provide useful state information. UDP does not establish a connection in the same way, so firewalls commonly track a temporary flow based on observed traffic and timeout behaviour. ICMP handling also varies by message type and implementation. Stateful inspection is therefore not a guarantee that every packet represents a legitimate user action.

State tables consume memory and processing resources. High connection rates, denial-of-service conditions, long timeouts or unusual application patterns can affect state capacity. Operators should monitor concurrent sessions, new-connection rates, table utilisation and drops. A firewall that has insufficient state capacity can become a bottleneck even when its advertised raw throughput looks adequate.

Stateful inspection is also not the same as application security. It can understand whether packets belong to a tracked flow, but it may not know whether a logged-in user is authorised to view a particular record or whether an application request contains malicious input.

5. Firewall rules and ACLs: building a clear policy

An access control list (ACL) is a set of permit and deny conditions applied to traffic. ACLs can exist on routers, switches, operating systems and firewalls. A network firewall may offer a richer policy framework, but the underlying idea is similar: compare traffic against conditions and take an action.

A well-designed policy starts with required communication flows. Record the source zone, destination zone, source and destination services, business owner, purpose, expected users and whether the connection must be initiated in one direction or both. Translate those needs into the narrowest practical rules.

Least privilege means allowing only the access required for a task. If a monitoring server needs to query a group of network devices using a defined management protocol, avoid allowing the entire user subnet to reach every management port. If a public web tier needs to access a backend service, specify the exact destination and service rather than opening unrestricted access to an entire internal network.

Deny by default means traffic that does not match an explicit permission is blocked. This approach reduces the chance that an unplanned service becomes reachable. It also makes rule review easier because the intended exceptions are visible. The implicit deny behaviour must be understood, documented and tested so that legitimate dependencies are not accidentally interrupted.

Every rule should have a purpose and an owner. Use descriptive names, ticket references or change identifiers where supported. Avoid ambiguous objects such as “Any-Any-Temporary” that remain in production long after their original need has passed. Temporary rules should have expiry dates and an accountable owner.

Rule order matters on platforms that use ordered evaluation. A broad allow rule placed above a restrictive deny can make the deny ineffective. Shadowed rules may never be reached. Regular analysis should identify duplicates, conflicts, unused rules and rules that are broader than their documented requirement.

6. Security zones and network segmentation

A security zone groups interfaces or networks with a similar trust level or policy role. Common examples include outside, inside, guest, server, management, partner and operational technology zones. A firewall policy controls traffic between zones according to business requirements.

Zones are not automatically secure merely because they have different names. The actual boundary depends on how interfaces, routes, VLANs, virtual networks and firewall policies are configured. A guest VLAN that can reach the internal server subnet is not effectively isolated just because it is labelled “Guest.”

Segmentation reduces the number of systems that can communicate freely. It can limit lateral movement after an endpoint is compromised and make suspicious traffic easier to identify. Segmentation should reflect data sensitivity, system function, operational dependencies and the impact of failure. Excessively complex segmentation can be difficult to maintain, so design boundaries that can be explained and tested.

For example, separate employee workstations, guest devices, production servers, backup systems and management interfaces. Permit only the flows needed for services such as DNS, identity, application access, backups and monitoring. Restrict administrative access to trusted management devices and accounts. Apply endpoint firewalls as another layer, particularly for systems that move between networks.

Microsegmentation takes the idea further by enforcing more granular policies between workloads or individual systems. It can use host agents, distributed firewalls, virtual network policy or identity-aware controls. The aim is not to create a rule for every packet manually, but to make access decisions closer to the workload and based on a clearly defined need.

7. What is a DMZ and when is it useful?

A demilitarized zone (DMZ) is a network segment used for systems that must communicate with less-trusted networks while remaining separated from sensitive internal resources. Public-facing web servers, reverse proxies, mail gateways, DNS services and other externally reachable systems may be placed in a DMZ, depending on the architecture.

The purpose is to limit what happens if a public-facing service is compromised. A web server in a DMZ should not automatically have broad access to employee devices or internal databases. Firewall rules should permit only the specific backend connections required, such as a web application reaching a designated application or database service on defined ports.

Some designs use a single firewall with multiple security zones. Others use separate firewalls or a screened subnet architecture. Cloud deployments may implement a DMZ-like pattern using virtual networks, subnets, route tables, security groups, network firewalls and load balancers. The terminology varies, but the principle is controlled separation between exposure levels.

A DMZ is not a magical safe zone. Public services still need patching, hardening, strong authentication, logging and application security. Administrative access should be restricted and monitored. Avoid placing secrets or unnecessary data on a public-facing host, and design backend permissions so that compromise of one service does not grant access to everything behind it.

8. NAT and firewall policy: related but different

Network Address Translation changes IP address information as packets cross a device. Source NAT can translate private internal addresses to a public address for outbound access. Destination NAT or port forwarding can map an externally addressed connection to an internal service.

NAT is frequently implemented on the same device as a firewall, which can make the two concepts appear identical. They are not. NAT changes addressing; firewall policy decides whether traffic is permitted. Some NAT implementations have stateful behaviour, but address translation alone is not a complete security strategy.

For an inbound service, a port-forwarding rule may translate a public destination address and port to a private server. The firewall must still apply the intended security policy. Administrators should confirm which address is used for policy matching, how rules are ordered relative to translation, and whether the platform uses separate NAT and access-control rule sets.

Outbound NAT can make many private devices share one public IPv4 address. This is common in homes and small offices. It does not prevent malware, phishing or malicious outbound communication from a compromised device. Egress filtering, DNS controls, endpoint protection and monitoring are still important.

When troubleshooting NAT, inspect both the original and translated flow, routing in both directions, session state and any upstream filtering. Asymmetric routing—where request and response packets take different paths—can break stateful inspection if the firewall does not see both directions or has not been designed for that topology.

9. Firewall types: packet filters, stateful, proxy and next-generation

Stateless packet filters evaluate individual packets using header information. They can be efficient and useful for simple controls, but do not maintain the same connection context as a stateful firewall.

Stateful firewalls track sessions and apply policy with awareness of connection state. They are widely used at network boundaries and between internal security zones.

Proxy firewalls act as intermediaries for supported application traffic. A proxy can terminate one connection and create another, providing a point to apply application-specific controls. Proxy designs can offer detailed inspection but may introduce compatibility, performance and certificate-management considerations.

Next-generation firewalls (NGFWs) commonly combine stateful inspection with features such as application identification, intrusion prevention, URL filtering, threat intelligence and user-aware policy. The exact functions vary by vendor, platform, subscription and configuration. A product's marketing category does not guarantee that every feature is enabled or effective.

Host-based firewalls run on individual computers or servers and control inbound and outbound traffic at the endpoint. They are valuable because network boundaries cannot protect a laptop when it moves to a public network or two compromised devices communicate within the same subnet. Host controls complement, rather than replace, network firewalls.

Cloud firewalls may be delivered as managed services or implemented through virtual appliances and native cloud network controls. They protect cloud workloads and network paths, but the operator must understand shared-responsibility boundaries, routing, identity integration, logging and how policies apply across regions and accounts.

10. Network firewall vs Web Application Firewall

A network firewall and a Web Application Firewall (WAF) solve related but different problems. A network firewall commonly controls traffic between networks, interfaces or security zones. It can allow or deny connections based on IP addresses, protocols, ports, connection state and sometimes application identity.

A WAF focuses on HTTP and HTTPS requests to web applications. It can inspect request paths, headers, parameters, cookies and payload patterns to detect or block attacks such as SQL injection and cross-site scripting attempts. WAFs can operate as reverse proxies, cloud services or integrated application-security controls.

A WAF does not replace a network firewall. A web application can be protected by both: the network firewall limits which systems can reach the web tier and backend services, while the WAF applies HTTP-aware rules to requests. Similarly, a network firewall cannot be assumed to understand every application-level vulnerability simply because it permits only TCP port 443.

Use the control that matches the risk. Network segmentation and stateful rules protect boundaries and reduce reachability. WAF policies help protect web request handling. Secure coding, authentication, patching, rate limiting, endpoint security and monitoring remain necessary layers.

11. Inbound and outbound filtering

Inbound filtering controls traffic entering a network or zone. It should expose only services that are intentionally reachable. For a public web service, that may mean allowing traffic to a load balancer or reverse proxy on the required ports while blocking direct access to backend management interfaces.

Outbound or egress filtering controls traffic leaving a network. It can limit which internal systems can connect to external destinations and services. For example, user devices may be allowed to reach approved DNS resolvers and web gateways, while database servers may have no general need for unrestricted internet access.

Egress controls can help limit command-and-control channels, data exfiltration and accidental exposure, but they require careful dependency mapping. Applications may rely on software repositories, cloud APIs, certificate status services, time synchronisation or vendor update endpoints. Start with visibility and a documented allowlist plan rather than abruptly blocking unknown traffic in a production environment.

Logging denied traffic can help identify unexpected dependencies and scanning. However, logging every packet can create excessive volume and obscure meaningful events. Choose useful log conditions, aggregate repetitive events, synchronise clocks and send important records to a protected central system.

12. High availability, throughput and performance

A firewall is often a critical network dependency. If it fails, internet access, site-to-site connectivity or communication between internal zones may stop. High-availability designs use redundant devices or service instances, health checks and state synchronisation where supported. Failover behaviour must be tested; two devices installed side by side do not automatically provide resilience.

Throughput figures depend on the traffic and features being measured. A vendor may publish a high firewall throughput number for basic packet forwarding, while enabling intrusion prevention, TLS inspection, application identification or extensive logging can reduce practical capacity. Compare performance for the feature set you intend to run.

Also consider concurrent session capacity, new sessions per second, VPN throughput, interface speeds, packet size, latency, failover time and log ingestion. A device sized only by the current internet circuit may be inadequate if east-west traffic, remote access or encrypted inspection grows significantly.

Capacity planning should include growth and peak periods. Monitor CPU, memory, session tables, interface errors, drops, queue utilisation and security-engine health. Establish alert thresholds and test representative traffic before major policy or software changes.

13. Firewall logging, monitoring and rule lifecycle

Firewall logs can show allowed and denied connections, policy matches, session creation and termination, NAT translations, VPN events, administrator actions and security detections. The available fields vary by product and configuration. Logs are useful only when time is synchronised, records are retained appropriately and teams know how to investigate them.

Send important logs to a central, access-controlled platform so they remain available if the firewall is damaged or compromised. Protect management and logging channels. Define who reviews alerts, how high-severity events are escalated and how evidence is preserved during incident response.

Rules need a lifecycle. A practical process includes request, risk review, approval, implementation, testing, monitoring, periodic recertification and removal. Every exception should have an owner and a business justification. Review temporary rules before their expiry and remove stale entries after application migrations or decommissioning.

Use change control for production policy updates. Where possible, test rules in a lab or staging environment, validate syntax, review the expected traffic impact and prepare a rollback. After deployment, verify both the intended permitted flow and the traffic that should remain blocked.

14. A practical small-office firewall design

Imagine a small organisation with an internet connection, employee devices, guest Wi-Fi, a public website, a file server, cameras and a management network. A useful starting design might create separate zones for outside, staff, guest, servers, cameras and management.

  • Outside: the internet-facing interface. Allow only explicitly published services and required VPN access.
  • Staff: employee devices. Permit approved business applications, DNS and internet access through the intended security controls.
  • Guest: visitor devices. Permit internet access while blocking internal address ranges and management services.
  • Servers: business applications and data stores. Permit only required application flows from approved source zones.
  • Cameras/IoT: connected devices. Permit communication to their recorder or controller and necessary update or time services; restrict other access.
  • Management: network-device and server administration. Permit access only from authorised administrator workstations and accounts.

If a public website is hosted on premises, place the public-facing component in a DMZ or equivalent isolated cloud segment. Do not let a public web server initiate arbitrary connections to employee endpoints. If it must reach a database, allow only the exact application-to-database flow and monitor it.

Document the diagram, address ranges, VLANs, firewall zones, permitted flows, service owners and recovery steps. A simple policy that is understood and maintained is more valuable than an elaborate rule set nobody can explain.

15. Common firewall mistakes and troubleshooting

Opening a broad port range to fix an application. This may make the immediate symptom disappear but creates unnecessary exposure. Identify the exact protocol, source, destination and port required. Check application documentation and logs before expanding access.

Assuming NAT blocks all inbound attacks. NAT is not a replacement for a firewall policy. Review port forwards, UPnP exposure, remote administration and rules that allow unsolicited traffic.

Creating a rule in the wrong order or zone. Verify interface-to-zone mapping, route selection, rule order, implicit deny and NAT processing. Use packet-trace or policy simulation tools where available.

Forgetting return routing. A firewall may permit the initial request but the response can leave through a different gateway. Check routing tables, policy-based routing, asymmetric paths and state synchronisation in HA designs.

Breaking DNS or identity services. Authentication, name resolution, time synchronisation and certificate validation are dependencies for many applications. Map them before tightening policy and monitor the impact of changes.

Allowing unrestricted internal traffic. A perimeter firewall does not protect every internal communication path. Segment critical systems and use host controls to reduce lateral movement.

Ignoring encrypted traffic visibility. TLS encryption protects data in transit, but it also limits what network inspection can see. Use endpoint telemetry, application logs, secure DNS controls and carefully governed inspection where appropriate. Do not disable encryption casually to gain visibility.

Not testing failover. Verify that redundant devices, links, routing and VPN tunnels behave as expected during an actual controlled test. Confirm that logs, alerts and session handling work after failover.

16. How to plan a firewall policy safely

Begin with an inventory of assets, network segments, applications, data classifications and communication dependencies. Identify which services must be reachable from the internet, which should be internal-only and which require restricted administrative access. Include remote workers, cloud workloads, partner connections and operational technology where relevant.

Draw traffic-flow diagrams before writing rules. For each flow, record who initiates it, which system receives it, the protocol and port, the business purpose, the owner and the expected frequency. Ask whether the flow is required or simply exists because the network has historically been permissive.

Apply least privilege and deny-by-default in stages. Start with visibility, then tighten a limited group of flows, test applications and expand carefully. Keep emergency access procedures documented and protected. A security policy that cannot be operated during an incident can create unnecessary risk.

Review the result against the organisation's threat model and compliance requirements. Confirm that sensitive systems are segmented, administrative access is restricted, logs are retained, changes are approved and the firewall itself is hardened. Keep firmware current and remove unused services, default credentials and unnecessary management exposure.

Conclusion: a firewall is a policy enforcement point, not a complete security strategy

A network firewall controls communication between networks and security zones. Packet filters match addresses and services; stateful inspection tracks conversations; zones and DMZs create boundaries; and NAT changes address information without replacing access-control policy.

Effective firewall design depends on clear traffic requirements, least privilege, deny-by-default rules, segmentation, logging and regular review. The firewall should be sized for the actual inspection features and traffic load, and high-availability behaviour should be tested rather than assumed.

Most importantly, firewalls are one layer in a wider security architecture. Combine network controls with endpoint protection, identity and access management, encryption, secure application development, patching, monitoring and incident response. The objective is not simply to block traffic; it is to allow necessary communication while limiting unnecessary access and containing the impact of compromise.

Frequently asked questions about network firewalls

1. What is a network firewall?

A network firewall is a hardware appliance, virtual appliance or software function that controls traffic between networks or security zones according to an established policy. It can allow, deny, inspect and log connections based on addresses, protocols, ports, connection state and, on some platforms, application or identity information.

2. What is the difference between a firewall and a router?

A router forwards packets between IP networks using routing information. A firewall enforces security policy on traffic. Many products combine routing and firewall functions, but routing a packet does not automatically mean the traffic should be permitted.

3. What is stateful inspection?

Stateful inspection tracks active communication sessions and evaluates packets in the context of connection state. It can allow valid return traffic for an approved connection while rejecting packets that do not match expected session behaviour.

4. What is a firewall rule or ACL?

A firewall rule or access control list entry defines which traffic is permitted, denied or handled in a particular way. Rules may match source and destination addresses, protocol, ports, interface, zone, connection state, user or application, depending on the firewall.

5. What is a DMZ in networking?

A demilitarized zone is a separate network segment used to host services that must communicate with less-trusted networks, such as public web or mail services. Firewall policies restrict which connections can pass between the DMZ, internet and internal networks.

6. Does NAT provide firewall security?

Network Address Translation changes address information as packets cross a device. It is not a complete security policy by itself. Security depends on explicit filtering, connection tracking, exposure settings and the device's configuration.

7. What is the difference between a network firewall and a WAF?

A network firewall controls traffic between network interfaces or security zones using network and transport information and sometimes application awareness. A Web Application Firewall focuses on HTTP and HTTPS application requests, helping protect web applications from attacks such as injection and malicious request patterns.

8. Should a firewall block all traffic by default?

A deny-by-default approach is a strong baseline: permit only required communication and deny other traffic. The policy still needs carefully defined exceptions, documented business reasons, monitoring and testing so essential services continue to work.

9. Can a firewall stop every cyberattack?

No. A firewall is one layer of defence. It cannot reliably stop every phishing attack, compromised endpoint, insider threat, malicious encrypted session or application vulnerability. It should be combined with endpoint protection, identity controls, patching, encryption, monitoring and incident response.

10. How often should firewall rules be reviewed?

Review rules on a defined schedule and whenever applications, users, network architecture or business requirements change. Remove obsolete and overly broad rules, verify rule owners and purpose, inspect logs, and test changes before and after deployment.
