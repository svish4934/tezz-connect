How DHCP Works: DORA, IP Leases, Reservations, Relay and Security

Learn how DHCP automatically configures IP addresses, how the DORA process works, how leases and reservations differ, and how relay agents, DHCPv6 and security controls fit together.

By Suraj Vishwakarma · Published by TEZZ CONNECT

DHCP is the network service that lets a phone, laptop, smart television or office workstation join an IP network without requiring a person to type every network setting. When a device connects to Wi-Fi or plugs into Ethernet, it can ask a DHCP server for an address and supporting configuration. The server manages a pool of addresses, tracks allocations and offers settings such as the subnet mask, default gateway and DNS resolvers.

The familiar four-step DHCPv4 exchange is called DORA: Discover, Offer, Request and Acknowledge. Yet DHCP is more than those four messages. Lease timers, renewals, reservations, relay agents, options, duplicate-address checks, IPv6 configuration and security controls all determine whether a device receives reliable network access.

1. What is DHCP and why do networks need it?

Dynamic Host Configuration Protocol (DHCP) automates the delivery of IP configuration to clients. The core DHCPv4 specification is IETF RFC 2131, with many configuration options defined in RFC 2132. Rather than manually assigning an address to every endpoint, an administrator defines a scope or pool and lets the service allocate addresses according to policy.

A typical client needs more than an IP address. It needs to know which addresses are local, where to send traffic for remote networks and which DNS servers can translate domain names. DHCP options can carry a subnet mask, router address, DNS server list, domain search information, lease duration and other parameters supported by the client.

Consider a home network using 192.168.1.0/24. The router may run a DHCP server with a pool from 192.168.1.100 to 192.168.1.199. When a new phone joins Wi-Fi, it can receive 192.168.1.104, a /24 subnet mask, the router's LAN address as its default gateway, and one or more DNS server addresses. The exact values depend on the router configuration.

DHCP reduces repetitive work, prevents many accidental address conflicts when correctly managed, and makes changes easier. If an organisation changes its DNS resolvers, it can update the DHCP scope rather than visiting every workstation. Clients receive the new configuration as leases renew or as they reconnect.

DHCP is a configuration protocol, not an internet service by itself. A successful lease does not prove that the broadband connection works, that DNS is reachable, or that a website is online. It simply gives the client the network parameters it needs to attempt communication.

2. The DORA process: Discover, Offer, Request and Acknowledge

DORA describes a common initial DHCPv4 address allocation. A client that has no usable IPv4 configuration begins by discovering available DHCP servers. Because it may not know a server address yet, the initial message is commonly broadcast on the local network.

Step 1: Discover

The client sends a DHCPDISCOVER message. It identifies itself using fields such as its hardware address and may include a requested address or other client information. On a typical Ethernet LAN, the client does not yet have a normal IPv4 address, so the message is sent using source address 0.0.0.0 and a broadcast destination. The exact packet flags and delivery details depend on the client and network.

Step 2: Offer

A DHCP server that can serve the client responds with a DHCPOFFER. The offer proposes an address and includes configuration options and lease information. More than one server may respond. The client can evaluate the offers and select one according to its implementation and policy; the first offer is not automatically guaranteed to be the one chosen.

Step 3: Request

The client sends DHCPREQUEST to indicate which offered address and server it has selected. In the common initial broadcast exchange, this message also informs other responding servers that their offers were not selected, allowing them to make those offered addresses available again. The request identifies the selected server and requested address through DHCP fields and options.

Step 4: Acknowledge

The selected server responds with DHCPACK if it approves the request. The acknowledgement confirms the lease and supplies the final configuration options. The client can then configure its interface and begin normal IPv4 communication. If the server cannot honour the request, it may send DHCPNAK, requiring the client to restart or obtain valid configuration.

DORA is a useful mental model, but not every DHCP exchange contains exactly these four messages. Renewals, rebinding, lease release, address checking, information-only requests and server-directed changes use other message sequences. Packet captures should be interpreted in context rather than assuming every DHCP packet belongs to a fresh DORA cycle.

3. DHCP message types and what they mean

DHCPv4 uses a set of message types for different stages of configuration. DHCPDISCOVER searches for servers; DHCPOFFER proposes configuration; DHCPREQUEST asks for or renews an address; DHCPACK confirms a lease; DHCPNAK rejects a request; DHCPDECLINE tells the server that an offered address appears to be in use; DHCPRELEASE relinquishes a lease; and DHCPINFORM asks for configuration parameters when a client already has an address configured through another method.

These messages share a common DHCP message structure. Fields include an operation code, hardware type and length, transaction identifier, elapsed time, flags, client and server addresses, client hardware address, optional server name and boot file fields, followed by a vendor-specific options area. The transaction identifier helps a client match replies to its request. Options carry much of the practical configuration information.

DHCP uses UDP. For DHCPv4, servers listen on UDP port 67 and clients use UDP port 68. A firewall or packet filter that blocks the required traffic between a client VLAN and its server or relay can prevent configuration. DHCP is not carried over TCP and does not use a web port such as 80 or 443.

In packet captures, a DHCP exchange may be labelled BOOTP because DHCP builds on the BOOTP message format. This does not mean that the network is necessarily using the older BOOTP configuration protocol. Wireshark commonly decodes DHCPv4 packets with BOOTP-related field names because of this protocol history.

4. DHCP leases: address allocation is time-limited

A DHCP lease is a time-limited agreement that allows a client to use an assigned address and associated parameters. The server records the binding and the client tracks when it must renew. A lease is important because address pools are finite. When a device disconnects permanently, its address can eventually return to the available pool rather than remaining reserved forever.

Lease duration is an administrative choice. A guest Wi-Fi network with many short-lived visitors may use shorter leases so addresses can be recycled. A corporate network with stable workstations may use longer leases to reduce renewal traffic and make address allocation predictable. Very short leases can create unnecessary renewal activity and make temporary server outages more disruptive; very long leases can delay recovery of addresses when devices disappear.

DHCPv4 clients commonly use two renewal milestones called T1 and T2. Unless configured otherwise, RFC 2131 defines default values of 0.5 of the lease duration for T1 and 0.875 for T2. At T1, the client normally attempts to renew with the original server using unicast. If it has not succeeded by T2, it enters rebinding and can broadcast a request so another server may respond. The server can supply different timer values, so these defaults should not be mistaken for fixed behaviour in every network.

If a lease is renewed successfully, the client receives a new lease period. If renewal fails but the lease has not expired, the client may continue using the address while trying again. Once the lease expires without renewal, the client must stop using that address and obtain valid configuration. Operating systems may present this to users as a brief network interruption or a connection that appears connected to Wi-Fi but has no usable IPv4 connectivity.

Lease records are also useful for operations and investigations. They can help an administrator associate an address with a client identifier or hardware address at a particular time. Logs must be retained and interpreted with time synchronisation and privacy requirements in mind. A current lease table alone may not answer who used an address last week if historical records were not retained.

5. DHCP renewal and rebinding explained

A device does not normally wait until a lease expires before asking to keep its address. It attempts renewal in advance. At T1, it typically contacts the server that granted the lease. This is efficient because the original server already knows the binding and can extend it if policy allows.

If the original server is unavailable, the client continues to retry according to its timers. At T2, it enters rebinding and broadens the request so another server can renew the lease. This is one reason DHCP servers in a coordinated environment can provide resilience. However, multiple servers must have consistent scope design and safeguards against handing out conflicting addresses.

Renewal is not the same as a brand-new DORA exchange. A DHCPREQUEST used for renewal has a different context from the initial request, and the client may already be configured with an address. A server can acknowledge the renewal, reject it, or fail to respond. A network trace showing DHCPREQUEST without a preceding DHCPDISCOVER is therefore not automatically evidence of a fault.

When a laptop sleeps, changes networks or moves between access points, the operating system may preserve or revalidate its lease depending on its state and network conditions. If it moves to a different subnet, the old address may no longer be appropriate. It must obtain configuration valid for the new link. This explains why reconnecting to a different Wi-Fi network can trigger DHCP activity even when the laptop was already configured moments earlier.

6. DHCP scopes, pools, exclusions and reservations

A DHCP scope defines the network and range of addresses a server can allocate, together with relevant options and policies. In a /24 network, an administrator might configure a usable pool that excludes the router, switches, printers and servers that have manually assigned addresses. Exclusions prevent the DHCP server from allocating addresses that are already used for infrastructure.

A reservation associates a chosen address with a client identity so the server offers that address to the matching device. The identity may be a MAC address, client identifier or another platform-specific identifier. Reservations are useful for printers, access points, cameras and other equipment that benefits from a predictable address while still receiving configuration from DHCP.

A reservation is not identical to a static address configured on the device. With a reservation, the server remains responsible for the allocation and can deliver gateway, DNS and other options. With a manually configured static address, the endpoint itself stores the address and related parameters. Administrators must ensure static addresses do not overlap with dynamic pools and that subnet, gateway and DNS settings are correct.

Reservations also depend on identity stability. A device that randomises its Wi-Fi MAC address may appear to the server as a different client and fail to receive the expected reservation. Some operating systems use a per-network private address, which improves privacy but can affect MAC-based network policies. Administrators should understand the endpoint's identity behaviour before relying on a hardware-address reservation.

For larger networks, scopes may be divided by VLAN or subnet, with policies for different device classes. Address planning should leave room for growth, infrastructure, failover and temporary devices. A pool that is nearly exhausted can cause intermittent failures: some clients may obtain leases while others receive no offer because no free addresses remain.

7. DHCP options: more than an IP address

DHCP options carry configuration details beyond the assigned address. Common DHCPv4 options include subnet mask (option 1), router/default gateway (option 3), DNS servers (option 6), domain name (option 15), lease time (option 51), message type (option 53), server identifier (option 54), renewal time (option 58) and rebinding time (option 59). The official option registry and standards define how values are represented.

The router option tells a client which next hop to use for destinations outside its local subnet. The DNS server option tells it where to send name-resolution queries. A client can have a valid IP address and still fail to open websites if it receives an incorrect DNS server or gateway. That is why troubleshooting should inspect all relevant options rather than checking only the address.

Some environments use options for network boot, voice devices, vendor-specific configuration or domain search behaviour. These options are not universally supported by every client. A server can send an option, but the endpoint must understand and apply it. Administrators should consult vendor documentation before relying on specialised options.

DHCP option 82, commonly called the Relay Agent Information Option, can be inserted by a relay or network access device to identify the circuit or remote access context from which a request arrived. It can help a server apply policy based on the access port or subscriber circuit. Because this information influences allocation decisions, relay insertion and trust boundaries must be configured carefully.

8. DHCP relay agents: serving multiple subnets

A DHCP server does not have to sit on every client subnet. A DHCP relay agent receives client broadcasts on a local network and forwards the relevant DHCP message to a server on another IP network. The relay makes centralised address management practical for campuses, offices, hotels and service-provider networks.

Routers do not normally forward IPv4 broadcast traffic from one subnet to another. Without a relay, a client broadcast may never reach a central DHCP server located elsewhere. A relay listens on the client-facing interface, adds information needed to identify the originating subnet, and forwards the request to the configured server. The server uses that context to select the correct scope and returns a response through the relay.

The relay's gateway address field, often called giaddr in DHCPv4, helps the server identify the client subnet. Relay agents may also add option 82 information. The server replies to the relay, which delivers the response on the client network. From the client's perspective, the relay is usually transparent.

When DHCP works on one VLAN but fails on another, check the relay configuration, helper address, server reachability, routing and access-control rules. Confirm that the server has a scope for the client subnet and that the relay is pointing to the intended server. A missing scope or incorrect relay interface can result in no offer even though the DHCP server itself is healthy.

Relays are security-sensitive infrastructure. A network should accept relay information only from trusted devices and interfaces. Unexpected relay metadata or requests arriving from untrusted network segments should be investigated. The server should not blindly trust client-supplied information that is intended to be inserted by an authorised relay.

9. DHCPv4 versus DHCPv6

DHCPv4 and DHCPv6 share a goal—delivering network configuration—but they are not simply the same packet format with different address lengths. DHCPv6 is specified by the current RFC 9915, which obsoletes RFC 8415. It supports stateful assignment of IPv6 addresses and prefixes as well as stateless delivery of other configuration information.

IPv6 also has Stateless Address Autoconfiguration (SLAAC). A host can form an IPv6 address using information in Router Advertisements, without asking DHCPv6 for an address. DHCPv6 may still provide DNS information or other parameters, depending on network policy and router-advertisement flags. In other deployments, DHCPv6 can assign addresses or delegate prefixes.

DHCPv6 uses UDP port 546 for clients and 547 for servers and relay agents. Its message exchanges use IPv6 link-scoped multicast so clients can discover servers or relay agents without already knowing their unicast addresses. A relay agent can forward messages when the server is not on the client's link.

One important difference is that DHCPv6 does not use the IPv4-style broadcast DORA sequence. It has its own message types and exchanges, including Solicit, Advertise, Request and Reply for a common stateful allocation. The names may look similar to DHCPv4, but the packet structure, addressing and details are distinct.

DHCPv6 and SLAAC can coexist. A device may have a link-local IPv6 address, one or more SLAAC global addresses and a DHCPv6-assigned address or configuration options at the same time. Troubleshooting IPv6 therefore requires checking router advertisements, prefix information, DHCPv6 service and DNS configuration rather than assuming one mechanism controls every address.

10. DHCP security: rogue servers, starvation and spoofing

DHCP was designed for convenient configuration, not as a complete identity or trust system for every endpoint. A rogue DHCP server on an access network can answer clients with a malicious or incorrect gateway, DNS resolver or other settings. A client may then send traffic through an attacker-controlled device or resolve names using an untrusted resolver.

DHCP starvation is an availability attack in which an attacker generates many requests with changing client identities to consume the available address pool. Legitimate devices may then be unable to obtain leases. Defences include access-layer rate limits, port security, network access control, monitoring for abnormal client churn and sensible pool sizing. Controls must be tuned to avoid blocking legitimate devices in dense or rapidly changing environments.

DHCP snooping on managed switches can help prevent unauthorised DHCP server replies. Administrators mark trusted ports—typically those connected toward authorised servers or relays—and leave ordinary client-facing ports untrusted. The switch can then block server messages arriving from untrusted ports and build a binding database of observed client, address, VLAN and port information.

That binding information may support Dynamic ARP Inspection and IP Source Guard on platforms that implement them. These controls can reduce certain address-spoofing risks, but they depend on correct VLAN, port and trust configuration. Misconfigured trusted uplinks or incomplete binding data can create security gaps or disrupt legitimate clients.

DHCPv6 has its own security considerations. The current specification discusses threats such as malicious servers and forged reconfiguration messages. Network operators should secure relay-to-server communication, constrain which devices can act as relays, use appropriate first-hop security features where available and monitor unexpected DHCPv6 activity. IPv6 security should not be ignored simply because an organisation believes it is using only IPv4.

DHCP does not encrypt every client-to-server exchange end to end. Do not treat receipt of a lease as proof that the network or server is trusted. Combine DHCP controls with 802.1X or other access controls, segmentation, secure DNS practices, endpoint protection, switch hardening and encrypted application protocols.

11. Common DHCP problems and how to troubleshoot them

No address or a 169.254.x.x address

On many IPv4 systems, an address in 169.254.0.0/16 indicates link-local addressing, often selected when normal DHCP configuration could not be obtained. Check Wi-Fi association or Ethernet link state first, then confirm that the client is on the intended VLAN and that DHCP requests reach a server or relay. A link-local address does not usually provide ordinary access to routed internet destinations.

DHCP pool exhaustion

Inspect the scope's available-address count and lease table. A pool may be too small for the number of concurrent clients, or stale allocations may be held longer than needed. Do not simply shorten every lease without understanding client behaviour and churn. Expand the subnet or pool only after checking address planning and avoiding infrastructure conflicts.

Wrong gateway or DNS server

Inspect the actual options received by the client, not only the server's intended configuration. A rogue server, incorrect scope, policy match or relay issue can deliver unexpected values. Compare the client's gateway and DNS list with a known-good device on the same VLAN.

One VLAN works, another fails

Check the DHCP relay or helper address on the failing VLAN's Layer 3 interface, routing to the server, firewall rules and the existence of a matching scope. Verify that relay information identifies the correct subnet and that return traffic can reach the relay.

Address conflict or repeated DHCPDECLINE

A client may decline an address if it detects that the address is already in use. Investigate static addresses placed inside the dynamic pool, duplicate reservations, stale server records or another DHCP server. A conflict should be resolved at the source; repeatedly forcing clients to retry does not fix the underlying address plan.

Intermittent connectivity after sleep or roaming

Check whether the client has moved to a different subnet, whether its lease is near expiry, and whether renewal messages receive acknowledgements. Compare the client's current address, gateway, DNS and VLAN with the expected network. Wireless roaming within one subnet should not normally require a new address, but roaming across routed segments may.

A useful troubleshooting sequence is: verify physical or wireless link; inspect the client's address and lease; capture DHCP packets; confirm Discover/Offer/Request/Acknowledge or the relevant renewal exchange; inspect options; verify scope capacity; check relay and firewall paths; and review switch security features. Change one variable at a time and record the result.

12. Practical DHCP examples for home and business networks

In a home router, DHCP is often enabled by default. The router may act as gateway, DHCP server, DNS forwarder and wireless access point in one device. The admin interface usually exposes a start and end address, lease duration, DNS settings and reservation controls. Before changing the pool, identify the router's own LAN address and any manually configured devices.

For a small office, separate VLANs may exist for staff, guests, printers, phones and infrastructure. Each routed VLAN needs an appropriate DHCP scope or a relay path to a central server. Different scopes can deliver different DNS suffixes, gateways or vendor options. Guest devices should not receive the same access permissions as internal workstations merely because both receive an IP address.

For a campus or multi-site organisation, central DHCP servers and relay agents reduce the need to maintain a server at every location. Redundancy, scope design, failover behaviour, logging, time synchronisation and change management become important. Administrators should document which server owns each scope and how relay devices reach it.

For IoT and building systems, address reservations can simplify inventory, but they should not replace network segmentation or device authentication. Cameras, access controllers, sensors and smart displays may have limited security update support. Put them in appropriately restricted segments and monitor their DHCP behaviour for unexpected changes.

13. What DHCP does not do

DHCP does not authenticate a user in the same way that an identity provider does. It does not encrypt general internet traffic, guarantee that a device is safe, or decide which applications a user may access. A client can receive a valid lease and still be blocked by network access policy or unable to reach the internet.

DHCP also does not replace DNS. DHCP can tell a client which DNS resolver to use, but DNS performs the name-to-address lookup. Nor does DHCP replace routing: it can provide a default gateway address, but routers determine how packets move between networks.

Finally, DHCP does not guarantee a device will always receive the same address. Dynamic allocation can return a different address after a lease expires, a client identity changes or network policy changes. If an endpoint needs a predictable address, use a properly planned reservation or a carefully managed static configuration.

14. Frequently asked questions about DHCP

What is DHCP?

DHCP automatically provides devices with network settings such as IP addresses, subnet masks, default gateways and DNS server information.

What does DORA stand for?

DORA means Discover, Offer, Request and Acknowledge—the common four-message sequence for an initial DHCPv4 lease.

How long does a DHCP lease last?

It depends on server policy. A home router or enterprise administrator can choose a lease duration suited to device turnover, pool size and operational needs.

Is a DHCP reservation the same as a static IP?

No. A reservation is managed by the DHCP server and associates an address with a client identity. A static address is configured directly on the device.

Why does my device get a 169.254 address?

Many operating systems use an IPv4 link-local address when normal DHCP configuration is unavailable. Check the link, VLAN, DHCP server, relay and scope capacity.

What ports does DHCP use?

DHCPv4 uses UDP 67 on servers and UDP 68 on clients. DHCPv6 uses UDP 547 for servers and relays and UDP 546 for clients.

Can a DHCP server be on another subnet?

Yes. A DHCP relay agent forwards client messages between the local subnet and a server on another network.

What is a rogue DHCP server?

It is an unauthorised server that responds to clients and may provide incorrect or malicious network settings. DHCP snooping and access-layer controls help mitigate this risk.

Does DHCPv6 replace SLAAC?

Not necessarily. IPv6 networks can use SLAAC, DHCPv6 or both, depending on router advertisements and network policy.

Does DHCP make my internet faster?

No. DHCP provides configuration; it does not increase broadband capacity or radio signal quality. Correct settings can restore connectivity, but speed depends on the access link, network conditions and services.

15. Standards and further reading

  • IETF RFC 2131 — Dynamic Host Configuration Protocol: DHCPv4 operation, message exchange, lease and renewal behaviour.
  • IETF RFC 2132 — DHCP Options and BOOTP Vendor Extensions: standard DHCPv4 configuration options.
  • IETF RFC 9915 — Dynamic Host Configuration Protocol for IPv6: current DHCPv6 specification, including stateful and stateless operation.
  • IETF RFC 3046 — DHCP Relay Agent Information Option: relay-agent information commonly associated with option 82.
  • IETF RFC 8213 — Security of Messages Exchanged between Servers and Relay Agents: security considerations for DHCP relay/server communication.
  • IETF RFC 3927 — Dynamic Configuration of IPv4 Link-Local Addresses: background on IPv4 link-local addressing.
