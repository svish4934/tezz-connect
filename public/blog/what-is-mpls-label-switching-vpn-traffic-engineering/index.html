What Is MPLS? Label Switching, L3VPNs and Traffic Engineering

Learn how Multiprotocol Label Switching forwards packets with labels, how L3VPNs connect business sites, and how providers engineer paths across network backbones.

By Suraj Vishwakarma · Published by TEZZ CONNECT

MPLS, or Multiprotocol Label Switching, is a packet-forwarding architecture used in many service-provider and enterprise networks. It adds labels to packets so routers inside an MPLS domain can forward traffic using label information. This approach supports services such as Layer 3 VPNs, Layer 2 circuits and traffic-engineered paths.

MPLS is often described as a private-network technology, but that description is incomplete. MPLS itself is not a VPN and does not encrypt data. It is a forwarding architecture that providers can use to build logically separated services over shared infrastructure. Understanding the difference helps businesses compare MPLS with internet VPNs, SD-WAN and dedicated connectivity.

1. What is MPLS?

Multiprotocol Label Switching (MPLS) is a way to forward packets through a network using labels. Rather than making every transit router repeat a full IP routing lookup for every packet, an MPLS ingress router classifies a packet into a forwarding equivalence class (FEC) and attaches a label. Routers inside the MPLS domain use that label to select the next hop and the label operation.

The word “multiprotocol” reflects that MPLS can carry different network-layer payloads, including IPv4 and IPv6, and can support services such as Layer 2 circuits and Layer 3 VPNs. MPLS is not a replacement for IP addressing, nor is it simply a faster version of Ethernet switching. It is an architecture that separates traffic classification and path selection from the label-based forwarding performed through the core.

MPLS is widely associated with service-provider backbones, enterprise wide-area networks, carrier Ethernet services and data-centre or inter-provider designs. It is especially useful when a provider needs to carry traffic for many customers over shared infrastructure while maintaining distinct forwarding contexts and offering different service characteristics.

At a high level, an MPLS network has an ingress edge, a label-switched core and an egress edge. The ingress classifies and labels traffic. Core routers forward based on labels. The egress removes the transport label and delivers the packet toward its destination. Actual deployments can include multiple label layers, protection mechanisms and additional control-plane protocols.

2. Why use labels instead of ordinary IP forwarding?

In ordinary IP forwarding, a router examines the destination IP address, performs a longest-prefix match in its forwarding information base and selects a next hop. Every router along the path makes its own forwarding decision using its local routing information. This is flexible and remains the foundation of internet routing.

MPLS introduces a label-based forwarding step. At the ingress, packets that should receive the same forwarding treatment can be assigned to the same FEC. A label represents that forwarding treatment within a particular MPLS context. A downstream router does not need to repeat the original destination-prefix lookup for that labelled packet; it consults its label forwarding information and applies the programmed operation.

This does not mean MPLS removes routing protocols or makes routers blind to IP. Routing protocols still establish reachability and provide the information from which labels and paths are built. The label is a forwarding instruction used within the MPLS domain. The control plane and data plane have different responsibilities: protocols calculate or distribute reachability and labels, while the forwarding plane processes packets at line rate where supported.

Historically, label switching was also attractive because it could support traffic engineering and services across different link technologies. Modern silicon performs IP forwarding very efficiently, so the primary reasons to deploy MPLS today are usually service architecture, VPN separation, traffic engineering, operational consistency and provider requirements—not a universal speed advantage.

3. What is inside an MPLS label?

An MPLS label stack entry is 32 bits. It contains a 20-bit label value, a 3-bit Traffic Class field, a 1-bit Bottom of Stack indicator and an 8-bit Time to Live (TTL) field. The label value identifies the forwarding action in the local context. Traffic Class can be used for class-of-service treatment. The Bottom of Stack bit indicates whether this is the final label in the stack, and TTL helps limit forwarding loops.

Labels are locally significant. A label value used by one router does not have to mean the same thing to another router. The receiving router interprets the label using its own label forwarding information. This local significance allows each hop to replace an incoming label with a different outgoing label while preserving the packet's intended path.

MPLS labels are often described as sitting between Layer 2 and Layer 3. On Ethernet links, the MPLS unicast EtherType identifies the payload as MPLS. The original IP packet remains inside the labelled packet. A stack can contain more than one label: an outer transport label can carry traffic across the provider core, while an inner service or VPN label tells the egress provider-edge router how to deliver the customer packet.

Special-purpose label values are reserved for defined functions. Implementations and standards specify how these are interpreted. Network operators should avoid assuming that a label number is globally meaningful or manually comparing label values across unrelated routers as if they were permanent identifiers.

4. How label switching works: push, swap and pop

Three operations describe the basic handling of an MPLS label stack:

  • Push: add a label to a packet. The ingress router commonly pushes a transport label, and may push a service label as well.
  • Swap: replace the top label with a new outgoing label selected by the next-hop forwarding entry. Core label-switching routers commonly perform this operation.
  • Pop: remove the top label. The egress router removes the transport label before delivering the packet, or a penultimate router may remove it earlier through penultimate-hop popping.

Imagine a customer packet entering a provider network at PE-A and leaving at PE-B. PE-A classifies the packet, selects a VPN route and applies a service label that identifies the destination forwarding context at PE-B. It also applies an outer transport label that carries the packet toward PE-B. Core routers swap the outer label as the packet moves across the backbone. The inner service label can remain unchanged through the core. At the egress, the transport label is removed and the service label is used to select the correct customer-facing forwarding action.

Penultimate-hop popping (PHP) is an optimisation in which the router immediately before the egress removes the outer transport label. The egress then receives the packet with the service label at the top of the stack. This can reduce work at the egress, although explicit-null labels and other design choices can preserve information such as traffic-class treatment or TTL behaviour.

Label stacks are a key reason MPLS can support multiple layers of service. The outer label can represent transport through the provider network; inner labels can represent a VPN, pseudowire or other service context. The stack is interpreted according to the architecture and forwarding state configured by the network.

5. Important MPLS devices: LER, LSR, PE, P and CE

A Label Edge Router (LER) sits at the boundary of an MPLS domain. An ingress LER classifies incoming traffic and imposes labels. An egress LER removes labels and forwards traffic out of the domain. In provider VPN terminology, these edge routers are commonly called Provider Edge (PE) routers.

A Label Switch Router (LSR) forwards labelled packets inside the MPLS domain. It uses the incoming label to identify the outgoing interface and label operation. In an MPLS provider backbone, a core Provider (P) router is typically an LSR. A P router does not normally need to maintain every customer's VPN routing table, which is one of the scalability benefits of the architecture.

A Customer Edge (CE) router belongs to the customer network and connects to the provider's PE router. The CE may exchange ordinary routing information with the PE using static routes, BGP or another supported routing protocol. The customer does not necessarily need to run MPLS on its CE device; many L3VPN services keep MPLS confined to the provider network.

These roles describe responsibilities, not necessarily separate hardware models. A router can perform multiple functions depending on its position and configuration. In a diagram, PE devices are usually at the customer-facing edges, P devices are in the provider core, and CE devices are on the customer side of the service demarcation.

6. What is a Label Switched Path (LSP)?

A Label Switched Path is the sequence of hops through which labelled packets travel from an ingress LSR to an egress LSR for a particular FEC. An LSP is generally unidirectional; return traffic uses a separately established path, even if the route is symmetrical.

The path can follow the normal route selected by the provider's Interior Gateway Protocol (IGP), or it can be explicitly engineered. In an IGP-aligned design, label distribution follows the next-hop topology calculated by OSPF or IS-IS. In a traffic-engineered design, the network can establish a path that meets constraints or follows an operator-selected route.

Operators monitor LSP state, reachability, label bindings, path changes and failure recovery. A label-switched path is not a physical cable and does not guarantee that every link is dedicated to one customer. It is a logical forwarding path across the provider's infrastructure.

When troubleshooting, trace the path from ingress to egress. Confirm that the ingress has classified the traffic correctly, that each hop has the expected label forwarding entry, that the next-hop interface is operational and that the egress has the correct service context. A working IP route alone does not prove that the relevant MPLS service and label state are correct.

7. How does MPLS distribute labels? LDP, RSVP-TE and Segment Routing

MPLS forwarding requires routers to agree on which labels to use for a FEC. Several control-plane approaches exist, and the correct choice depends on the network design.

Label Distribution Protocol (LDP)

LDP distributes label bindings for FECs, commonly using the IGP's next-hop information. It is often used to create label-switched paths that follow ordinary IP routing. LDP is comparatively straightforward for a best-effort MPLS transport design, but by itself it does not provide the same explicit path-control model as RSVP-TE.

RSVP-TE

Resource Reservation Protocol with Traffic Engineering extensions can establish explicitly routed LSPs and signal constraints such as bandwidth reservations or administrative affinities. This can help operators steer traffic away from congested or unsuitable links. RSVP-TE requires additional planning and operational state, and its role varies as networks evolve.

Segment Routing

Segment Routing encodes an ordered set of instructions, called segments, into the packet or associated forwarding state. With the MPLS data plane, segment identifiers are represented as labels. Segment Routing can reduce reliance on a separate per-LSP signalling protocol in some architectures, with information distributed through an IGP or BGP. It can support traffic engineering and fast reroute designs when implemented and engineered correctly.

These approaches should not be collapsed into one interchangeable protocol. LDP, RSVP-TE and Segment Routing have different control-plane models, operational characteristics and feature support. Migration can involve coexistence and interworking phases. Operators should verify platform support, interoperability, protection behaviour and the actual service requirements before changing a production backbone.

8. MPLS Layer 3 VPNs: the service-provider model

An MPLS Layer 3 VPN allows a service provider to connect multiple customer sites across a shared IP/MPLS backbone while keeping each customer's routing information logically separate. The customer sites can communicate as though they were part of a private routed network, even though the provider carries many customers over the same physical infrastructure.

The PE router maintains a Virtual Routing and Forwarding (VRF) instance for each customer routing context. A VRF has its own routing information and forwarding state. Two customers can use overlapping private IPv4 address ranges because their routes are held in separate VRFs rather than being mixed into one global routing table.

PE routers exchange VPN reachability using Multiprotocol BGP (MP-BGP). VPN routes carry additional information that distinguishes otherwise overlapping prefixes and route-target communities that control which VRFs import or export those routes. The PE also advertises a VPN label associated with the route or forwarding context. The provider core transports the labelled packet to the correct egress PE.

A common packet journey is as follows:

  1. A device at Site A sends an IP packet to its local CE router.
  2. The CE forwards the packet to the provider PE connected to Site A.
  3. The PE looks up the destination in the customer's VRF and selects the remote PE and VPN route.
  4. The ingress PE imposes a VPN/service label and a transport label for the path across the provider backbone.
  5. Core P routers forward using the outer transport label without needing the customer's full VPN routes.
  6. The egress PE removes the transport label, uses the VPN label and VRF context to select the customer-facing route, then forwards to the destination CE.

This architecture is described in IETF RFC 4364. It is a routing and forwarding separation model; it does not automatically encrypt the customer's traffic. Confidentiality requirements need a separate security design.

9. Route distinguishers, route targets and VRFs

Three terms are central to understanding MPLS L3VPNs.

VRF: a separate routing and forwarding table on a PE router. It keeps one customer's routes apart from another customer's routes. Interfaces or subinterfaces are associated with a VRF so packets enter the correct routing context.

Route distinguisher (RD): a value that makes a customer IPv4 or IPv6 prefix unique in the VPN address family. If two customers both use 10.0.0.0/24, the RD allows the provider to represent the routes as distinct VPN routes. The RD is not, by itself, a policy saying who should receive the route.

Route target (RT): a BGP extended community used to control VPN route import and export. A PE exports routes with configured route targets. Other VRFs import routes matching their configured targets. This policy determines which customer sites or services can learn one another's routes.

It is important not to confuse an RD with an RT. The RD provides uniqueness in the VPN routing information; the RT controls distribution between VRFs. A route-target mistake can unintentionally connect networks that should remain separate or prevent legitimate sites from communicating. Review import/export policy carefully and test both intended and prohibited reachability.

VRF separation also does not remove the need for security controls. Firewalls, access control lists, route filtering, management-plane protection and customer edge controls may still be required. A private routing context is not equivalent to a cryptographic security boundary against every threat.

10. MPLS Layer 2 VPNs and pseudowires

MPLS can also carry Layer 2 services. In a Layer 2 VPN, a provider can connect customer Ethernet segments or other supported Layer 2 services across its backbone. A pseudowire is a logical point-to-point connection that emulates a service across a packet network.

In a common Ethernet pseudowire design, customer Ethernet frames enter a provider edge device, are encapsulated for transport across the MPLS core and are delivered to the remote PE, which presents the service toward the far-end customer. The provider may use a service label to identify the pseudowire and a transport label to carry traffic across the backbone.

Layer 2 VPNs and L3VPNs solve different problems. A Layer 2 service extends a link-layer service between sites, leaving more routing responsibility with the customer. An L3VPN provides a routed service in which the provider PE participates in exchanging customer routes. The correct choice depends on whether the customer needs transparent Layer 2 adjacency, provider-managed routing, multicast support, segmentation or a specific legacy application.

Extending Layer 2 over long distances can introduce broadcast-domain scale, loop, failure-domain and troubleshooting concerns. A Layer 2 VPN should not be selected simply because it sounds more transparent. Understand the size of the broadcast domain, spanning-tree boundaries, MTU requirements and how failures will be isolated.

11. MPLS traffic engineering and Quality of Service

Traffic engineering is the practice of steering network traffic to use resources in a way that meets operational goals. Ordinary shortest-path routing can send many flows over the same low-cost links even when other paths have spare capacity. Traffic engineering gives the operator tools to use alternate paths, respect constraints and manage congestion.

RSVP-TE can establish paths with explicit routes or bandwidth-related constraints. Segment Routing can express paths as segment lists and can work with a controller or distributed computation, depending on the architecture. These mechanisms can support primary and backup paths, service differentiation and more predictable use of backbone resources.

Quality of Service (QoS) is related but distinct. QoS classifies traffic and applies policies such as queuing, scheduling, shaping, policing and marking. MPLS Traffic Class bits can carry class-of-service information across the MPLS domain. The provider must map and preserve these markings consistently; a label does not magically create bandwidth or guarantee an application's performance.

For voice, video, enterprise applications and critical services, an operator should define measurable service objectives. These may include delay, jitter, packet loss, availability and restoration time. Monitoring must measure the path and service actually used by the traffic. A premium label or queue configuration is not evidence of a service-level guarantee unless the entire end-to-end design supports it.

12. Is MPLS secure? What it does—and does not—protect

MPLS VPNs provide logical separation through VRFs, route distribution policy and label-based forwarding. That can keep one customer's traffic from being routed into another customer's VPN under normal, correctly configured operation. But MPLS labels are not encryption, and the label stack does not conceal the payload from a party able to observe the traffic.

Security depends on provider architecture, configuration, operational controls and the trust model. A misconfigured route target, incorrect interface-to-VRF assignment or provider control-plane compromise can affect separation. Customers should understand the provider's service design, demarcation responsibilities, incident process and available security options.

If data confidentiality is required across an untrusted or shared network, use an appropriate encryption technology such as IPsec between customer gateways or another approved end-to-end security mechanism. Protect routing adjacencies, management interfaces and device credentials. Apply route filters, prefix limits, authentication where supported, logging and change control.

For organisations with regulatory or contractual obligations, evaluate the whole service rather than relying on the label “private network.” Confirm encryption requirements, key management, audit evidence, data residency, availability targets and responsibilities for incident response.

13. MPLS vs internet VPN vs SD-WAN

MPLS, internet VPNs and SD-WAN are often compared as if they were direct substitutes, but they describe different parts of a WAN architecture.

MPLS WAN: commonly delivered by a service provider with a private routed service, defined demarcation and optional service-level commitments. It can be attractive for predictable connectivity and provider-managed operations, but cost, provisioning time and geographic availability can be limitations.

Internet VPN: uses public internet access with encryption, commonly IPsec, to connect sites. It can be cost-effective and widely available, but performance depends on broadband quality, internet routing, congestion and the VPN design. Redundant ISPs and multiple tunnels can improve resilience.

SD-WAN: is an overlay and policy-driven approach for selecting and managing WAN paths. It can use MPLS, broadband, dedicated internet access, LTE/5G or combinations of these. SD-WAN can measure path quality and steer applications according to policy, but it still depends on the quality and availability of the underlying links.

Many enterprises use hybrid designs: MPLS for selected critical sites or applications, broadband for general traffic, mobile connectivity for backup, and SD-WAN to apply consistent policy across them. Compare total cost, application performance, security, failover, operational skills and provider support rather than choosing based on a single technology label.

14. Where MPLS is used

MPLS is used in service-provider backbones that carry traffic for many enterprises, government networks, mobile operators, wholesale carriers and large distributed organisations. It can support L3VPNs between branches, Layer 2 services for legacy connectivity, transport between data centres and engineered paths for traffic with particular performance needs.

Mobile networks may use MPLS in transport and aggregation architectures, depending on operator design and evolution. Enterprise WANs may use provider MPLS services to connect offices, factories, campuses and data centres. Wholesale providers may use MPLS to offer services to other carriers or managed network providers.

Not every network needs MPLS. A small organisation with a few offices may find secure internet VPNs or an SD-WAN service more practical. A cloud-first company may connect to cloud providers using internet-based or dedicated cloud connectivity rather than extending a traditional private WAN to every site. MPLS remains useful where its service model solves a real requirement.

15. Common MPLS troubleshooting steps

Customer site cannot reach a remote site: verify CE-to-PE link state, interface VRF assignment, local route learning, PE VRF route table, MP-BGP VPN route exchange, route-target import/export and the remote CE path. Check that the intended prefix is present in the correct VRF at both ends.

VPN route is visible but traffic is dropped: inspect the VPN label binding, transport LSP reachability, label forwarding entries, MTU, ACLs, firewall policies and egress VRF forwarding. A route can exist in the control plane while a data-plane label or interface problem prevents delivery.

Only large packets fail: investigate path MTU and encapsulation overhead. MPLS labels add bytes to the packet, and additional tunnels or security headers add more. Ensure that links and endpoints support the required MTU and that Path MTU Discovery is not blocked.

Traffic takes an unexpected path: inspect IGP metrics, LDP bindings, RSVP-TE or Segment Routing policies, ECMP behaviour and traffic-engineering constraints. Confirm the active path from the actual ingress router, not just from a network diagram.

One customer can see another customer's routes: treat this as a serious segmentation incident. Check VRF bindings, route-target import/export, route leaking, shared services, route maps and recent configuration changes. Preserve logs and follow the provider's security incident process.

Intermittent loss or delay: correlate interface errors, queue drops, congestion, link flaps, LSP changes, protection events and provider performance measurements. Use probes from the relevant VRF and service path. A generic ping from a router's global table may test a different route than the customer application uses.

16. Planning an MPLS service: questions to ask a provider

Before purchasing or redesigning an MPLS service, document the sites, bandwidth requirements, application priorities, availability targets, growth forecast and security obligations. Ask whether the service is L3VPN, L2VPN or another transport product, and identify the customer and provider responsibilities at each demarcation.

  • Which access technologies and bandwidth options are available at every site?
  • What are the committed information rate, burst policy and upgrade process?
  • What delay, jitter, packet-loss and availability objectives are measured?
  • How are primary and backup paths engineered, and what is the expected restoration time?
  • Which routing protocols, addressing rules and VRF options are supported?
  • How are QoS classes mapped, policed and monitored end to end?
  • Does the service include encryption, or must the customer provide it?
  • What monitoring portal, reports, escalation process and maintenance notifications are available?
  • How are cloud connectivity, internet breakout and remote access handled?
  • What are installation charges, recurring fees, contract terms and exit arrangements?

Request a design diagram and service description. Confirm how failover is tested, whether both access links share a duct or local exchange, and whether the provider can demonstrate route diversity. A backup circuit is not truly independent if it shares the same physical risk as the primary circuit.

17. The future of MPLS: coexistence, automation and network evolution

MPLS continues to coexist with newer approaches rather than disappearing overnight. Segment Routing can simplify parts of traffic engineering and reduce some signalling state. EVPN can provide scalable control-plane learning for Ethernet services across IP or MPLS fabrics. SD-WAN adds application-aware policy across multiple underlay transports. Network automation and telemetry make it easier to provision, validate and monitor services.

Operators often evolve networks incrementally. A backbone may continue to carry MPLS VPNs while introducing Segment Routing in selected regions, using EVPN for particular services or moving some enterprise traffic to internet and SD-WAN platforms. Interworking, migration testing and operational consistency are essential because customer services cannot simply stop during a technology transition.

For customers, the important question is not whether MPLS is old or new. It is whether the service meets measurable business requirements at an acceptable cost and with a support model the organisation can operate. Technology decisions should follow application needs, resilience objectives, security obligations and the provider's real capabilities.

Conclusion: MPLS is a service and forwarding architecture, not a magic speed boost

MPLS classifies packets into forwarding equivalence classes, attaches labels and moves traffic through a label-switched path. Routers can push, swap and pop labels, while LDP, RSVP-TE or Segment Routing provide different ways to establish or distribute forwarding information.

Its most recognised enterprise application is the MPLS Layer 3 VPN. VRFs separate customer routing contexts, MP-BGP distributes VPN routes, route distinguishers make prefixes unique and route targets control which VPN routes are imported. The provider core can forward labelled packets without maintaining every customer's full routing table.

MPLS does not automatically encrypt traffic or guarantee better speed. It is valuable when its service separation, traffic engineering, provider support and operational model meet a real requirement. Compare it with internet VPNs and SD-WAN based on measurable performance, security, resilience and total cost.

Frequently asked questions about MPLS

1. What does MPLS stand for?

MPLS stands for Multiprotocol Label Switching. It is a packet-forwarding architecture in which routers classify traffic into forwarding equivalence classes and use short labels to guide packets through an MPLS domain.

2. Is MPLS a type of VPN?

MPLS is a forwarding technology, not a VPN by itself. Service providers commonly use MPLS as part of Layer 2 and Layer 3 VPN services that keep customer traffic logically separated across a shared backbone.

3. How does an MPLS label work?

An MPLS label is a short, fixed-length identifier carried between the data-link header and the network-layer packet. Each label-switching router uses the incoming label to select an outgoing interface and label operation, such as swap, push or pop.

4. What is the difference between a PE and a P router?

A Provider Edge router connects a customer network to the provider backbone and commonly handles customer routing and VPN context. A Provider router operates inside the provider core and normally forwards transit traffic using transport labels without holding every customer's VPN routes.

5. What is an MPLS L3VPN?

An MPLS Layer 3 VPN is a provider service that uses separate routing contexts, commonly called VRFs, at provider-edge routers. MP-BGP distributes VPN reachability and labels so customer sites can communicate across a shared provider backbone.

6. What is the difference between LDP and RSVP-TE?

LDP distributes labels that follow routes selected by the underlying routing protocol. RSVP-TE can establish explicitly engineered label-switched paths with constraints such as bandwidth or administrative policy, depending on implementation.

7. Does MPLS encrypt data?

No. MPLS labels do not encrypt payloads. VPN separation is based on forwarding and routing isolation, not cryptographic confidentiality. Organisations needing encryption should use IPsec, MACsec or another suitable security layer.

8. Is MPLS faster than normal IP routing?

Not inherently. Modern routers can forward IP and MPLS traffic in hardware. MPLS is valuable for service separation, traffic engineering and operational control; it should not be assumed to make every packet faster.

9. Is MPLS being replaced by SD-WAN?

Not universally. SD-WAN changes how enterprises select and manage WAN paths across services such as broadband, internet, LTE/5G and private circuits. MPLS remains in use where predictable provider-managed connectivity, service levels or legacy integration are valuable.

10. Can small businesses use MPLS?

They can, but availability and cost depend on the provider and location. Smaller organisations should compare MPLS with business broadband, internet VPNs and SD-WAN based on application needs, resilience, security and total cost.
