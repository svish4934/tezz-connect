How Web Push Notifications Work: Service Workers and Push API

A news site can alert you to a breaking story, a delivery service can report a parcel update, and a web application can remind you about an important event even when its page is not open. Web push makes this possible through a browser push service and a background service worker. This guide explains the complete delivery path, user permission, subscriptions, VAPID, encryption, platform limits and responsible implementation.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Why websites send notifications

A traditional website usually communicates while a visitor has the page open. It can update text, show a banner, play a sound or refresh information while its JavaScript is running. But that page may be closed, in another tab, or no longer active when something important happens. If a delivery status changes two hours later, the website cannot rely on its original page still being present.

Push notifications solve a different problem. They allow an application server to ask a browser's push service to deliver a small message to a particular browser subscription. The browser can wake the site's service worker, which handles the push event and may display a notification. The website does not need to keep a normal page open or maintain a permanent JavaScript connection for every subscriber.

Examples include a message alert, a flight gate change, a price movement, a security warning, a calendar reminder or a delivery update. The feature is useful only when the message is timely and wanted. Sending frequent, irrelevant alerts can cause people to block notifications or uninstall an installed web app. A good notification system starts with a clear user benefit and a respectful permission process.

What is web push?

Web push is a standards-based system for delivering messages from an application server to a user agent, usually a web browser. It uses several browser capabilities that work together: the Push API, service workers and the Notifications API. A push service sits between the application server and the browser. It accepts a delivery request from the server and routes the message to the correct browser installation or subscription.

The application server does not normally open a direct inbound connection to the user's phone or laptop. Instead, the browser creates a subscription with a push service and gives the website a subscription object. The website sends that subscription information to its own server. Later, the server sends an encrypted push request to the push service endpoint contained in the subscription.

The W3C Push API specification describes how an application server can send a message to a web application through a push service, including when the application or user agent is inactive. The message is delivered to a service worker associated with the website's origin. The current specification status should be checked when implementing because web platform documents can evolve; browser compatibility remains implementation-specific.

The five main components

1. Website or web application: The page explains why notifications are useful, asks for permission at an appropriate moment and registers the service worker. It also allows the user to manage notification preferences.

2. Service worker: This is a script that the browser can run separately from a page. It can handle events such as push and notification clicks, use supported background capabilities and display a persistent notification through its service worker registration. It is event-driven and may be stopped by the browser when it has no work to do.

3. Push service: This infrastructure accepts a message from the application server and routes it to the browser or device. Browsers may use platform-operated push services. The application server sends requests to the endpoint supplied in the subscription rather than choosing an arbitrary destination.

4. Application server: The website's backend stores subscriptions associated with user preferences, prepares messages, encrypts payloads and sends requests to push service endpoints. It must protect subscription details and authentication keys.

5. Notifications interface: The browser and operating system display the notification according to the device's settings. The user may see it on a lock screen, notification centre or desktop notification area. The website cannot control every part of the visual presentation or guarantee that the operating system will show every message.

How a web push notification travels from server to screen

The delivery flow has several stages. First, the user visits a secure website. The site registers a service worker and explains the value of enabling notifications. After the user makes a deliberate choice and grants permission, the page asks the browser to create a push subscription. The subscription includes an endpoint and cryptographic key material used for message encryption.

The website sends the subscription object to its backend over HTTPS and associates it with the relevant account or anonymous browser installation. The server stores it securely. When an event occurs, the application server selects the subscriptions that should receive the alert, prepares a payload and sends a request to each push endpoint. The request uses the Web Push protocol and normally includes application-server identification through VAPID.

The push service validates the request, accepts or rejects it and attempts delivery to the browser. If the browser is able to receive it, the service worker is started and receives a push event. The worker reads the payload and calls the notification display API. If the user taps the notification, the service worker receives a notification click event and can focus an existing page or open a relevant URL.

Each stage can fail independently. Permission may be denied, a subscription may expire, the push service may return an error, the device may be offline, the payload may be malformed, or the operating system may suppress visible alerts. A robust system records meaningful outcomes and can refresh subscriptions rather than assuming that one successful subscription will work forever.

Service workers: the background event handler

A service worker is a JavaScript file registered by a website and managed by the browser. It has no direct access to the page's DOM and does not behave like a permanently running background process. The browser starts it when an event needs handling and may stop it after the event has completed. This event-driven design helps the platform manage memory, CPU and battery use.

Service workers commonly support offline caching and network request handling, but they are also central to web push. A service worker can listen for the push event, parse the received data and show a persistent notification. It can also handle a notification click and coordinate with open pages using supported client APIs.

Because the browser can terminate a worker between events, do not rely on in-memory variables to preserve long-term application state. Store necessary data using appropriate persistent browser storage or retrieve it from the server when the event occurs. Keep event handlers efficient and complete asynchronous work using the event lifetime mechanisms provided by the service worker platform.

Service workers require a secure context in normal production use. HTTPS is the standard deployment choice, with localhost treated as a secure development origin by browsers. The script's scope determines which pages it controls, so place and register it deliberately. A service worker update can also be subject to browser lifecycle rules; test changes and activation behaviour rather than assuming that every visitor immediately runs the newest file.

Permission: why timing and user choice matter

Notification permission is a sensitive browser decision. A site should not immediately trigger a permission prompt the moment a visitor lands on the homepage. The user may not understand why the site wants to send alerts, and an unexpected prompt can lead to denial. Some browsers make it difficult or impossible for a site to ask again after a user blocks the request.

A better pattern is to explain a concrete benefit first. For example, a delivery website can offer a button labelled “Get delivery updates” after the user tracks a parcel. A news site can explain that alerts are available for selected topics. Only after the user chooses to continue should the page request browser permission. The request should be tied to a clear interaction, not disguised as an unrelated control.

Permission can be granted, denied or left in a default state. Users can change notification settings in their browser or operating system. A website must respect those choices and should offer an in-product way to unsubscribe or manage categories. If permission is denied, the site should continue to work without push and provide another way to see important information.

Do not confuse permission to display notifications with consent to every type of marketing. The application should explain the categories, frequency and purpose of alerts, and follow applicable privacy and consumer-protection rules. A user who agrees to an order update has not necessarily agreed to promotional campaigns.

Push subscriptions and endpoint management

A push subscription represents the browser's relationship with a push service for a particular website and browser context. It contains an endpoint URL and cryptographic material used to protect push messages. The application server needs this information to address future messages and encrypt their payloads.

The endpoint is not an ordinary public URL to place in page markup or analytics logs. It acts like a capability: someone who obtains it may be able to attempt delivery to that subscription, subject to the protocol's protections and application-server authentication. Treat the subscription endpoint and its keys as sensitive data. Store them server-side, restrict access, avoid logging complete values and delete them when the user unsubscribes or the subscription becomes invalid.

Subscriptions can change. Browsers or push services may rotate endpoints, remove old subscriptions or report that a subscription is no longer valid. The website should handle subscription changes, update the backend record and remove stale endpoints when delivery attempts return an appropriate permanent error. Do not keep retrying a subscription indefinitely after the push service says it is gone.

Associate subscriptions with the correct account and device context. One user may have several browsers or devices, while a shared computer may have multiple users. Provide a way to view or revoke active notification subscriptions where appropriate. Account logout should not accidentally leave a sensitive account's alerts connected to a shared browser profile without a clear user choice.

VAPID: identifying the application server

Voluntary Application Server Identification, or VAPID, is a standard method for an application server to identify itself to a push service. The server maintains an elliptic-curve key pair and signs a JSON Web Token for requests to the push service. The token includes information such as the push service origin and an expiry. The public key is provided when the subscription is created, and the private key is used by the application server when sending messages.

VAPID helps a push service associate requests with an application server identity and can restrict a subscription to the server that supplied the corresponding public key. It is not the same as end-user authentication. A valid VAPID token says something about the sending application server; it does not prove that the person who owns the browser account requested a particular message.

Keep the VAPID private key secret and protect it like any other server credential. Do not embed it in frontend JavaScript or commit it to a public repository. The public application-server key is designed to be shared with the browser during subscription creation. If the private key is compromised or rotated, subscription management may need a coordinated migration depending on how subscriptions were restricted.

The details are specified in IETF RFC 8292. The underlying Web Push protocol is described in RFC 8030.

Payload encryption and privacy

Push messages can pass through infrastructure operated by a browser vendor or another push service. Transport security protects the connection to that service, but transport encryption alone would not prevent the push service from reading the message body. Web Push therefore defines payload encryption so that the application server encrypts the content for the browser subscription. The service can route the encrypted payload without normally seeing its plaintext.

The encryption scheme is described in IETF RFC 8291. Applications should use maintained libraries that implement the protocol correctly rather than inventing their own cryptographic format. Key material and subscription records must be handled securely on both sides.

Encryption does not remove every privacy risk. The push service may still observe metadata such as delivery timing, request size and endpoint information. The operating system may display the notification text on a lock screen where nearby people can see it. Avoid including account numbers, private message contents, health details, authentication codes or other sensitive information in visible notification text unless there is a clear, carefully assessed need.

For sensitive workflows, send a generic alert such as “You have a new account update” and require the user to open the authenticated website or application to view the details. Keep payloads small, minimise identifiers and define retention limits for stored subscriptions and delivery logs.

Delivery timing, offline devices and expiration

Push is asynchronous. The application server asks a push service to deliver a message, but it does not control exactly when the browser or operating system will display it. A phone may be offline, asleep, in a battery-saving mode or subject to background restrictions. The push service may hold a message temporarily according to its supported time-to-live rules, but a message can expire before the device reconnects.

Use an expiry that matches the meaning of the message. A one-time offer may become irrelevant quickly. A security alert may need a different strategy from a live sports score. A stale notification can confuse a user if it arrives after the event has ended. For critical information, do not treat push delivery as the only record or proof that the user received the message.

Design the destination page to show current server state when opened. A notification is a prompt to check information, not necessarily the authoritative source. If an order has already been delivered, the order page should show that latest state even if an earlier “out for delivery” alert is tapped later.

Do not assume that push guarantees delivery, ordering or exactly-once display. Your application should tolerate delayed, duplicated, dropped or superseded notifications. Where multiple events happen quickly, coalesce them into a single current-state alert or send a summary rather than overwhelming the user with a queue of outdated messages.

Persistent notifications and notification clicks

The Notifications API can display notifications from a service worker using the service worker registration's notification method. These are persistent notifications: they can remain visible and interactive beyond the lifetime of a particular page. This is important for mobile web applications, where the page may not be open when the notification arrives.

A notification can include a title, body, icon, badge, tag and other supported options. Browser and operating-system support varies, and the platform may alter how the notification is rendered. Use concise text and a meaningful destination. Avoid using a notification as a substitute for a complete application screen.

When the user taps the notification, the service worker receives a click event. The worker can examine the notification data and focus an existing controlled window or open a new page. Validate any destination and data carried in the notification; do not let untrusted payload values become arbitrary navigation targets or script content.

Notification tags can help replace an earlier notification with a newer one, such as a current delivery status. This is useful for avoiding a stack of alerts about the same object. However, tags and display behaviour can differ across platforms, so test on the browsers and operating systems that matter to your audience.

Browser and operating-system differences

Web push is not identical on every browser or device. Support depends on browser engine, operating system, installation mode and platform integration. Some environments require a site to be installed as a web app before push is available; others support push directly from a browser tab. Permission prompts and notification presentation also differ.

Apple documents web push for web apps on supported Apple platforms and describes the need to request permission, register a service worker, create a subscription and use a VAPID key. Its documentation also notes platform-specific requirements, including how notifications should be handled when received. Developers should test the actual supported operating systems rather than assuming desktop browser behaviour maps directly to every phone.

Feature-detect the APIs before showing an enable-notifications control. Check for service worker support, PushManager and Notification availability, and verify permission state. If the required APIs are unavailable, explain the limitation and keep the website's normal functionality intact. Provide email, in-app or account-page alternatives for important updates.

Web push versus polling, WebSockets and native app push

Polling: A page periodically asks a server whether anything has changed. It is easy to implement but requires the page or app to remain active and creates repeated requests. It is suitable for simple dashboards where a small delay is acceptable.

WebSockets: A persistent two-way connection lets a running page exchange messages with a server. It is useful for interactive sessions, live chat and collaborative tools while the page is connected. It is not a replacement for background push when the page is closed or the browser has suspended the application.

Web push: A push service can deliver a message to a service worker even when the page is not currently open, subject to platform support and permission. It is designed for asynchronous notifications, not continuous high-frequency data streaming.

Native application push: Installed native applications commonly use platform push services such as Apple Push Notification service or Firebase Cloud Messaging integrations. Web push uses browser standards and browser/platform push infrastructure, but the underlying delivery constraints and user settings remain similar: delivery is not a guaranteed real-time channel.

Many products combine approaches. A collaboration app may use WebSockets while open and web push for important events when closed. A news site may use push for selected breaking stories and ordinary HTTP to load the full article. Select the channel based on message urgency, frequency, interaction and user expectations.

Security and abuse prevention

Notification permission should never be obtained through deceptive prompts or dark patterns. The application should clearly identify the sender, explain what messages will be sent and provide a simple way to stop them. Do not use notifications to impersonate system warnings, browser security messages or unrelated organisations.

Protect subscription endpoints and VAPID private keys. Require authenticated access to subscription-management endpoints and verify that a subscription belongs to the account attempting to register or remove it. Apply rate limits to subscription creation and message sending. Validate payload length and structure, and ensure that notification click destinations are restricted to trusted application routes.

Prevent cross-account delivery by checking ownership when selecting recipients. When a user signs out, decide whether the subscription remains associated with the browser or should be removed from the account. For shared devices, make this behaviour explicit. Avoid sending confidential content in the visible title or body, and minimise stored delivery metadata.

Monitor unusual sending volume, repeated failed delivery attempts and spikes in subscription creation. A compromised application server could send unwanted messages at scale. Protect administrative tools, rotate credentials carefully and maintain an incident response plan that can disable a sender or revoke affected subscriptions.

Common implementation problems and troubleshooting

Permission prompt does not appear: Check whether the page is served from a secure context, whether the browser supports notifications, whether permission is already denied, and whether the request follows a user gesture. Do not repeatedly trigger prompts when the browser has blocked them.

Service worker registration fails: Check the script URL, scope, MIME type, JavaScript syntax and HTTPS configuration. A worker may be controlled by a different scope than expected. Inspect the browser's application or service-worker developer tools for registration and update errors.

Subscription creation fails: Confirm that PushManager is available, permission is granted and the VAPID public key is correctly encoded for the browser API. Ensure the subscription is stored by the backend and that server-side code can parse the endpoint and key material.

Push service rejects a send request: Inspect the HTTP response status and provider response body. A gone or invalid subscription should be removed. Authentication failures may indicate an incorrect VAPID key, audience or token expiry. Payload encryption errors may indicate mismatched or corrupted subscription keys.

Push arrives but no notification appears: Check that the service worker handles the push event and awaits the notification display operation. Review operating-system notification settings, focus modes, browser permissions and platform-specific requirements. Some platforms expect a visible notification to be shown promptly after a push event.

Notification opens the wrong page: Validate the click handler's URL logic, ensure the notification data is associated with the correct event and avoid trusting arbitrary external URLs supplied by a message payload.

Designing a responsible notification strategy

Before implementing the protocol, decide which events deserve a push message. A useful alert is timely, actionable and expected. A security event, delivery update or appointment reminder may justify a notification. A minor content change, routine marketing message or repeated background update may not.

Let users choose categories and frequency. Provide quiet hours where appropriate, group repeated events and collapse old status notifications. Make notification text understandable without exposing private details. When a user disables a category, stop sending that category rather than continuing until a browser permission is revoked.

Measure quality as well as delivery. Track opt-in and unsubscribe rates, notification click-through, complaints, duplicate alerts and stale-message incidents. Do not optimise only for clicks: a system that sends too many messages may temporarily increase activity while damaging long-term trust.

Finally, treat push as a convenience channel rather than the source of truth. The website or application should always show the current state after a user opens it. Critical information should also be available through the user's account, email or another appropriate channel when required.

Frequently asked questions

1. What are web push notifications?

Web push notifications are messages an application server sends through a push service to a browser or device. The browser delivers the event to the website's service worker, which can display a notification even when the page is not open.

2. Can a website send notifications when it is closed?

Yes, where the browser and operating system support web push and the user has granted permission. A service worker can receive a push event without the website page being open, although delivery and background execution are subject to platform rules.

3. What is the difference between a push notification and an in-page notification?

An in-page message is displayed by a website while its page is running. A push notification is delivered through a browser or operating-system push service and can reach the user when the site is not actively open.

4. Do web push notifications require a service worker?

The browser Push API delivers push events to a service worker, which handles the event and can display a persistent notification. A service worker is therefore a core part of standard web push on supported browsers.

5. Does a user have to give permission?

Yes. Websites must request notification permission and users can allow, deny or later change that permission. The request should follow a clear explanation and a deliberate user action.

6. What is VAPID in web push?

VAPID is a standard method for an application server to identify itself to a push service using a signed token and an application server key pair.

7. Are web push message contents encrypted?

The Web Push message encryption scheme protects the payload so that the push service cannot normally read its contents. Applications should still minimise sensitive information in notifications because the displayed text may be visible on a lock screen.

8. Will web push work if a phone is offline?

A push service may queue a message for later delivery within its supported time-to-live and platform limits, but delivery is not guaranteed. Expired messages, disabled permissions, battery policies and connectivity can prevent or delay delivery.

9. Can users unsubscribe from web push?

Yes. A website should provide an unsubscribe control, remove or deactivate the stored subscription on its server and respect browser or operating-system permission changes.

10. Are web push notifications supported on every browser?

No. Support and installation requirements vary by browser, operating system and device. Developers should feature-detect the relevant APIs, explain limitations and provide a non-push alternative.
