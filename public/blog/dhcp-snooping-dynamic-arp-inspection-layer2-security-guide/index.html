DHCP Snooping and Dynamic ARP Inspection: Protecting a Layer 2 Network

A practical guide to stopping unauthorised DHCP responses and reducing ARP spoofing risk at the switching edge—without confusing the two controls or overlooking the operational details.

By Suraj Vishwakarma · TEZZ CONNECT · 27 November 2026

Switches do more than forward Ethernet frames. In a managed network, they can also enforce rules about which devices are allowed to provide network configuration and which address claims should be trusted. DHCP snooping and Dynamic ARP Inspection are two important first-hop security controls. This guide explains their roles, how they work together, where they can fail, and how to deploy them safely.

Quick answer: DHCP snooping limits unauthorised DHCP server traffic and builds IP-to-MAC attachment bindings. Dynamic ARP Inspection uses trusted bindings or ARP ACLs to validate ARP messages. They are complementary controls, not interchangeable features.

Why Layer 2 networks need these controls

An Ethernet LAN is designed to let devices discover one another and exchange frames with very little manual configuration. That convenience also creates a trust problem. A workstation, printer, access point, or small unmanaged switch may be connected to an access port, but the network cannot assume every device behaves correctly. A misconfigured laptop can run a DHCP server. A compromised endpoint can send forged ARP messages. A visitor may connect equipment that changes how other clients configure their network paths.

Two switch security features address different parts of this problem. DHCP snooping examines DHCP messages as they cross a switch and builds a record of legitimate address assignments. Dynamic ARP Inspection (DAI) checks ARP messages against trusted IP-to-MAC information, commonly the DHCP snooping binding database. Used together, they make it harder for an unauthorised device to hand out network settings or poison neighbouring devices' ARP caches.

These controls are not a substitute for endpoint security, segmentation, access control, or monitoring. They are enforcement points inside the local switching infrastructure. Their value comes from placing validation close to the access port where an untrusted device enters the network.

The two attacks in plain language

A rogue DHCP server responds to client broadcasts with its own offer. It may provide an incorrect default gateway, DNS resolver, subnet mask, or lease. A victim can then send traffic through an attacker-controlled device or lose connectivity. The attack can be accidental: a consumer router connected to a corporate wall port with its DHCP service still enabled can cause the same symptoms as a malicious server.

ARP spoofing abuses the way IPv4 hosts map local IP addresses to Ethernet MAC addresses. ARP has no built-in cryptographic authentication. A host may accept an ARP reply claiming that the gateway's IP address belongs to another MAC address. If the false mapping is installed, traffic intended for the gateway may be sent to the attacker. The attacker may relay traffic, inspect unencrypted data, modify traffic, or simply disrupt connectivity.

The attacks are related but not identical. DHCP snooping controls selected DHCP messages and records address assignments. DAI validates ARP packets. Blocking rogue DHCP does not automatically stop forged ARP. DAI without reliable bindings may lack the information needed to decide whether an ARP claim is legitimate.

How DHCP snooping works

A snooping-capable switch observes DHCP client and server messages on configured VLANs. It classifies interfaces as trusted or untrusted for DHCP purposes. Client-facing access ports are normally untrusted. Ports leading toward an authorised DHCP server, DHCP relay, or upstream switching infrastructure may need to be trusted according to the actual topology and vendor implementation.

The switch permits expected client-originated DHCP messages from untrusted interfaces, while restricting server-originated messages such as DHCPOFFER, DHCPACK, and DHCPNAK when they arrive from an untrusted edge. This prevents an ordinary client port from acting as an authorised DHCP-server path. The precise message handling and exceptions vary by platform.

As clients complete DHCP exchanges, the switch can create binding records. A typical record includes the assigned IP address, client MAC address, VLAN, switch interface, lease duration, and sometimes additional context. This database becomes a local source of evidence about which endpoint received which address on which attachment.

Think of the switch as maintaining a ledger: this address was leased to this hardware identity on this VLAN and this port for a defined period. DAI and IP Source Guard can consume that ledger for additional checks.

DHCP message flow and trust boundaries

A simplified DHCPv4 exchange is Discover, Offer, Request, and Acknowledgement. A client broadcasts DHCPDISCOVER. An authorised server or relay path returns DHCPOFFER. The client selects an offer and broadcasts DHCPREQUEST. The server confirms the lease with DHCPACK. The switch observes these packets and uses interface trust to decide which direction is allowed to provide server responses.

The important design question is not simply whether a port is an uplink. It is whether the devices reachable through that port are trusted to originate DHCP server-side traffic. A port connected to a router, relay, distribution switch, or virtualisation host may carry legitimate DHCP server responses, but it may also aggregate untrusted devices. Trusting an entire trunk without understanding what sits behind it can create a bypass.

In a multi-switch access network, the binding database must be available where dependent checks are performed. Each switch only sees traffic that traverses it. A binding learned on one switch does not automatically appear on every other switch unless the platform or network design provides a mechanism to distribute or synchronise that information. Validate the behaviour across access, distribution, and aggregation layers before enabling enforcement widely.

Trusted and untrusted ports: a topology decision

A common campus design has endpoint ports configured as untrusted and the uplink toward the authorised DHCP infrastructure configured as trusted. That is a useful starting model, not a universal command recipe. If an access switch uplink leads to another switch that inserts DHCP relay information, the receiving switch may need specific Option 82 handling. If a server is directly attached to an access switch, its port may be trusted. If multiple legitimate DHCP paths exist, each must be mapped.

Never mark all ports trusted to make DHCP problems disappear. That removes the control at the exact boundary where it is needed. Equally, do not blindly mark every trunk untrusted: legitimate server replies may be discarded, and relay-agent behaviour may be affected. Document the expected DHCP path for each VLAN and test the full DORA exchange from a representative endpoint.

Trust is a security policy, not a synonym for physical reliability. A cable can be stable and still lead to an untrusted device. A port can be operationally important and still require validation. Use the narrowest trust boundary that matches the topology.

What the binding database does—and does not—prove

A DHCP snooping binding is evidence that the switch observed an address assignment under its configured rules. It is not proof of a person's identity, a device's health, or the absence of compromise. A device may use a manually configured static IP address and therefore have no DHCP-learned entry. A lease may expire, move, or be renewed. A switch reboot or database persistence issue may remove useful state.

Some platforms support saving the binding database to persistent storage or an external agent so entries can be restored after a restart. That behaviour is vendor- and model-specific. Confirm whether bindings survive reloads, how lease timers are handled, and whether the device clock is accurate. A stale database can be as disruptive as a missing one.

Static-address endpoints require deliberate handling. Depending on the switch, DAI may use ARP access control lists or another static binding mechanism for hosts that do not use DHCP. Printers, servers, infrastructure appliances, hypervisors, and network management interfaces often need special consideration. Do not disable validation globally just because a few static devices are present; define and review explicit exceptions.

Dynamic ARP Inspection: validating address claims

DAI examines ARP requests and replies received on untrusted interfaces in VLANs where the feature is enabled. It compares the IP-to-MAC information in the ARP packet with trusted information, commonly DHCP snooping bindings. If the packet does not match an allowed binding or configured ARP ACL, the switch can drop it and optionally log the event.

For example, suppose a client received 192.0.2.25 with MAC address 00:11:22:33:44:55 on VLAN 20. A later ARP packet arriving on that client port claims that 192.0.2.1, the gateway, belongs to the client's MAC address. That claim does not match the client's learned binding and should be rejected by a correctly configured DAI policy. The exact checks available depend on the platform and optional validation settings.

DAI is generally an ingress control: it evaluates ARP packets as they enter the switch on configured interfaces. It does not magically clean every ARP cache in the wider network, and it cannot protect hosts attached to switches or segments where equivalent checks are absent. Its protection boundary is the portion of the Layer 2 domain where enforcement is actually active.

ARP ACLs and static-address networks

DHCP snooping is a convenient source of dynamic bindings, but not every endpoint uses DHCP. Some servers, printers, network appliances, and industrial devices use manually assigned addresses. A DAI deployment must account for these systems. Many switch platforms provide ARP ACLs or static IP-to-MAC bindings so administrators can define valid ARP claims without relying on a DHCP lease.

An ARP ACL is not the same as an ordinary IP access list. It describes permitted ARP address relationships for a VLAN or platform-specific scope. The ordering and precedence between ARP ACL entries and snooping database entries varies by implementation and must be checked in the relevant vendor documentation. A rule that is too broad can weaken protection; a rule that is too narrow can interrupt legitimate devices.

Inventory static endpoints before enforcement. Record their IP address, MAC address, VLAN, physical or logical attachment, owner, and business purpose. Where devices are replaced, moved, or readdressed, update the authoritative record and test the change. Avoid permanent exceptions that no one remembers.

Option 82 and DHCP relay considerations

DHCP Option 82, commonly called the Relay Agent Information option, allows a relay agent or network device to add information about where a client request entered the network. Sub-options can identify a circuit or remote endpoint. Service providers and large campus networks may use this information for policy, subscriber identification, or address allocation.

When snooping is deployed across multiple switching layers, Option 82 handling becomes a design issue. An access switch may insert relay-agent information; an aggregation switch may receive the packet on a port that is not trusted. Some implementations drop such packets by default unless a specific, carefully scoped setting permits them. Other platforms have different behaviours. Do not enable an allow-untrusted exception without understanding which device inserts the information and which downstream devices consume it.

Document whether the DHCP relay, access switch, or another device inserts Option 82. Check whether the DHCP server echoes or processes the option as expected. Test client leases across every path, including failover and redundant uplinks. A configuration that works on one access switch may fail when a client is moved to another building or VLAN.

Rate limits, validation and logging

DHCP snooping implementations may support per-port rate limits for DHCP packets. These can reduce abuse from a device flooding DHCP messages, but an overly low threshold may affect legitimate clients during mass reconnects, phone restarts, wireless access-point recovery, or a classroom full of devices powering on together. Establish realistic limits from observed traffic and vendor guidance rather than copying a number from an unrelated switch model.

DAI implementations may also rate-limit ARP packets on untrusted ports. ARP bursts can occur during host startup, network recovery, virtual-machine movement, or large Layer 2 events. If a platform disables or blocks a port after a threshold is exceeded, the operational impact can be significant. Monitor counters and understand recovery behaviour before applying aggressive thresholds.

Logging should answer useful questions: which VLAN, interface, source IP, source MAC, destination IP, destination MAC, and validation rule caused a drop? Centralise relevant logs where possible, synchronise device clocks, and alert on repeated violations. A single invalid packet may be a typo or stale endpoint; repeated spoofing patterns or a rogue DHCP server appearing on an edge port deserve investigation.

Relationship with IP Source Guard and port security

DHCP snooping, DAI, and IP Source Guard are related first-hop security controls, but they inspect different traffic. DHCP snooping observes DHCP exchanges and builds bindings. DAI validates ARP claims. IP Source Guard can use binding information to restrict IP source addresses on an interface. Port security limits or controls MAC addresses learned on a switch port. 802.1X authenticates a user or device before granting network access, while network access control can apply broader identity and posture policy.

Together, these features can reduce address spoofing and unauthorised network services at the edge. They do not replace segmentation or encryption. An attacker who compromises a trusted infrastructure device, abuses a permitted endpoint, or operates outside the enforced VLAN may still cause harm. Treat the controls as layers in a defence-in-depth design.

Before enabling multiple controls simultaneously, understand their dependencies. If DHCP snooping does not learn a valid binding, DAI and IP Source Guard may reject traffic from the same endpoint. Deploy in stages, validate the binding database, and keep a tested rollback procedure.

A safe deployment sequence

Start with a topology and endpoint inventory. Identify VLANs, DHCP servers, relay agents, switch uplinks, trunks, wireless controllers, voice devices, static-IP endpoints, hypervisors, and any port that aggregates downstream switches. Confirm which switch sees each client DHCP exchange and where DAI will be enforced.

Next, enable DHCP snooping on a small pilot VLAN or a limited set of access switches. Configure the correct trusted server-facing paths and leave endpoint-facing ports untrusted. Observe DHCP transactions and inspect the binding table. Test new leases, renewals, releases, reboots, relay paths, and failover. Confirm that legitimate DHCP responses reach clients and rogue server responses from an untrusted test port are blocked in a controlled lab.

Then enable DAI in a low-risk pilot scope. Check whether legitimate ARP packets match the database. Add explicit exceptions for approved static endpoints using the vendor-supported method. Expand VLAN by VLAN only after reviewing logs and confirming there are no unexplained drops.

Finally, consider IP Source Guard and related controls. Record the configuration, trusted-port rationale, exception owners, monitoring thresholds, and rollback steps. Review the design whenever a switch, relay, VLAN, DHCP server, or endpoint addressing model changes.

Troubleshooting common failures

If clients cannot obtain an address after snooping is enabled, check whether snooping is active on the client VLAN, whether the DHCP server or relay path is correctly trusted, and whether Option 82 is being inserted or rejected unexpectedly. Inspect DHCP snooping statistics and logs. Verify that the client-facing port is not accidentally trusted or rate-limited too aggressively. Confirm that the server's offer and acknowledgement traverse the expected path.

If a client gets a lease but cannot communicate after DAI is enabled, inspect the binding database and compare the client's actual IP, MAC, VLAN, and switch port. Look for a static IP address, stale lease, missing binding after a switch reload, asymmetric Layer 2 path, or a binding learned on a different switch. Check ARP drop counters and logs before changing policy.

If a port becomes err-disabled or blocked, identify the exact feature and threshold responsible. Do not repeatedly bounce the interface without understanding the cause. A rogue DHCP flood, ARP burst, or incorrect rate threshold may recur immediately. Use a controlled recovery procedure, correct the source or threshold, and confirm the port's security state after restoration.

If only devices behind one downstream switch fail, investigate trust boundaries and binding visibility across the switch chain. If only static devices fail, add narrowly scoped static ARP policy. If failures occur after a maintenance window, verify binding persistence, time synchronisation, configuration changes, and DHCP server reachability.

Limitations and security boundaries

These controls are not universal anti-spoofing solutions. DHCP snooping focuses on DHCP traffic that crosses participating switches and configured VLANs. It cannot stop a rogue DHCP server on a segment that bypasses enforcement. DAI protects ARP traffic only where it is enabled and only to the extent that its trusted database or ACLs correctly represent legitimate endpoints.

A trusted port is a high-impact exception. If an attacker can connect to or compromise a device behind a trusted interface, the switch may accept traffic that would be checked on an untrusted access port. Keep trusted paths short, documented, physically protected, and monitored. Where an uplink carries many downstream endpoints, consider the implications of trusting the whole aggregate.

Static addressing, IPv6, wireless bridging, virtualisation, high availability, and service-provider relay designs require platform-specific review. IPv4 DAI is not a substitute for IPv6 Neighbor Discovery protections. IPv6 networks need appropriate controls for Router Advertisements, Neighbor Discovery, DHCPv6, and source address validation. RFC 7513 describes an IETF SAVI approach for binding DHCP-assigned addresses to attachment points; it is related to the broader source-validation problem, but it is not a vendor-neutral command guide for every switch feature.

Most importantly, a switch cannot infer business intent from packets alone. Maintain accurate inventory, access policy, segmentation, patching, endpoint protection, and incident response alongside first-hop controls.

What administrators should measure

Useful operational measures include the number of active bindings per VLAN, binding age and persistence, DHCP snooping drops by reason, DAI drops by reason, ARP rate-limit events, ports entering a disabled state, and the count of approved static exceptions. Track changes over time rather than treating a zero counter as proof of security. A feature may be enabled on the wrong VLAN or bypassed by a trusted path.

During a pilot, compare baseline and post-change DHCP success rates, time to obtain a lease, endpoint onboarding failures, and help-desk incidents. For DAI, monitor false positives as well as blocked invalid ARP packets. A large increase in drops after enabling the feature may indicate an attack, but it may also reveal stale bindings or an incorrect trust model.

Review exceptions periodically. Every static ARP ACL, trusted port, special Option 82 setting, and rate-limit override should have an owner and a reason. Remove exceptions when devices are retired or moved. Treat the binding database and switch configuration as operational security data that must be backed up and reviewed.

Conclusion: build trust from the access edge

DHCP snooping and Dynamic ARP Inspection solve complementary problems in an Ethernet LAN. Snooping restricts which interfaces can provide DHCP server responses and records the assignments it observes. DAI uses trusted address information to evaluate ARP messages and reduce the risk of address-cache poisoning. Together, they provide a practical foundation for first-hop security.

The quality of the result depends less on enabling a checkbox than on understanding the network. Map the real DHCP path, choose trusted ports narrowly, account for static devices and Option 82, preserve binding state where supported, and monitor drops before expanding enforcement. Apply the controls to every relevant switching path, not just the easiest access switch.

A careful staged deployment can make the LAN more resistant to accidental misconfiguration and common local attacks without disrupting legitimate users. A rushed deployment can block printers, phones, servers, wireless clients, or entire VLANs. Treat validation, testing, documentation, and rollback as part of the security feature itself.

Practical deployment checklist

  • Map DHCP servers, relays, VLANs, trunks, access ports, and downstream switches.
  • Mark only legitimate DHCP server-side paths as trusted; keep endpoint ports untrusted.
  • Enable snooping on the intended VLANs and verify bindings before enforcing dependent controls.
  • Test Option 82 behaviour and relay paths across every switching layer.
  • Inventory static-IP devices and create narrowly scoped ARP exceptions where required.
  • Enable DAI in a pilot VLAN, inspect drops, and expand gradually.
  • Review rate limits, logging, database persistence, clock synchronisation, and recovery procedures.
  • Document trusted ports and exceptions with owners, reasons, and review dates.

Frequently asked questions

What is DHCP snooping?

DHCP snooping is a Layer 2 switch security feature that inspects DHCP messages, restricts server-side responses on untrusted interfaces, and can build a database of IP-to-MAC-VLAN-port bindings.

What is a rogue DHCP server?

A rogue DHCP server is an unauthorised device that offers network configuration to clients. It may provide a malicious or incorrect gateway, DNS resolver, subnet mask, or lease.

What is Dynamic ARP Inspection (DAI)?

DAI is a switch security feature that checks ARP packets on configured untrusted interfaces against trusted IP-to-MAC information, commonly DHCP snooping bindings or configured ARP ACLs.

Does DHCP snooping prevent ARP spoofing?

No. DHCP snooping restricts DHCP server responses and creates bindings. DAI is the separate control that uses trusted bindings to validate ARP packets.

Does DAI require DHCP snooping?

Many common deployments use the DHCP snooping binding database as DAI's source of IP-to-MAC information. Static-address or non-DHCP environments may require ARP ACLs or another vendor-supported binding method.

Which switch ports should be trusted?

Only interfaces that legitimately carry DHCP server or relay-side responses should be trusted, based on the topology and vendor implementation. Client-facing ports are normally untrusted.

Can DAI block devices with static IP addresses?

It can if no matching trusted binding or exception exists. Administrators should inventory static endpoints and configure narrow ARP ACLs or static bindings supported by the switch.

What is DHCP Option 82?

Option 82 is relay-agent information that can identify the circuit or remote endpoint through which a DHCP request entered the network. Its handling must be planned across switching and relay layers.

Is DAI enough to secure an entire network?

No. DAI protects ARP only on participating switches and VLANs. It should be combined with segmentation, access control, endpoint security, monitoring, and appropriate IPv6 protections.

What should I check if clients lose connectivity after enabling DAI?

Check the snooping binding table, client IP and MAC, VLAN and port, static addressing, trusted paths, stale entries, ARP drop logs, and whether the same Layer 2 path is visible to the enforcing switch.
