What Is a Web Application Firewall (WAF)? How It Works

A practical guide to the security layer that examines web requests before they reach a website or API. Learn how WAF rules work, what they can detect, where they fall short, and how to tune protection without blocking real visitors.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Why websites need protection at the application layer

A website is more than a collection of pages. It accepts requests, reads parameters, authenticates users, searches databases, processes uploads, calls APIs and returns information. Every public endpoint creates an interaction between an outside client and application code. Some requests are ordinary: a visitor opens a page, signs in, searches a catalogue or submits a contact form. Others are crafted to exploit weaknesses, consume resources, probe software versions or automate actions at a scale that normal users would never produce.

Network firewalls remain essential, but a rule that allows HTTPS traffic to a web server cannot tell whether a particular URL parameter contains a suspicious database expression or whether a request body resembles an exploit attempt. That is the gap a web application firewall is designed to help address. A WAF examines web traffic at the application layer and applies policies to HTTP requests and, depending on the product, responses. It can allow, log, challenge, rate-limit or block traffic according to configured rules.

A WAF is not a magic shield and cannot make insecure software secure. Its value comes from adding a layer of inspection and enforcement in front of the application, where common attack patterns and abusive request behaviour can be identified before they consume application resources or reach vulnerable code.

What is a Web Application Firewall?

A Web Application Firewall (WAF) is a security control that monitors and filters HTTP traffic exchanged between clients and a web application. It may run at a cloud edge, in a reverse proxy, in a hosting platform, inside a data centre or as software alongside an application. The exact architecture differs, but the central idea is consistent: requests pass through a policy enforcement point before reaching the protected origin.

Unlike a basic packet filter, a WAF can understand web-specific elements such as the request method, host name, URL path, query string, headers, cookies and—in products that support it—the body of a request. It can compare those elements with signatures, behavioural signals, protocol rules and custom conditions. For example, a policy might detect a request containing a known SQL injection pattern, challenge suspicious automation on a login endpoint or limit repeated requests to an expensive search API.

WAF products vary widely. Some focus on signature-based detection, some add bot intelligence and behavioural analysis, and others combine application security with DDoS mitigation, API discovery or client-side protections. A product's label alone does not tell you which capabilities are included in a particular plan. Read the current feature and limits documentation before designing a policy around a feature that may not be available to your deployment.

How a WAF fits into a website request

Imagine a visitor opening a page on a site protected by an edge WAF. The browser resolves the domain name and connects to the service that receives public traffic. The WAF or reverse proxy evaluates the incoming request. It may first apply network and reputation controls, then inspect the HTTP method, host, path, headers and available request content. Managed signatures and custom rules are evaluated according to the provider's processing order. If no terminating rule matches, the request is forwarded to the origin server. The application processes it and sends a response back through the proxy to the visitor.

If a rule matches, the result depends on the action. A logging action records the event but lets the request continue. A challenge asks the client to demonstrate that it is likely to be a legitimate browser or user. A block action stops the request at the security layer. A rate-limit action counts repeated requests and applies mitigation when a configured threshold is reached. These actions are not interchangeable: a challenge can be appropriate for uncertain automation, while a clear exploit signature may justify a block. A sensitive endpoint may need authentication and application checks regardless of what the WAF decides.

In a cloud deployment, the WAF can sit close to users at globally distributed points of presence. In a self-managed deployment, it may be a reverse proxy or an engine such as ModSecurity in front of the web server. The location affects latency, visibility, operational ownership and failure modes. A cloud edge may absorb unwanted requests before they reach the origin, while an in-process or local proxy may have more direct access to application-specific context. Neither architecture removes the need to secure the origin itself.

WAF versus network firewall, IDS, IPS and CDN

These technologies can work together, but they solve different problems. A network firewall commonly controls connections using addresses, ports, protocols and connection state. A WAF focuses on application requests and can inspect web-specific fields. An intrusion detection system (IDS) identifies suspicious activity and raises alerts; an intrusion prevention system (IPS) can take action to stop traffic. Some products combine several functions, so the boundaries can overlap, but the operational question remains: what data can the control inspect, and what action can it enforce?

A content delivery network (CDN) primarily distributes and caches content closer to users. Many modern CDN providers also offer WAF, bot controls and DDoS mitigation at the edge. The CDN's caching function does not itself validate every request as safe. A cached response may reduce origin load, but a malicious request can still target uncached paths, login forms, APIs or cache behaviour. Security policies should account for both cached and dynamic traffic.

WAF protection is also different from endpoint protection, secure coding, runtime application self-protection and identity controls. A WAF may recognise a suspicious payload, but it generally cannot understand every business rule or prove that a logged-in user is authorised to transfer a particular account's funds. Treat the WAF as one layer in a defence-in-depth design, not as a replacement for the controls inside the application.

Common attack patterns a WAF may detect

SQL injection attempts try to alter the meaning of a database query by placing unexpected input into a parameter or request body. Cross-site scripting (XSS) attempts try to introduce script content that may execute in another user's browser. Path traversal attempts use crafted path components to access files outside an intended directory. Remote file inclusion, command injection, malicious file uploads and protocol anomalies are other examples that some WAF rule sets attempt to identify. The effectiveness of detection depends on the rule set, request parsing, application behaviour, encoding and the attack technique.

WAFs can also help with automated abuse. A login endpoint may be targeted by credential stuffing, where attackers try username and password combinations leaked from other services. A registration endpoint may receive scripted account creation. Search or product endpoints may be scraped at high volume. A WAF can combine request characteristics, reputation, bot signals and rate limits to slow or challenge some of this activity. It cannot reliably identify every automated client, and legitimate crawlers, accessibility tools, mobile apps and partner integrations must be considered.

Modern attacks frequently combine several techniques. An attacker may enumerate routes, test input fields, exploit a vulnerable dependency and then use an authenticated session. A single signature rarely tells the whole story. Good protection combines managed detection, custom rules for the application's own routes, identity and authorisation controls, monitoring, patching and a response process for incidents.

Managed rules and the OWASP Core Rule Set

Managed rules are prebuilt detection policies maintained by a provider or security team. They are designed to cover common attack patterns and are updated as new techniques and vulnerabilities become known. They reduce the need for every website owner to write every signature from scratch. A managed rule can have a default action and severity, and administrators may be able to change its action, disable a specific rule or create a narrowly scoped exception.

The OWASP Core Rule Set (CRS) is a widely used generic rule set for compatible WAF engines. It includes rules intended to detect common web attacks and protocol misuse. CRS uses anomaly scoring: matching rules contribute scores, and the combined score is compared with a configured threshold. This approach allows multiple weak signals to be considered together rather than treating every individual match as conclusive proof of an attack.

Rule sets are not identical across vendors. A provider may adapt CRS, combine it with proprietary signatures or apply its own scoring defaults. Do not assume that two WAF dashboards using the words “OWASP rules” behave identically. Review the version, enabled rule groups, sensitivity settings, exclusions and action. The official CRS documentation explains the project's model and tuning concepts; the OWASP CRS project page describes its purpose and supported ecosystem.

Custom rules: protect the routes that matter to your application

Managed rules provide a baseline, but your application has routes and workflows that generic signatures cannot fully understand. Custom rules let an administrator express local policy. Examples include challenging unusual traffic to a login route, restricting access to an internal administrative path, allowing a trusted integration to reach a documented endpoint, or blocking a request pattern that should never be generated by the public interface.

Good custom rules are narrow, explainable and tested. A broad condition such as “block every request with a query string” may stop some probes but will also break search, filters, pagination and normal application behaviour. A rule that blocks an entire country or user-agent family may affect legitimate customers, monitoring systems or search crawlers. Before enforcing a rule, identify the exact route, method, request pattern, expected client and business consequence. Prefer a managed challenge or logging mode when confidence is uncertain.

Document why each custom rule exists, who owns it and how to disable it safely. Review it when application routes change. Rules that made sense for an old login page may become harmful after an API migration or a new mobile app release. A WAF policy is part of application operations and should be maintained with the same care as code and infrastructure configuration.

Rate limiting: slowing abuse without confusing it with an attack signature

Rate limiting controls how frequently a client or group of clients can make matching requests during a defined period. It is especially useful for endpoints where repeated operations are costly or sensitive: login, password reset, account creation, search, coupon validation, comments, form submissions and API calls. A policy might count requests by source IP, authenticated identity, API key, session or another supported characteristic. The available counting keys and time windows depend on the WAF provider and plan.

Rate limiting is not simply “block an IP after a fixed number of requests.” Shared networks, offices, schools, mobile carrier NAT and household connections can place many legitimate people behind one public IP address. A low threshold based only on IP can affect an entire group. Where possible, combine rate limits with route, method, identity or session context. Use different policies for expensive operations and ordinary page views. A login form, static image and public article should not necessarily share one threshold.

Thresholds should reflect normal usage and the cost of the operation. Start by measuring baseline traffic, including peak periods and legitimate automated clients. Set a limit that leaves room for bursts and retries. Decide whether to log, challenge, throttle or block when the threshold is exceeded. Test the policy with realistic users and load patterns. Rate limiting is a control with trade-offs, not a substitute for fixing an endpoint that performs unbounded work.

Bot management and the SEO risk of blocking good crawlers

Not all bots are malicious. Search engine crawlers discover pages so they can be indexed. Uptime monitors check availability. Payment providers, webhook senders, feed readers and partner integrations may use automated clients. Attackers also use bots for scraping, credential stuffing, inventory hoarding, spam and vulnerability scanning. A policy that treats all automation as hostile can harm the business as much as an attack.

Bot detection may use verified-bot lists, request behaviour, browser signals, reputation, machine-learning scores or other telemetry. A WAF may challenge suspicious automation while allowing verified crawlers, but the exact capabilities differ by provider. Avoid assuming that a user-agent string alone proves identity: it can be copied. Where the provider offers a verified-bot signal, understand its definition and coverage. For important search crawlers, follow the provider's documented verification method and monitor whether key pages remain accessible.

SEO checks should be part of WAF deployment. Test important landing pages, robots.txt, sitemaps, canonical URLs and structured-data pages from a normal browser and from verified crawler diagnostics where available. Review challenge and block events for search engines and monitoring services. Cloudflare's WAF troubleshooting guidance specifically warns that mitigation rules can unintentionally affect known bots and SEO. Security policy should protect the site without making useful public content inaccessible to legitimate discovery systems.

False positives: when a WAF blocks a legitimate request

A false positive occurs when a security rule identifies a harmless request as malicious. This can happen because a customer enters code-like text into a support form, uploads a document containing unusual content, searches for a product name with punctuation, or sends a large but valid API payload. A rule may also misinterpret an encoded value, a modern framework request or a third-party integration. The risk increases when rules are highly sensitive or when an application accepts complex input.

Do not solve every false positive by disabling the entire managed ruleset. First identify the rule ID, request path, method, matched field and action. Confirm that the request is legitimate and understand why it matched. Then create the smallest possible exception: a specific rule on a specific route and field, with a documented reason and an owner. Keep other protections active. Re-test the exact legitimate workflow and a representative malicious test case after changing the policy.

Monitor false positives after application releases, new integrations and content changes. A WAF that was quiet last month may begin blocking a new editor, checkout flow or API version. Track support reports alongside security events. The aim is not to eliminate every alert; it is to make enforcement accurate enough that legitimate work continues while meaningful threats are still detected.

WAFs and API security: useful but incomplete protection

APIs expose application functions through structured requests. A WAF can inspect the HTTP layer and may recognise suspicious payloads, unexpected methods, malformed protocol behaviour or unusually frequent calls. Some products support API discovery, schema-aware validation or JSON body inspection. These capabilities can improve visibility, but they should not be confused with full API security.

A generic WAF usually cannot determine whether a user is allowed to read a particular customer record, whether an order total is valid, whether a payment state transition is permitted or whether an account has exceeded a business quota. Those decisions require application context. APIs still need strong authentication, object-level authorisation, input validation, output filtering, secure token handling, schema enforcement, audit logs and abuse controls. Rate limits should be designed around identities and operations, not just network addresses.

NIST SP 800-228, Guidelines for API Protection for Cloud-Native Systems, discusses API protection across development and runtime. Its treatment of WAFs is a useful reminder: request inspection is valuable, but it does not replace API-specific validation and controls. If your API accepts JSON, GraphQL, file uploads or long-running queries, test how your WAF parses those formats and what size or inspection limits apply.

WAF limitations and bypass considerations

A WAF only sees the traffic that passes through it. If an attacker can connect directly to the origin IP address, they may bypass an edge policy unless the origin is restricted to trusted proxy networks or protected by an equivalent control. Keep origin addresses private where possible, restrict inbound access, authenticate origin connections and verify that the application trusts forwarding headers only from known proxies. A public DNS record or old server address can expose an alternate path around the security layer.

Request parsing differences can also create gaps. A proxy, WAF and application framework may normalise URL paths, decode characters or interpret duplicate headers differently. Attackers sometimes exploit disagreements between components. Keep software current, use consistent request parsing and test how encoded paths and unusual headers are handled. Do not rely on a single signature to detect every variation of an attack.

Encrypted HTTPS traffic must be decrypted at a point where inspection is possible. A reverse proxy or edge service can inspect the HTTP request after terminating TLS, but end-to-end encryption arrangements and application architecture determine what the WAF can see. Large bodies, streaming uploads, WebSockets, gRPC and unusual protocols may have different inspection support. Check product limits rather than assuming every request byte is inspected.

Finally, a WAF cannot reliably stop every zero-day, compromised account, insider threat, malicious business transaction or attack that uses valid application functionality. If an attacker logs in with stolen credentials and performs permitted actions, a signature-based WAF may see ordinary requests. Detection, identity security, secure application design, patching, backups and incident response remain necessary.

How to deploy a WAF safely: a practical sequence

Begin with an inventory of public applications, domains, APIs, origin servers and critical routes. Identify which services process personal information, payments, account credentials or business-critical data. Map the normal user journeys and integrations. Decide where the WAF will sit and confirm that all public traffic actually passes through it. Restrict direct origin access before relying on edge filtering as a security boundary.

Next, enable a sensible baseline of managed rules and collect logs. If the product offers a detection or logging mode, use it to learn which rules match real traffic before turning on aggressive blocking. Review high-severity matches and test representative attack simulations in a controlled environment. Avoid testing destructive payloads against production systems or third-party services without permission. Confirm the provider's rule update process and who receives notifications when a ruleset changes.

Then add custom rules and rate limits for the routes with the greatest risk. Start with narrow policies for authentication, account creation, password reset, expensive searches and API endpoints. Protect administrative paths with identity-aware access controls rather than relying only on obscure URLs. Ensure that verified crawlers, uptime monitors and essential integrations continue to work. Define a rollback path before applying a change that could block all visitors.

Finally, monitor outcomes. Compare WAF events with origin logs, application errors, latency and support reports. Check whether blocked requests were genuinely malicious and whether allowed requests reached the correct application. Review policy after every major application release and periodically test the complete path from client to edge to origin. Security is a continuing operational process, not a one-time switch.

Monitoring, logging and incident response

Useful WAF logs should help an operator answer: what request matched, which rule matched, what action occurred, when it happened, and whether the request reached the origin. Depending on the provider, logs may include source IP, country, URI, method, user-agent, rule ID, action and selected request metadata. Avoid collecting or retaining sensitive request bodies unnecessarily. Logs can contain personal information, authentication tokens or customer input, so apply access controls and retention policies.

Build alerts around meaningful changes rather than every single match. A sudden increase in blocked login attempts, repeated probes against an unpatched route, a surge in 5xx responses or an unexpected rise in challenge rates may deserve investigation. A high volume of low-confidence signature matches may simply be background internet scanning. Correlate WAF events with application, identity and infrastructure telemetry before deciding what happened.

Prepare a response playbook. It should identify who can change a rule, how to preserve evidence, how to contact the hosting or WAF provider, how to restore service if a rule causes an outage and how to communicate with affected users. For a confirmed application vulnerability, blocking one payload is not enough: patch or mitigate the underlying defect, review logs for exploitation and rotate credentials if compromise is suspected.

Choosing a WAF: questions to ask before selecting a provider

Start with the architecture. Does the WAF support your hosting environment, protocols, APIs, file sizes and traffic volume? Can it protect every public entry point, including alternate domains and origin addresses? Does it terminate TLS, and how are certificates managed? What happens if the provider or inspection service is unavailable? Can you fail open or fail closed, and what are the security and availability consequences of each choice?

Evaluate detection quality and control. Which managed rule sets are included? How frequently are they updated? Can you inspect rule IDs and match details? Are custom expressions, rate limits, bot controls, API discovery and schema validation available on your plan? Can you stage policy changes, create narrow exclusions and roll back quickly? How does the product verify trusted crawlers? What are the limits for request-body inspection, logging and retention?

Finally, calculate the total operating cost. Consider traffic charges, advanced security add-ons, log storage, support, engineering time and the cost of investigating false positives. A lower-priced plan may be entirely adequate for a small informational site, while a financial or high-volume API service may need more advanced controls and human support. Choose based on the risks and capabilities you can operate responsibly, not on the longest feature list.

Key takeaway: a WAF is a filter, not a substitute for security engineering

A web application firewall adds an important inspection and enforcement layer between internet traffic and an application. It can help detect common exploit patterns, reduce automated abuse, apply route-specific policies and limit repeated requests. Managed rules and the OWASP Core Rule Set provide a starting point; custom rules, rate limits and bot controls make protection more relevant to the application.

The strongest deployment is not the one that blocks the most traffic. It is the one that blocks meaningful threats while allowing legitimate users, crawlers and integrations to complete their work. That requires accurate routing, secure origin configuration, careful rule tuning, useful logs, tested rollback procedures and continuous review. Pair WAF controls with secure coding, authentication, authorisation, dependency updates, API validation and incident response. A WAF can reduce exposure, but the application must still be built and operated securely.

Frequently asked questions

1. What is a web application firewall in simple terms?

A web application firewall is a security layer that inspects HTTP and HTTPS requests to a website or API. It applies rules to allow, log, challenge or block suspicious traffic before that traffic reaches the application. It focuses on web requests rather than only network addresses and ports.

2. What attacks can a WAF help stop?

Depending on its rules and visibility, a WAF can help detect or block common web attack patterns such as SQL injection, cross-site scripting, protocol abuse, malicious file uploads and some automated abuse. It cannot prevent every vulnerability or attack, particularly those involving valid credentials or application business logic.

3. Is a WAF the same as a firewall?

No. A traditional network firewall mainly controls traffic using network and transport information such as IP addresses, ports and protocols. A WAF focuses on web application traffic and can inspect HTTP methods, paths, headers, parameters and request bodies.

4. Does a WAF protect an API?

A WAF can inspect API requests and help block common malicious patterns or abusive request rates. It does not replace API authentication, authorisation, schema validation, business-logic controls or secure handling of sensitive data.

5. What is the OWASP Core Rule Set?

The OWASP Core Rule Set is a widely used set of generic detection rules for common web attack patterns. It can be deployed with compatible WAF engines and needs testing and tuning for the application it protects.

6. Can a WAF block legitimate visitors?

Yes. A rule may mistake legitimate input, uploads, search terms or unusual client behaviour for an attack. Logs, staged rollout, narrow exclusions and repeated testing help reduce false positives.

7. Does a WAF stop DDoS attacks?

A WAF can help mitigate some application-layer floods and abusive request patterns, but volumetric and network-layer DDoS protection require broader capacity, edge filtering and provider-level controls.

8. Should every website enable a WAF?

Public websites and APIs can benefit from an appropriately configured WAF, but the policy should match the application's routes, users and risk. Enabling broad blocking rules without monitoring can disrupt legitimate traffic.

9. Can a WAF replace secure coding and software updates?

No. A WAF is a compensating security layer, not a substitute for secure design, input handling, access control, dependency updates, testing, backups and incident response.

10. How do I know whether my WAF is working?

Review request and rule logs, confirm that test traffic triggers the intended rules, monitor origin traffic and application errors, check legitimate user journeys, and periodically test policy changes and bypass-resistant configurations.
