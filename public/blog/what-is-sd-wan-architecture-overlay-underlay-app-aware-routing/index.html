What Is SD-WAN? Architecture, Overlay Networks, Traffic Steering and Security

Learn how software-defined WAN connects branches, cloud and remote sites using overlays, multiple internet and private links, application-aware routing, central policy and security.

By Suraj Vishwakarma · Published by TEZZ CONNECT

SD-WAN (Software-Defined Wide Area Network) is a way to connect offices, data centres and cloud environments using centrally managed policy across multiple network transports. It separates the logical WAN overlay from the physical or provider underlay, allowing organisations to combine broadband, private circuits and cellular links while applying application-aware routing and security policy.

SD-WAN is not a magic internet-speed booster and it does not automatically replace MPLS. It is an architecture for operating a multi-transport WAN with better visibility, automation and control. This guide explains how it works, where it helps, what it cannot solve and how to plan a deployment.

1. What is SD-WAN?

Software-Defined Wide Area Network (SD-WAN) is an approach to connecting geographically separated offices, data centres, cloud environments and users through centrally managed network policy. It separates the logical WAN service from the individual circuits that carry traffic. An organisation can use a mix of broadband internet, dedicated internet access, MPLS, fibre and cellular connectivity while applying a consistent set of policies across locations.

Traditional wide-area networks often relied on private circuits and hub-and-spoke designs. Branch traffic was sent to a central data centre for internet access, security inspection or access to business applications. That model can still be appropriate, but it may be inefficient when users increasingly access cloud platforms, SaaS applications and services hosted outside the corporate data centre.

SD-WAN introduces software-driven control and orchestration. Edge devices at branches and hubs build logical connections over available transports. The platform can identify application flows, measure path conditions and apply policies to determine how traffic should travel. Management is commonly centralised, allowing administrators to define configuration and policy templates rather than manually configuring every branch router.

SD-WAN is not a single protocol or a synonym for broadband. It is an architecture and service model. Products differ in how they discover peers, distribute routes, secure tunnels, identify applications, measure performance and handle failures. A deployment must be evaluated by its actual capabilities and operational model, not just by the SD-WAN label.

2. Why enterprise WAN designs are changing

Businesses now operate across offices, cloud regions, remote workers, partner networks and mobile devices. Applications may be hosted in a corporate data centre, a public cloud, a SaaS provider or a third-party platform. Sending every packet through one central hub can increase latency, consume expensive backhaul capacity and make cloud access dependent on the health of a limited number of sites.

Traditional WANs commonly use private MPLS services because they can provide provider-managed connectivity, predictable routing and service-level commitments. However, private circuits may take time to provision, can be expensive in some markets and may not be the most direct route to a cloud application. A private circuit is also not automatically encrypted simply because it is private.

Internet connectivity has become available at many branch locations, and multiple providers or access technologies can offer resilience. But ordinary internet paths vary in congestion, delay, packet loss and routing. An enterprise needs a way to decide which traffic can use which path, how to detect degradation and how to fail over without requiring a manual change at every branch.

SD-WAN addresses these operational challenges by combining multiple underlays with centrally managed overlay connectivity and policy. It can improve visibility and make network changes more consistent. It does not guarantee that broadband will behave like a private circuit, nor does it make every cloud service faster. The value depends on the quality of the underlays, policy design and end-to-end application architecture.

3. Underlay and overlay: the most important SD-WAN concepts

The underlay is the transport infrastructure that carries packets between locations. It may include broadband internet, dedicated internet access, MPLS, Ethernet private lines, 4G LTE, 5G or satellite connectivity. Each underlay has its own capacity, availability, latency, jitter, loss characteristics, provider responsibilities and cost.

The overlay is the logical network built across one or more underlays. SD-WAN edge devices create logical connections or tunnels between sites and use policy to decide how application traffic enters those paths. Overlay routing can present a consistent network across locations even when the underlying circuits are provided by different carriers or use different technologies.

Separating overlay from underlay helps an organisation change transports without redesigning every application network. A branch can move from one broadband provider to another, add a cellular backup or introduce a private circuit while retaining much of the same logical policy. The edge device and controller coordinate the required configuration and connectivity.

However, the overlay still depends on the underlay. If the local fibre is cut, a tunnel using that fibre cannot carry traffic. If the internet provider has high packet loss, encrypted overlay packets may experience that loss too. SD-WAN can choose another healthy path if one exists and if the policy allows it, but it cannot create capacity or availability that the physical network does not provide.

When evaluating a design, document every site’s underlay circuits, access technologies, bandwidth, provider, physical diversity and service terms. Then document the overlay topology, tunnel relationships, route exchange and policy. Keeping these layers distinct makes troubleshooting much clearer.

4. SD-WAN architecture: edge devices, controllers and orchestrators

Most SD-WAN architectures include edge devices, centralised management and one or more control-plane components. Names vary by vendor, but the functional roles are broadly similar.

SD-WAN edge

The edge device is deployed at a branch, campus, data centre or cloud environment. It connects to local LANs and one or more WAN transports. It may establish secure tunnels, classify application traffic, enforce segmentation, apply quality policies and forward packets along the selected path. Edge devices can be physical appliances, virtual appliances or software instances.

Controller or control plane

Control components help establish trusted relationships, distribute topology and routing information, and communicate policy or path information to edge devices. Some products use several specialised controller roles; others combine functions. Control-plane availability matters because devices may need it for onboarding, policy changes, route exchange or recovery, even if established data-plane forwarding can continue during a temporary controller outage.

Management and orchestration

The management system provides a central interface for inventory, templates, configuration, policy, monitoring, software lifecycle and troubleshooting. Orchestration automates tasks such as device onboarding, certificate handling and deployment workflows. Centralised management reduces repetitive configuration, but a compromised management account or incorrect global template can affect many sites at once.

Cloud-hosted and on-premises models

Control and management components may be hosted by a vendor, a service provider or the enterprise itself. Cloud-hosted models can reduce infrastructure maintenance, while on-premises models may provide greater direct control over hosting and data paths. Each model has dependencies involving internet reachability, identity, certificates, backups, redundancy, data residency and disaster recovery. Confirm the responsibility split before choosing.

5. How an SD-WAN packet travels

Consider an employee at a branch opening a cloud-based collaboration application. The branch edge receives the traffic from the local network and identifies the application flow using the methods supported by the product. It evaluates the policy associated with that flow. The policy may specify preferred transports, minimum path-quality conditions, encryption requirements and what to do if the preferred path is unavailable.

The edge measures or receives information about available paths. It may use probes or tunnel statistics to assess delay, jitter and packet loss. If the primary internet circuit is healthy and meets the application's policy, traffic can use that path. If the path degrades beyond a configured threshold, the edge may move new flows or eligible traffic to a different link, such as a second broadband circuit or MPLS.

The packet is encapsulated for the overlay and sent across the selected underlay. At the remote edge or cloud gateway, the overlay packet is authenticated or decrypted as appropriate, decapsulated and forwarded toward the destination. The return direction has its own path-selection and policy considerations; it is not always guaranteed to use the identical physical route.

Some platforms support packet duplication, forward error correction or steering individual packets across multiple links for selected traffic. These features have trade-offs in bandwidth, reordering, latency and cost. Many designs instead steer entire application flows or sessions to a preferred path to avoid unpredictable packet ordering.

Do not assume every product uses the same detection interval, tunnel protocol or failover method. Ask the vendor to demonstrate what happens to an active voice call, a long-lived TCP session and a new application connection when a circuit fails or crosses a loss threshold.

6. Application-aware routing and business intent

Application-aware routing means policies can treat different traffic types differently. A real-time voice or video flow may need low delay, low jitter and low loss. A large software update may tolerate delay and can use a lower-cost link. A business-critical transaction may require a preferred private path or a specific security inspection point.

Application identification can rely on ports, protocol signatures, domain information, endpoint agents, certificates, traffic patterns or vendor-specific classification methods. Encryption and changing application behaviour can limit visibility. A cloud application may use shared IP addresses or dynamic endpoints, so a static address-based rule may not reliably identify it.

Policy should express measurable intent. For example, a voice class may prefer a path while its measured loss, delay and jitter remain within defined thresholds, then use an alternate path when those thresholds are exceeded. A bulk-transfer class may prefer the lowest-cost available transport. A sensitive application may require encryption or a particular security service regardless of the link selected.

Application policies need testing. A broad classification rule can misidentify traffic or send it down an unsuitable path. Review how the platform handles unknown applications, encrypted DNS, QUIC, shared SaaS endpoints, software updates and traffic that does not match a known signature. Keep business owners involved in defining what “critical” means.

7. Path quality: latency, jitter, packet loss and availability

SD-WAN products commonly monitor path characteristics to make steering decisions. Latency is the time taken for traffic to travel between endpoints. Jitter describes variation in packet delay. Packet loss is the proportion of packets that fail to arrive. These measures can affect interactive applications, especially voice, video and remote desktop sessions.

Measurements need context. A probe to a nearby provider gateway does not necessarily represent the path to a SaaS application. The destination may be farther away, use a different transit network or have its own congestion. Where possible, monitor application-relevant destinations and compare synthetic probes with actual user experience.

Thresholds should reflect the application and business requirement. A single universal latency or loss threshold is not suitable for every service. A voice policy, file transfer and database replication job may tolerate very different conditions. Define the metric, measurement interval, direction, threshold and recovery hysteresis to avoid unnecessary path flapping.

Availability also has multiple layers. A tunnel can be up while the application is unreachable. A broadband circuit can report carrier signal while DNS or upstream routing is broken. Monitoring should combine interface status, tunnel state, path probes, application reachability and user experience where practical.

Path steering is only as good as its alternatives. If both broadband circuits share the same local duct, power supply or upstream provider, they may fail together. Physical and provider diversity matter as much as the number of WAN interfaces shown in a dashboard.

8. SD-WAN security: encryption, identity and segmentation

SD-WAN often uses encrypted tunnels to protect traffic across public networks. IPsec is a common mechanism, although implementations and supported tunnel methods vary. Encryption protects data in transit between trusted endpoints, but it does not by itself decide whether a user or application should be allowed to access a particular resource.

Device identity and secure onboarding are important. An edge device should prove that it is authorised to join the network, commonly through certificates or another strong identity mechanism. Protect private keys, rotate credentials according to policy, revoke compromised devices and secure the management plane with strong authentication and role-based access.

Segmentation separates traffic into logical groups such as corporate users, guest access, payment systems, voice, IoT and management. Policies should prevent one segment from reaching another unless a documented service requires it. Segmentation must be enforced consistently across branches, data centres and cloud environments; a label on a dashboard is not a security boundary by itself.

Some SD-WAN platforms include or integrate firewalls, intrusion prevention, secure web gateways, DNS filtering and cloud security services. Feature depth varies. Verify whether security is performed locally at the branch, in a cloud point of presence or at a central data centre. Consider the effect on latency, encrypted traffic, logging, data privacy and service availability.

SD-WAN is not automatically equivalent to zero trust or SASE. A secure design still needs endpoint protection, identity governance, patching, application security, vulnerability management, incident response and continuous monitoring. Treat the SD-WAN control plane as a high-value management system that requires its own hardening and recovery plan.

9. SD-WAN vs MPLS: competitors or complementary technologies?

MPLS and SD-WAN are often compared, but they are not exact opposites. MPLS is a forwarding and service-provider technology often used to deliver private WAN connectivity. SD-WAN is an overlay and policy-driven WAN architecture that can use MPLS as one of its transports.

MPLS services may offer provider-managed routing, traffic classes and contractual service levels. They can be useful for sites that need predictable private connectivity or where internet access is limited. The actual service characteristics depend on the provider contract, access circuit and end-to-end design. MPLS does not inherently encrypt payloads.

SD-WAN can combine MPLS with broadband, dedicated internet and cellular links. This can provide more transport choice and application-aware steering. It may reduce reliance on expensive private circuits for some traffic, but broadband quality varies and SD-WAN appliances, subscriptions, support and operations also have costs.

A hybrid design may retain MPLS for latency-sensitive or business-critical flows while using direct internet for SaaS and general browsing. Another organisation may use dual broadband with encrypted overlays and no MPLS. The right answer depends on geography, provider availability, application needs, risk tolerance, service levels and total cost—not on a universal claim that one technology is always better.

10. SD-WAN vs traditional VPNs

A site-to-site VPN creates a protected logical connection between networks, commonly using IPsec. It can be configured manually on routers or firewalls and is suitable for many small and medium deployments. A remote-access VPN connects individual users or devices to an organisation's network or applications.

SD-WAN can use VPN tunnels as part of a larger system. It adds centralised orchestration, application classification, policy distribution, path measurement and multi-transport steering. Instead of manually building and maintaining each tunnel, an administrator may define a topology and policy that the platform distributes to many edge devices.

For a small number of sites, traditional VPNs may be simpler and cheaper. For many branches with multiple circuits, dynamic application requirements and frequent changes, SD-WAN may reduce operational effort. Compare licensing, support, device lifecycle, controller hosting, logging, interoperability and staff skills. The presence of an encrypted tunnel alone does not make a solution SD-WAN.

11. Direct internet access and cloud connectivity

Direct internet access (DIA) allows a branch or site to reach internet services locally rather than sending all traffic through a central headquarters. SD-WAN can apply policy and security controls to this local breakout. This can reduce backhaul and improve the route to nearby cloud services when the local provider path is good.

Local breakout changes the security model. The branch may need local firewalling, DNS protection, web filtering, endpoint controls and central logging. An organisation should decide which traffic can leave directly, which must pass through a central inspection point and which requires a cloud security service. Policies should also account for regional privacy and data-residency requirements.

Cloud connectivity may use public internet tunnels, dedicated cloud interconnects, provider gateways or virtual SD-WAN edges. Consider where the cloud application is hosted, how routes are advertised, whether traffic is symmetric, and what happens when the preferred cloud region or gateway is unavailable.

Optimising the branch-to-cloud path does not control the entire route inside the SaaS provider's network. Measure application performance end to end and understand the provider's own availability and service commitments.

12. SD-WAN topologies: hub-and-spoke, full mesh and regional hubs

In a hub-and-spoke topology, branches connect to one or more central hubs. This can simplify security inspection and access to shared data-centre services, but traffic between branches may travel through a hub even when a direct path would be more efficient.

A full-mesh topology allows sites to establish direct logical connectivity with other sites where policy and platform support permit. It can reduce hairpinning and support direct branch-to-branch applications, but the number of possible relationships and the policy surface can grow quickly as sites are added.

Regional hub designs place aggregation points closer to groups of branches or cloud regions. They can balance centralised control with shorter paths. Some deployments use dynamic on-demand tunnels so not every branch maintains a permanent tunnel to every other branch.

Choose topology based on application flows, security boundaries, routing scale, operational complexity and failure domains. A diagram should show not only the preferred path but also the alternate path during hub, controller, circuit and cloud-gateway failure.

13. Resilience and failover: what actually happens when a link fails?

SD-WAN can monitor multiple paths and move traffic when a circuit or tunnel fails. The result depends on failure detection, policy, available capacity and application behaviour. A physical interface-down event may be detected quickly, while an upstream black hole can require probes or service checks to identify.

Failover is not always seamless. An established TCP session may survive if the new path preserves addressing and state, but some platforms or topologies may reset sessions. Voice and video applications may experience a short interruption or packet loss during convergence. Ask vendors to demonstrate realistic failure cases rather than relying on a generic “automatic failover” claim.

Capacity matters during failover. If a branch normally uses two 500 Mbps circuits simultaneously and one fails, the remaining circuit may not support the full combined load. Define which applications receive priority and what traffic can be rate-limited or deferred during degraded operation.

Test more than cable removal. Simulate packet loss, high latency, jitter, DNS failure, upstream internet outage, controller unavailability, power failure and a remote hub outage. Confirm alerting, failback behaviour and whether traffic returns to the preferred link too aggressively. Use hold-down timers or hysteresis where supported to avoid rapid switching.

14. SD-WAN performance and sizing

Size edge devices for encrypted throughput, packet rate, tunnel count, concurrent sessions, application identification and enabled security features. A device advertised for a high raw throughput may deliver less when encryption, deep inspection, logging or advanced traffic optimisation is enabled.

Account for both directions and peak periods. Video meetings, backups, software distribution, cloud synchronisation and business transactions may overlap. Determine whether the platform supports QoS and shaping on each underlay, and whether it can reserve or prioritise capacity for critical traffic.

Check tunnel overhead and effective MTU. Encapsulation and encryption add headers, which can reduce the usable payload size. Poorly handled path MTU discovery may cause large packets to fail or applications to behave inconsistently. Test representative packet sizes and VPN paths.

Performance is also affected by the underlay provider, last-mile contention, peering, DNS, SaaS service health and endpoint quality. SD-WAN telemetry can help isolate some of these factors, but it cannot fix an overloaded access circuit or a slow application server. A clear baseline before deployment makes post-change comparison more meaningful.

15. Deployment models: do-it-yourself, co-managed and managed SD-WAN

In a do-it-yourself model, the enterprise procures circuits, chooses the platform, deploys edge devices, configures policy and operates the service. This offers direct control but requires networking skills, time, monitoring, support processes and the ability to coordinate multiple circuit providers.

A co-managed deployment shares responsibilities between the enterprise and a service provider or integrator. The provider may deploy and maintain the platform while the customer retains control over selected policies, application priorities or service parameters. Responsibilities must be explicit to avoid gaps during incidents or change windows.

A fully managed service can reduce the internal operational burden and provide a single support relationship. However, the organisation may have less direct control over configuration, visibility or provider selection. Understand service-level commitments, escalation, data access, change approval, contract exit and how configurations can be exported.

Regardless of model, define who owns underlay circuits, edge hardware, controller availability, certificates, security policies, software updates, monitoring, backups and incident response. A clear RACI or responsibility matrix prevents assumptions from becoming outages.

16. SD-WAN monitoring and troubleshooting

Start troubleshooting by identifying the affected application, user, site, time window and direction. Confirm whether the issue affects one branch, many sites or only one destination. Check local LAN health before assuming the WAN is responsible.

Inspect underlay interfaces for carrier state, negotiated speed, errors, drops, utilisation and provider events. Review overlay tunnel status, peer reachability, route exchange and encryption state. Compare measured delay, jitter and loss across available paths. Determine whether the policy selected the path that the design intended.

Check application identification and policy matches. If traffic is classified incorrectly, it may receive the wrong route or QoS treatment. Confirm DNS resolution, destination IP changes, certificate validity, proxy behaviour and whether the application provider has an outage. Compare the same application from another network when possible.

For intermittent issues, correlate telemetry with timestamps and configuration changes. Look for path flapping, circuit congestion, queue drops, asymmetric routing, MTU problems, expired certificates, controller events and software defects. Preserve logs before they roll over and record the exact device, software version and policy state.

Use a layered troubleshooting sequence: endpoint and LAN, local edge, underlay circuit, overlay tunnel, remote edge or gateway, destination network and application. This avoids changing global policy to fix a problem that originates in one local circuit or endpoint.

17. Planning an SD-WAN project: requirements and questions

Begin with a site inventory. Record each location's user count, applications, traffic volume, existing circuits, provider, bandwidth, contract term, physical diversity and criticality. Map the current routing, security zones, VPNs, data-centre paths and cloud connections.

Define application classes and measurable objectives. Identify which services are latency-sensitive, which need encryption, which must use a particular inspection path and which can use best-effort internet. Avoid vague requirements such as “make everything fast.” Set targets that can be measured and reviewed with application owners.

  • Which underlays are available at each site, and are they physically and provider-diverse?
  • Does the platform support the required encryption, segmentation, routing and identity model?
  • How are application flows identified, especially encrypted SaaS and changing endpoints?
  • What are the thresholds and intervals for loss, delay and jitter measurement?
  • What happens to active sessions during circuit, tunnel, hub and controller failures?
  • Where are management and control components hosted, and who operates them?
  • How are certificates, device onboarding, software updates and administrator access protected?
  • What logging, telemetry export, APIs and audit records are available?
  • How are cloud gateways, direct internet breakout and remote users handled?
  • What are the licensing, hardware, circuit, support, training and exit costs?

Pilot representative sites before a broad rollout. Include a small branch, a large site, a location with poor broadband diversity and a site with critical real-time applications. Test the migration and rollback process. Keep a record of baseline performance and user experience so improvements or regressions can be demonstrated.

18. SD-WAN, SASE and the future of enterprise networking

SD-WAN is increasingly combined with cloud-delivered security. Secure Access Service Edge (SASE) is an architectural approach that brings network connectivity and security services together, often using a cloud-delivered service model. Components may include SD-WAN, secure web gateway, cloud access security broker, zero-trust network access and firewall as a service.

The terms are related but not interchangeable. SD-WAN focuses on connecting sites and steering traffic across WAN transports. SASE extends the model to security services and user access across locations. Some vendors bundle the functions, while others integrate separate products. Evaluate actual capabilities and control ownership rather than relying on a product label.

Other developments include more automated policy, telemetry-driven operations, cloud-native edge functions and stronger integration with identity systems. Standardisation work is also evolving. For example, IETF RFC 10090 describes BGP usage for SD-WAN overlay networks; operators should distinguish published standards from Internet-Drafts and vendor-specific implementation details.

The long-term direction is not simply to replace every private circuit. Enterprises will continue to use a mixture of private and public transports, cloud connectivity and security controls. The best architecture is the one that meets the organisation's application, resilience, compliance and operational requirements with measurable outcomes.

Conclusion: SD-WAN is an operating model for a multi-transport WAN

SD-WAN builds a policy-driven overlay across one or more underlying transports. Edge devices connect sites, control and management components distribute configuration, and application-aware policies can steer traffic according to path conditions, security requirements and business intent.

Its benefits can include simpler central management, more flexible use of broadband and private circuits, improved application visibility and controlled local internet access. Its limitations are equally important: it depends on underlay quality, requires careful security and policy design, introduces platform and subscription costs, and does not guarantee seamless failover or faster applications.

Plan SD-WAN as an end-to-end service. Measure the applications people use, design diverse underlays, protect the management plane, define realistic path thresholds, test failure scenarios and assign operational responsibilities. Compare it with MPLS and traditional VPNs on actual requirements rather than slogans.

Frequently asked questions about SD-WAN

1. What does SD-WAN stand for?

SD-WAN stands for Software-Defined Wide Area Network. It is an approach to building and operating wide-area networks in which software-driven policy and orchestration manage connectivity across one or more underlying transport networks.

2. How does SD-WAN work?

SD-WAN edge devices establish overlay connectivity across available underlay links, exchange or receive control information, identify application flows and apply policies to select paths. Depending on the product, traffic can be steered using link health, application requirements, security policy and cost.

3. Does SD-WAN replace MPLS?

Not necessarily. SD-WAN can use MPLS as one of its underlay transports alongside broadband internet, dedicated internet access and cellular links. Some organisations reduce MPLS use, while others retain it for selected applications or sites.

4. Is SD-WAN the same as a VPN?

No. A VPN is a method of creating protected or private connectivity, often using encryption such as IPsec. SD-WAN is a broader WAN architecture and management approach that can use encrypted tunnels as part of its overlay.

5. Does SD-WAN make internet faster?

Not by itself. SD-WAN can select a better available path, avoid a degraded link or use multiple transports, but it cannot remove congestion or poor performance on every underlying circuit or on the destination service.

6. Is SD-WAN secure?

Security depends on the design and enabled features. SD-WAN deployments commonly use authenticated devices, encrypted tunnels, segmentation and centrally managed policies, but still need firewall controls, identity security, patching, monitoring and careful management-plane protection.

7. What is the difference between SD-WAN and SASE?

SD-WAN focuses on WAN connectivity, traffic steering and network policy. SASE combines networking capabilities with cloud-delivered security services, often including secure web gateway, cloud access security broker, zero-trust network access and firewall as a service.

8. Can SD-WAN use two internet connections?

Yes. An SD-WAN edge can use multiple broadband or dedicated internet links and apply policies to distribute or steer traffic. The actual failover, load-sharing and packet-level behaviour depends on the platform and configuration.

9. What is an SD-WAN underlay and overlay?

The underlay is the physical or provider connectivity that carries packets, such as broadband, MPLS, fibre or LTE/5G. The overlay is the logical network built across those transports, often using tunnels and policy to connect sites.

10. Is SD-WAN suitable for small businesses?

It can be, especially for organisations with several sites, cloud applications or a need for centrally managed multi-link connectivity. A small business with one location may find a well-configured router and reliable broadband simpler and less expensive.
