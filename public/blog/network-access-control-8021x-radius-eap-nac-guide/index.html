Network Access Control Explained: 802.1X, RADIUS, EAP and NAC

How do organisations stop an unknown laptop, unauthorised phone or unmanaged device from joining an internal network? Network access control (NAC) combines identity checks, authentication protocols and network policy so access depends on more than plugging in a cable or knowing a Wi-Fi password.

1. What is network access control?

Network access control is an approach to deciding whether a person or device may connect to a network, what level of access it receives and what should happen when its identity or security state changes. NAC is not one universal protocol or one appliance. It is an architecture that can combine switches, wireless access points, authentication servers, identity directories, certificate services, endpoint agents, firewalls and monitoring systems.

Imagine an office with employee laptops, visitor phones, printers, cameras and contractor devices. Treating every connection as equally trusted would create unnecessary risk. NAC lets an organisation apply different rules: a managed employee laptop may reach approved business applications; a printer may communicate only with print services; a visitor may receive internet-only access; and an unknown endpoint may be denied or placed in a restricted remediation network.

NAC reduces the assumption that physical connection equals trust. It can support least privilege, segmentation, auditability and controlled onboarding. It does not prove that a device is harmless. A valid identity can be compromised, a trusted endpoint can become infected, and an incorrect policy can expose resources. NAC therefore complements endpoint protection, patching, firewalls, encryption and monitoring rather than replacing them.

What NAC is not

NAC is not the same as a firewall. A firewall commonly filters traffic between networks or security zones, while NAC makes an access decision about a connecting endpoint or session. NAC is not antivirus or endpoint detection and response: those tools inspect device security, while NAC may consume posture signals to decide network access. NAC is also not a replacement for identity governance or continuous monitoring.

2. NAC, IEEE 802.1X, RADIUS and EAP compared

RADIUSAAA protocolCarries authentication and authorization exchanges between network equipment and an authentication server; it can also carry accounting.

AuthenticatorNetwork edge roleA switch or access point controlling the connection and relaying authentication messages.
Authentication serverDecision roleValidates the exchange and returns an accept, reject or challenge response.

IEEE 802.1X describes port-based network access control. It distinguishes a controlled port, which carries normal authorised communication, from an uncontrolled port used for authentication and key-management exchanges. The standard uses EAP and its LAN encapsulation, EAP over LAN (EAPOL), to support authentication. IEEE describes 802.1X as guarding network access against unidentified or unauthorised parties.

RADIUS is commonly used between the authenticator and the authentication server. The switch or access point acts as a RADIUS client; it is not the end-user's laptop. EAP messages can be carried inside RADIUS attributes, allowing the authentication server to handle the selected method while the network edge forwards the exchange. In short: NAC is the policy approach; 802.1X controls port access; EAP provides the authentication conversation; and RADIUS transports AAA messages.

Authentication, authorization and accounting

Authentication asks whether the presented identity has been verified. Authorization determines what that identity may do. Accounting records selected session details, such as start, stop or usage information, depending on the implementation. These functions are commonly grouped as AAA. A successful authentication does not automatically grant unrestricted access; the authorization policy still matters.

3. How an 802.1X authentication session works

Consider a managed laptop connecting to a company switch. The following is a simplified sequence; exact exchanges, retries and attributes depend on the implementation.

  1. Connection: The endpoint connects to an Ethernet port or associates with an enterprise Wi-Fi network.
  2. Restricted initial state: The authenticator does not yet allow ordinary protected traffic through the controlled port. It permits the authentication exchange.
  3. EAP conversation: The endpoint supplicant and authenticator exchange EAPOL messages. The authenticator may request an identity or start a configured method.
  4. RADIUS request: The switch or access point sends a RADIUS Access-Request to its configured server. EAP information is carried in the request when EAP authentication is used.
  5. Validation: The server processes the EAP conversation. It may validate a certificate, check a directory, verify credentials or consult another identity system.
  6. Challenge, if required: The server can send Access-Challenge messages. The authenticator relays the EAP request to the endpoint and returns the response.
  7. Decision: The server returns Access-Accept or Access-Reject. An accept may include policy attributes such as a VLAN assignment or session limits.
  8. Enforcement: The authenticator opens or configures the controlled port according to the result. A successful authentication is not necessarily unrestricted access.
  9. Session lifecycle: Accounting, reauthentication, link-down events, timeouts or administrative changes may update or terminate the session.

The endpoint-to-authenticator exchange is commonly EAPOL on an IEEE 802 LAN. The authenticator-to-server exchange is commonly RADIUS over IP. These are separate links in one authentication process. A packet capture on the endpoint may show EAPOL but not the RADIUS exchange; a capture near the server may show RADIUS without the original endpoint's Ethernet frames.

What Access-Accept means

Access-Accept means the server accepted the request under the policy it evaluated. It is not a statement that every destination should be reachable. The network edge applies the returned profile, and firewalls or other controls can further restrict traffic. If an endpoint authenticates but cannot reach an application, investigate authorization, routing, DNS and firewall policy instead of assuming authentication failed.

4. EAP methods: passwords, tunnels and certificates

EAP is an extensible framework, not one authentication algorithm. The selected EAP method determines how the peer and server prove identity and whether cryptographic keys are established. The endpoint, authenticator and server must support and correctly configure the chosen method.

EAP-TLS

EAP-TLS uses certificates for mutual authentication. In a managed-device deployment, the endpoint validates the authentication server's certificate and the server validates the endpoint's client certificate. This avoids relying on a reusable password as the only proof of device identity. Certificate lifecycle is essential: certificates must be issued to the correct devices, protected, renewed before expiry and revoked when a device is lost or decommissioned.

RFC 9190 specifies EAP-TLS using TLS 1.3. It describes improvements including forward secrecy and reduced exposure of peer identity compared with earlier EAP-TLS versions. EAP-TLS is widely used with IEEE 802.1X in Wi-Fi and MACsec environments. A deployment still needs a sound certificate authority, trusted server names, revocation handling and compatible clients.

PEAP and EAP-TTLS

Tunneled methods such as PEAP and EAP-TTLS create a protected TLS tunnel and then carry an inner authentication method. Their security properties depend on the inner method and client configuration. A common operational risk is a client that accepts any server certificate or fails to verify the expected server identity. If a device connects to a rogue authentication server, credentials may be exposed or policy undermined.

Choosing a method

There is no universal best method for every network. Certificate-based EAP-TLS is often a strong choice for managed endpoints because it supports mutual authentication. Password-based methods may be easier to introduce in some environments but require careful server-certificate validation, credential protection and lifecycle controls. Test compatibility with operating systems, phones, IoT endpoints and certificate infrastructure before choosing.

Never tell users to click through an unexpected certificate warning to make Wi-Fi work. It may indicate an expired certificate, wrong server name, untrusted authority or rogue network. Verify the configured authentication server identity with IT support.

5. Authorization, VLANs, guest access and device exceptions

After successful authentication, a RADIUS server can return attributes that the network device uses to apply policy. Depending on vendor support, this may include a VLAN identifier, downloadable access-control list, session time limit or role information. Attribute names, syntax and supported combinations vary. A policy designed for one switch family should not be assumed to work identically on another.

Dynamic VLAN assignment

A dynamic VLAN can place a device into a network segment based on identity or group. An employee laptop might enter a corporate access VLAN, a printer a restricted device VLAN, and a guest an internet-only VLAN. Segmentation limits which systems can communicate, but VLAN assignment alone is not a complete security policy. Routing and firewall rules must enforce the intended boundaries.

Guest access

Guest access may use a captive portal, sponsor approval, temporary credentials or a dedicated guest SSID. Guests should not receive a path into internal file shares, management interfaces or sensitive applications. Time limits, acceptable-use notices, rate limits and logging may be appropriate, subject to local law and privacy policy. Keep guest onboarding separate from employee authentication and test what happens when guest credentials expire.

Printers, cameras and IoT

Some endpoints cannot perform 802.1X. Organisations may use alternatives such as MAC Authentication Bypass (MAB), certificate-based onboarding through a gateway or a restricted device network. MAB uses a device MAC address as an identifier; it is not equivalent to cryptographic authentication because MAC addresses can be copied or spoofed. If used, pair it with restrictive segmentation, inventory controls and monitoring. Do not create broad, permanent bypass rules simply because an endpoint is difficult to configure.

Posture and zero trust

Some NAC platforms consume posture signals such as operating-system version, patch status, disk encryption, endpoint protection status or the presence of a management agent. Network profiling may infer a device category from observed behaviour. These signals can help assign policy, but they are not infallible proof of safety. A printer needs a different baseline from a managed laptop; a visitor phone may receive internet-only access without being held to employee-device requirements.

Zero trust is broader than NAC. NAC can contribute through initial admission control and segmentation, but application-level authentication, device health, least-privilege permissions, encryption, monitoring and response processes remain important. If an endpoint fails a posture check, it may be placed in a remediation segment that reaches only update services, device-management systems or a help portal. That segment itself must be isolated.

6. Planning a safe NAC deployment

A rollout is an identity, endpoint and network operations project—not simply a switch configuration change. Begin with discovery and a limited pilot. A staged approach helps avoid locking out users or disrupting equipment.

  1. Inventory endpoints: Identify managed laptops, phones, printers, cameras, building systems, servers, personal devices and specialist equipment. Record ownership and support contacts.
  2. Map access needs: Document which groups need which services. Avoid treating “internal network” as one broad permission.
  3. Choose authentication: Evaluate EAP-TLS, tunneled methods and endpoint compatibility. Plan certificate or credential provisioning and renewal.
  4. Build resilient services: Consider redundant RADIUS servers, reliable DNS and time services, monitored certificates, protected management access and tested backups.
  5. Configure network devices: Define server addresses, shared secrets or supported protected transports, timeouts, retries, accounting and fail-open or fail-closed behaviour.
  6. Design exceptions: Plan restricted access for printers and devices that cannot use 802.1X. Avoid broad permanent bypasses.
  7. Pilot representative users: Test different operating systems, wired and wireless connections, roaming, sleep/wake, certificate renewal and device changes.
  8. Test failure cases: Simulate an unavailable RADIUS server, expired or revoked certificate, unknown device, wrong server name and incorrect VLAN response.
  9. Roll out gradually: Start with a limited building, department or SSID. Keep a documented rollback path and out-of-band access for network administrators.
  10. Monitor: Review authentication failures, rejected devices, reauthentication patterns, exception use and help-desk trends.

High availability and fallback

Authentication infrastructure becomes part of the network's availability path. If all RADIUS servers are unreachable, new connections or reauthentication events may fail. Some devices retain existing sessions, use cached results or apply a configured critical-access policy, but behaviour varies. A fail-open policy may preserve connectivity while weakening admission control. A fail-closed policy may protect access while interrupting legitimate work. The right choice depends on network sensitivity and the consequences of downtime.

Document what happens to existing sessions, new devices, roaming clients and devices that reauthenticate during an outage. Test those behaviours rather than relying on a vendor default. Include the authentication service in monitoring, capacity planning, backup and incident response.

Protect the RADIUS path

RADIUS traffic can contain identity information and authentication-related attributes. Restrict which network devices can contact the servers, use strong unique secrets where applicable, protect management interfaces and monitor unexpected clients. Traditional RADIUS does not encrypt the entire packet like a modern secure tunnel. Evaluate RADIUS over TLS (RadSec) where supported, or network-layer protection such as IPsec according to the architecture and standards in use.

Do not reuse one shared secret across an unlimited fleet if per-device secrets are supported. Rotate secrets through a controlled process and keep them out of source code, tickets and chat logs. Enable required EAP integrity protections. Maintain an inventory of RADIUS clients and remove entries when network devices are retired.

7. Troubleshooting NAC and 802.1X problems

Identify which stage failed: link or association, EAP exchange, RADIUS transport, certificate validation, identity lookup, authorization or network enforcement. A generic “authentication failed” message is not enough to identify the cause.

Correlate the evidence

Record the endpoint identity, switch or access-point name, port or SSID, timestamp with time zone, RADIUS server, EAP method and final result. Correlate endpoint, network-device and server logs in the same time window. Check time synchronisation because clock drift can break certificate validation and make logs difficult to compare.

For wired access, inspect the switch authentication session and port state using vendor-supported commands. For wireless, inspect the client session on the controller or access point. On the RADIUS server, review the detailed reason for accept, reject or timeout. Avoid collecting passwords, private keys or unnecessary personal data in tickets.

Do not confuse NAC with DHCP or DNS

A device may authenticate successfully but fail to obtain an IP address because the assigned VLAN has no working DHCP scope or relay. It may receive an address but fail to resolve names because DNS is unavailable. It may resolve names but fail to reach an application because of routing or firewall rules. Verify the whole path after admission instead of treating every connectivity problem as an authentication failure.

8. Practical NAC security checklist

  • Use a documented authentication method and tested endpoint profile.
  • Validate the authentication server certificate and expected server identity on clients.
  • Prefer certificate-based mutual authentication for managed devices where feasible.
  • Maintain certificate issuance, renewal, revocation and device offboarding procedures.
  • Register only authorised RADIUS clients and protect their secrets or transport.
  • Restrict RADIUS traffic to approved paths and monitor unexpected requests.
  • Use least-privilege authorization, segmentation and firewall rules.
  • Keep guest, IoT, printer and employee access policies distinct.
  • Treat MAB as a limited exception, not strong identity proof.
  • Test redundant servers, outage behaviour, reauthentication and rollback.
  • Review logs and exceptions while respecting privacy and retention requirements.
  • Train support teams to distinguish EAP, RADIUS, certificate, DHCP, DNS and application failures.

Frequently asked questions

1. What is network access control (NAC)?

NAC decides which users and devices can connect to a network and what access they receive. It can combine identity authentication, device posture, segmentation and policy enforcement.

2. Is NAC the same as IEEE 802.1X?

No. NAC is the broader architecture and policy approach. IEEE 802.1X is a standard for port-based network access control that can be one part of a NAC deployment.

3. What is the difference between RADIUS and EAP?

EAP is an authentication framework supporting different methods. RADIUS is an AAA protocol commonly used to carry authentication exchanges between a switch or access point and an authentication server.

4. What are the three main roles in 802.1X?

The roles are the supplicant (endpoint requesting access), authenticator (switch or access point controlling the connection) and authentication server (which validates the exchange and makes an access decision).

5. Is EAP-TLS more secure than password-based enterprise Wi-Fi?

EAP-TLS provides certificate-based mutual authentication and can avoid using a reusable password as the sole proof of identity. Its security depends on correct certificate issuance, validation, renewal, revocation and endpoint configuration.

6. Can 802.1X be used on wired Ethernet and Wi-Fi?

Yes. IEEE 802.1X can control wired switch ports and enterprise wireless networks. The authenticator is typically a switch for wired access and an access point or wireless controller for Wi-Fi.

7. What happens if a RADIUS server is unavailable?

It depends on network-device configuration and whether redundant servers or a critical-access policy exist. New authentication may fail, existing sessions may continue, or a restricted fallback may be applied. Test the deployed behaviour.

8. Can printers and IoT devices use 802.1X?

Some can, while others lack a compatible supplicant or certificate capability. Restricted alternatives such as MAB may be used, but a MAC address is not strong cryptographic identity and should not grant broad access.

9. Does successful 802.1X authentication give full network access?

No. Authentication establishes that the configured identity check succeeded. Authorization may still place the device in a restricted VLAN or role, and firewalls can further limit reachable services.

10. Is NAC enough to implement zero trust?

No. NAC can support initial admission control and segmentation, but zero trust also requires application authentication, least privilege, device and user evaluation, encryption, monitoring and ongoing policy enforcement.
