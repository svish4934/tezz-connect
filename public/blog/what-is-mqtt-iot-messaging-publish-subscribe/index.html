What Is MQTT? How IoT Messaging and Publish-Subscribe Work

A smart meter reports electricity use, a factory sensor publishes temperature, and a mobile dashboard receives updates without connecting separately to every device. MQTT makes these patterns possible through lightweight publish-subscribe messaging. This guide explains the broker, topics, quality-of-service levels, sessions, retained messages, security and the practical decisions behind a reliable Internet of Things system.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Why connected devices need a messaging protocol

The Internet of Things (IoT) describes physical objects that use sensors, software and network connections to collect or exchange information. A temperature sensor may report a reading every minute. A water meter may send a usage update several times a day. A vehicle tracker may publish its location while moving. A smart building can have hundreds of controllers, meters, alarms and environmental sensors that all need to communicate with software.

These devices do not always have the memory, battery capacity, processing power or stable connectivity of a laptop or smartphone. Some operate over low-bandwidth mobile links. Others sleep for long periods to conserve energy, connect through gateways, or experience intermittent coverage. A messaging design that requires every device to maintain a complex relationship with every other device can become difficult to manage.

MQTT addresses this with a publish-subscribe model. A device sends a message to a broker under a topic name. Other devices or applications subscribe to topics they want to receive. The broker matches publications to subscriptions and forwards messages. Publishers do not need to know the identity or network address of every subscriber. Subscribers do not need a direct connection to each publisher.

This separation is useful in sensor networks, industrial telemetry, smart buildings, fleet systems, agriculture, energy monitoring and connected products. MQTT is not the only way to build IoT systems, and it does not solve every networking problem. It provides a standard messaging layer that applications can use when its communication pattern fits.

What is MQTT?

MQTT is a lightweight messaging protocol based on publish-subscribe communication. It is designed for efficient exchange of application messages between clients through a server commonly called a broker. The protocol is maintained by OASIS, and MQTT 5.0 is specified in the OASIS MQTT Version 5.0 standard.

The letters historically expanded to Message Queuing Telemetry Transport. Today the name is generally used as the protocol name rather than as a description of every implementation detail. MQTT is an application-layer protocol. It defines how clients connect, publish, subscribe, acknowledge messages and manage sessions; it does not define the physical radio, cable or internet service used to carry those bytes.

MQTT 5.0 requires an underlying transport that provides an ordered, lossless byte stream. TCP is commonly used, and TLS can protect that connection. WebSocket transport is also supported by implementations. The standard does not restrict every deployment to one specific physical network: a device may reach its broker through Ethernet, Wi-Fi, cellular, satellite backhaul or a private industrial network.

MQTT's small protocol overhead can be useful for constrained devices and narrow links, but total traffic includes payloads, acknowledgements, keepalive packets, TLS overhead, retransmissions and any gateway traffic. A compact protocol does not automatically make an application low-power. Message frequency, radio wake time, payload size and network coverage all influence energy consumption.

The four main parts: clients, broker, publishers and subscribers

An MQTT client is any program or device that connects to an MQTT server. A sensor can be a client, but so can a cloud service, a desktop dashboard, a mobile application or a local gateway. A client can publish messages, subscribe to topics, or do both.

The broker is the central server in the messaging arrangement. It accepts network connections, authenticates clients according to its configuration, receives publications, manages subscriptions and forwards matching messages. It can also manage session state, retained messages and Last Will messages. The broker is responsible for routing; it does not need to understand the business meaning of every payload.

A publisher sends an application message to a topic. A subscriber registers a topic filter to receive matching messages. These roles are not permanent device types. The same client may publish sensor readings and subscribe to control commands. A smart thermostat, for example, could publish its current temperature while subscribing to a desired-temperature topic.

Consider a building with 50 room sensors and one facilities dashboard. Each sensor connects to the broker and publishes under a topic such as building/a/room/12/temperature. The dashboard subscribes to building/a/+/temperature to receive readings for rooms one level below that path. The sensors do not need to know the dashboard's address, and the dashboard does not open 50 separate application connections to the sensors.

How publish-subscribe messaging works

A typical exchange begins when a client opens a network connection to the broker and sends an MQTT CONNECT packet. The broker responds with CONNACK, accepting or rejecting the connection. The client can then send a SUBSCRIBE packet to request messages matching one or more topic filters. The broker acknowledges the subscription with SUBACK and records it in the session.

When a publisher sends a PUBLISH packet, it includes a topic name, a payload and delivery options such as Quality of Service. The broker checks which subscriptions match the topic and forwards a copy to each relevant subscriber, subject to permissions and subscription settings. A publisher does not receive a list of subscribers and does not need to manage their connections.

For example, a sensor might publish a JSON payload to factory/line2/motor7/vibration. A monitoring dashboard can subscribe to the same topic. An alerting service can subscribe to a wider filter covering all motor vibration topics. A storage service can subscribe to the factory namespace and record readings for later analysis. The broker handles the distribution while each application decides what the data means.

This architecture reduces direct coupling, but it introduces a central dependency: the broker. Production systems therefore need to consider broker availability, clustering or failover, session persistence, network paths, monitoring and recovery. The broker is a key part of the system design, not merely a transparent cable between devices.

MQTT topics and topic filters

Topics are hierarchical names separated by forward slashes. A topic might look like home/kitchen/temperature, factory/line2/motor7/status or fleet/vehicle/482/location. The names are chosen by the application designer. MQTT does not prescribe a universal naming scheme or require that a topic map to a physical device.

Subscribers use topic filters to select messages. The plus sign (+) is a single-level wildcard. For example, home/+/temperature matches home/kitchen/temperature and home/bedroom/temperature, but it does not match an extra nested level such as home/kitchen/window/temperature.

The hash sign (#) is a multi-level wildcard and must be used as the final character of a topic filter. A filter such as factory/line2/# matches topic names below that prefix, including deeper paths. Broad filters are powerful but can expose more information than a client needs. Subscription design should follow least privilege rather than giving every dashboard access to every topic.

Topic names are case-sensitive, and naming conventions should be documented. Avoid inconsistent spellings, unpredictable identifiers and accidental exposure of personal information in topic paths. A useful structure often includes a tenant or organisation, site, device identity, measurement or command type, and sometimes a version. Keep topic depth and naming rules consistent so that subscriptions remain understandable.

Do not confuse a topic name with a URL or a DNS hostname. It is a broker-level routing label. It does not tell the client how to reach the broker and should not contain secrets such as passwords or access tokens.

Quality of Service: QoS 0, QoS 1 and QoS 2

MQTT offers three Quality of Service levels for message delivery between a sender and receiver. Choosing a level involves a trade-off between delivery assurance, protocol exchanges, latency, bandwidth and stored state. The broker handles delivery to each subscriber independently; the QoS used on the publisher-to-broker leg and the broker-to-subscriber leg can differ.

  • QoS 0 — at most once: The message is sent without a protocol acknowledgement. It may arrive once or not arrive. This is useful for frequent measurements where the next reading will soon replace the last one.
  • QoS 1 — at least once: The receiver acknowledges the publication. If the sender does not receive the expected acknowledgement, it can retry. The message should arrive, but duplicates are possible and the application should handle them safely.
  • QoS 2 — exactly once in the MQTT exchange: A multi-step acknowledgement flow coordinates delivery so that the application message is delivered once to the receiving MQTT client within that protocol flow. It uses more packets and state than the lower levels.

The phrase exactly once needs careful interpretation. QoS 2 does not make a database update, payment or physical action exactly-once across every component in a distributed system. If an application processes a message, crashes before recording completion and later replays work from another queue, business logic can still repeat. For important operations, use application-level identifiers, idempotency, durable transaction handling and clear acknowledgement boundaries.

QoS should be selected per message type, not by assuming that the highest level is always best. A rapidly changing temperature sample may be suitable for QoS 0. A command to change a machine's operating mode may need stronger delivery handling and an explicit application acknowledgement. A safety-critical control system needs a full hazard analysis and independent safety mechanisms; choosing MQTT QoS 2 alone does not make it safe.

Retained messages: giving new subscribers the latest state

A retained message allows a broker to store the latest retained publication for a topic. When a new subscriber creates a matching subscription, the broker can immediately send that stored value. This is useful for state that changes occasionally. A newly opened dashboard can learn that a device is currently online or that a room's last reported temperature was 22 degrees without waiting for the next periodic sensor update.

A retained message is not a complete history. It is generally the latest retained value for a topic, not an archive of every publication. If the application needs historical readings, audit trails or time-series analysis, it should send data to an appropriate database or event-storage system.

Retained state needs clear semantics. Decide which topics should retain values, how stale values are identified, and how a device clears a retained value when it is decommissioned or its state is no longer meaningful. A retained command can be dangerous if a newly connected device receives an old instruction that was intended only for a previous moment. State and commands should use separate topic patterns and carefully designed expiry behaviour.

Persistent sessions and reconnect behaviour

Devices can lose connectivity because of weak radio coverage, power interruptions, roaming, maintenance, overloaded networks or broker restarts. MQTT sessions can preserve relevant state across network connections, depending on the protocol version, client settings and broker implementation. Session state can include subscriptions and in-flight messages that have not completed their delivery exchanges.

In MQTT 5.0, the client can specify a Clean Start flag and a Session Expiry Interval. These controls let an application decide whether to begin with a fresh session and how long the broker should preserve session state after a disconnection. A device that sleeps and reconnects may benefit from a persistent session, but the broker must have enough storage and a retention policy that matches the device fleet.

Persistent sessions are not unlimited storage or a guarantee that every message will be retained forever. Brokers have resource limits and administrative policies. The application must decide what to do when the session expires, when the device is offline for longer than expected, or when the queue of pending messages grows too large. For telemetry, dropping old readings may be better than delivering a long backlog of obsolete measurements after a device reconnects.

Clients should implement controlled reconnection with exponential backoff and random jitter. If thousands of devices all retry immediately after a regional outage, they can overwhelm a recovering broker or network. A planned retry strategy spreads the load and makes recovery more predictable.

Last Will and Testament: reporting an unexpected disconnect

When a client connects, it can configure a Last Will and Testament (often called a Will message). The client supplies the topic, payload and relevant delivery options. If the broker detects that the client has disconnected unexpectedly, it can publish the Will message on the client's behalf according to the protocol rules.

A common example is device availability. A connected device publishes a retained status of online. It configures a Will message that publishes offline to its status topic if the connection is lost unexpectedly. A dashboard can subscribe to the status topic and display a useful availability signal without continuously polling every device.

Will messages are not an instantaneous physical health detector. The broker must first determine that the connection has ended unexpectedly, which may depend on keepalive timing, transport failure detection and network conditions. A device that loses power may take time to be declared offline. Applications should represent the status as a broker-observed connection state, not proof that the device hardware is functioning perfectly.

MQTT 5.0 features that matter in real systems

MQTT 5.0 added features that help large or more complex deployments communicate intent and manage resource constraints. These include reason codes, user properties, message expiry intervals, session expiry intervals, topic aliases, flow control settings, shared subscriptions and enhanced authentication mechanisms. Not every broker or client library implements every feature in the same way, so check compatibility before relying on one.

Message expiry lets a publisher indicate that a message should not be delivered after a defined period. This is useful for transient information such as a short-lived command or current reading that becomes stale quickly. Session expiry controls how long session state remains after a connection closes. These are different concepts: a message can expire while a session continues to exist.

Topic aliases can reduce repeated topic-name bytes on a connection, which may help when many messages use long topic names. Flow control features allow clients and servers to limit certain in-flight exchanges. Reason codes make it easier to understand why a connection, subscription or publication was rejected. User properties allow additional metadata to be carried in protocol packets, but should not be used as a substitute for a well-defined application payload.

Shared subscriptions allow multiple sessions to share a subscription so that a matching publication is sent to one member of the group rather than every member. This can distribute processing across a pool of consumers. It is different from a normal subscription, where every matching subscriber receives a copy. Shared subscription support and selection behaviour should be checked in the broker's documentation.

MQTT security: protect the broker and every device

A broker that accepts unauthenticated connections or allows every client to publish and subscribe to every topic can become a serious security weakness. An attacker may read private telemetry, issue commands to devices, impersonate sensors, exhaust broker resources or publish misleading data. MQTT is a messaging protocol, not a complete security architecture.

Use TLS to protect data in transit and validate the broker's server certificate on clients. Depending on the environment, authenticate devices with unique usernames and passwords, client certificates or another supported identity system. Avoid shared credentials across an entire fleet because one compromised device could expose every other device. Plan how credentials are provisioned, rotated, revoked and recovered when a device is lost or replaced.

Apply topic-level authorisation. A temperature sensor may be allowed to publish to its own telemetry path but not subscribe to other devices' command topics. A dashboard may be allowed to read a building's measurements but not issue machine-control commands. A device should not be able to impersonate another device by choosing its client identifier or publishing under another device's topic.

Also limit message sizes, connection rates, subscriptions and resource consumption. Validate payloads at the application boundary. Monitor failed logins, unusual publish rates, unexpected topic access and repeated reconnects. Keep broker software and client libraries updated, isolate the broker from unnecessary public exposure, and use network segmentation where appropriate.

Cloud IoT services document similar principles: unique device identities, TLS-protected connections and permissions scoped to intended actions. See the AWS IoT security overview and AWS IoT security best practices for examples of device identity and topic authorisation controls.

Where MQTT is used

Smart homes: Sensors, switches, energy monitors and home-automation software can exchange state and commands through a local or hosted broker. Topic-based routing helps separate rooms and device types. A home automation system still needs safe defaults when internet access or the broker is unavailable.

Industrial monitoring: Machines and gateways can publish vibration, temperature, pressure, operating state and alarm data. Separate consumers can monitor dashboards, analytics and maintenance alerts. Industrial deployments need careful network segmentation, authenticated devices, controlled command paths and engineering safety systems independent of general-purpose messaging.

Agriculture: Soil moisture sensors, weather stations, irrigation controllers and pump monitors can report field conditions. Low-bandwidth messaging may help when devices communicate through cellular or long-range gateways. The system must plan for intermittent coverage, battery life and safe local operation when cloud connectivity fails.

Fleet and asset tracking: Vehicles or portable assets can publish location, status and diagnostic events. A central application can subscribe to selected fleets or regions. Location data can be sensitive, so access controls, retention periods and data minimisation matter.

Energy and utilities: Smart meters, inverters, batteries and building energy systems can send telemetry and receive authorised control messages. Such systems require robust identity, audit logging, resilience and carefully bounded command permissions because incorrect actions may affect physical infrastructure.

MQTT compared with HTTP, WebSockets and AMQP

HTTP is a natural choice for request-response interactions such as retrieving a device profile, updating a configuration or submitting a form. It is widely supported and easy to integrate with web APIs. But a system that needs many devices to exchange frequent events may find a brokered publish-subscribe model easier than building and maintaining a separate request path for every update.

WebSockets provide a persistent, bidirectional connection between two endpoints, often a browser and an application server. They are useful for interactive web interfaces and live collaboration. MQTT adds broker-managed topics and publish-subscribe routing, which can be more convenient when many devices and services need to exchange messages without direct peer relationships. MQTT can itself run over WebSocket transport in supported implementations.

AMQP is another messaging protocol used in enterprise messaging systems. It offers a different set of messaging and routing capabilities and is often selected for application integration and brokered business workflows. The best choice depends on device constraints, message patterns, delivery requirements, ecosystem support, operational skills and infrastructure.

MQTT is not automatically faster, more secure or more reliable than these alternatives. It is a good fit when lightweight broker-mediated messaging is valuable. For simple occasional device requests, HTTP may be easier. For a browser-to-server interactive session, WebSockets may be more direct. For complex enterprise message routing, an AMQP-based platform may fit better.

Planning an MQTT deployment

Start by defining the data and control flows rather than choosing a broker based only on a headline connection count. List device types, expected message frequency, average and maximum payload size, concurrent connections, number of subscriptions, fan-out, offline duration and geographic distribution. Estimate peak traffic, including reconnect storms and software updates.

Design a topic namespace before devices are deployed. Define ownership, tenant boundaries, device identifiers, measurement names, command topics, state topics and schema versions. Document which identities can publish or subscribe to each branch. Use clear topic patterns so that a device cannot accidentally read another customer's data or receive commands intended for a different machine.

Choose QoS based on the consequence of loss or duplication. Define whether a message is a transient measurement, a current state snapshot, a durable event or a command. Decide whether retained messages are appropriate and how stale values are cleared. Specify how devices behave when the broker is unreachable and whether they buffer data locally.

Evaluate the broker's persistence, clustering, backup, authentication, authorisation, observability and upgrade model. Test failure scenarios: disconnect a device, restart the broker, interrupt the network, revoke a credential, deliver a duplicate, fill a queue and restore connectivity after a long outage. Measure recovery time and confirm that the system returns to a safe state.

Finally, monitor broker health and application meaning separately. Connection count, packet rate, queue depth, message latency and rejected operations are infrastructure metrics. Sensor freshness, missing measurements, invalid readings and command completion are application metrics. Both are needed to know whether the system is actually working.

Common MQTT design mistakes

  • Using one shared credential for every device: Give devices unique identities so that a compromised credential can be revoked without replacing the entire fleet.
  • Allowing broad wildcard subscriptions: Scope topic permissions to the minimum information each client needs.
  • Assuming QoS 2 makes business actions exactly once: Use idempotency keys and durable application processing for critical operations.
  • Using retained messages as an event database: Retained state is not a full history. Store historical data separately.
  • Ignoring stale messages: Use message expiry or timestamps and define what happens when delayed telemetry arrives.
  • Reconnecting every device immediately: Use backoff and jitter to prevent a retry storm after an outage.
  • Publishing commands and telemetry in the same topic branch: Separate read-only measurements from control operations and enforce different permissions.
  • Assuming a broker is highly available by default: Plan persistence, backups, failover and capacity based on the actual implementation.
  • Putting secrets in topic names or payload logs: Keep credentials out of message content and protect sensitive telemetry throughout its lifecycle.
  • Skipping end-to-end tests: Test the complete path from device sensor to broker to subscriber and downstream storage or action.

Frequently asked questions

1. What is MQTT in simple terms?

MQTT is a lightweight publish-subscribe messaging protocol. Devices publish messages to named topics on a broker, and other clients subscribe to topics to receive matching messages.

2. What does MQTT stand for?

MQTT historically referred to Message Queuing Telemetry Transport. The protocol is now commonly identified simply as MQTT and is maintained as an OASIS standard.

3. What is an MQTT broker?

An MQTT broker is the server that accepts client connections, receives publications, manages subscriptions and forwards messages to clients whose topic filters match.

4. What are MQTT topics?

Topics are hierarchical UTF-8 names used to route messages, such as building/floor1/temperature. Clients subscribe using topic filters, which can include single-level plus and multi-level hash wildcards.

5. What are MQTT QoS 0, 1 and 2?

QoS 0 delivers at most once, QoS 1 delivers at least once and can create duplicates, and QoS 2 uses a protocol exchange to deliver exactly once between a sender and receiver in the MQTT flow.

6. Does MQTT require Wi-Fi or the internet?

No. MQTT needs a suitable network transport between client and broker, but it can operate over local networks, cellular links, wired networks or internet connections. Devices still need a reachable broker.

7. Is MQTT secure?

MQTT itself does not automatically secure every deployment. Use TLS, authenticate clients, apply topic-level authorisation, protect credentials, validate input and monitor broker access.

8. What is a retained MQTT message?

A retained message is the broker's stored latest retained publication for a topic. A new matching subscriber can receive it immediately, which is useful for current device state but not a complete event history.

9. What is an MQTT Last Will message?

A Last Will and Testament is a message configured by a client at connection time. If the client disconnects unexpectedly, the broker can publish the will to the specified topic according to the protocol rules.

10. When should I use MQTT instead of HTTP or WebSockets?

MQTT is useful when many devices need broker-mediated publish-subscribe messaging, topic routing and configurable delivery behaviour. HTTP often fits request-response APIs, while WebSockets fit direct persistent two-way sessions between an application client and server.
