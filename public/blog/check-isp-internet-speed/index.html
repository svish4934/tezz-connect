Broadband & ISP Insights

How Can I Check If My ISP Is Delivering the Speed I Pay For?

A repeatable way to measure your broadband, separate home-network problems from provider-side issues, understand India's declared-speed guidance and prepare a clear complaint.

By Suraj Vishwakarma · Published by TEZZ CONNECT

Start with the question your test can answer

If you pay for a 100 Mbps broadband plan but your phone shows 42 Mbps over Wi-Fi, that result does not immediately prove that the internet provider is under-delivering. The phone may be connected to a congested band, sitting behind walls, using an older wireless adapter or sharing airtime with other devices. On the other hand, repeated low readings from a capable computer connected directly to the router can be a useful warning that deserves investigation.

A speed test measures throughput between a particular device and a particular test server at a particular moment. It does not measure every route you use on the internet, and it cannot by itself identify whether a limitation sits in your device, router, local access line, ISP network or remote server. The goal is not to find one dramatic number. It is to build a fair, repeatable picture that helps isolate the cause. This guide focuses on fixed broadband such as fibre, cable and DSL. Mobile data has additional radio-coverage and cell-load variables.

1. Read the exact plan terms before testing

Find the plan confirmation, bill, provider app or tariff page that applied when you subscribed. Record the plan name, monthly price, declared download speed, upload speed if stated, validity period, data allowance and any fair-use or traffic-management conditions. Save a dated copy or screenshot because plan names and promotional pages can change.

Look closely at the language. A headline may say “up to 100 Mbps”, while the detailed tariff may disclose typical download and upload speeds. A plan might also specify a fair-use threshold after which speed is reduced, or distinguish promotional speed from the speed available after an introductory period. These are not interchangeable promises. If the tariff describes a typical speed, preserve that wording rather than calling it a guaranteed constant.

Check whether the stated speed is symmetric. A 100 Mbps download plan may have a much lower upload rate. This matters for video calls, cloud backups, sending large files and live streaming. Keep a reference record containing the provider, access technology, plan name, date checked, exact download and upload wording, data cap and any speed-reduction condition. If your plan changed recently, verify its effective date before comparing results.

2. Understand Mbps, MB/s and the numbers on screen

Internet plans are usually described in megabits per second (Mbps), while many file managers display megabytes per second (MB/s). One byte contains eight bits, so 100 Mbps is theoretically equivalent to 12.5 MB/s before protocol overhead and other practical limitations. A download showing 10 MB/s is therefore roughly 80 megabits per second, not 10 Mbps.

Also distinguish Mbps from Gbps. One gigabit per second is 1,000 megabits per second in the usual decimal network-rate convention. A browser download can fluctuate because of the remote server, file source, disk, CPU, encryption and connection count. A speed test estimates network throughput under its own test conditions; it does not guarantee that every file download will run at that rate. Always compare like units.

3. Prepare a test that does not accidentally measure Wi-Fi

The most useful first measurement is normally a wired test. Connect a laptop or desktop directly to a LAN port on the router using a sound Ethernet cable. If your fibre connection uses an ONT and a separate router, follow the provider's approved arrangement; do not change WAN settings or bypass required authentication.

Check every link in the chain. An older 10/100 Ethernet port cannot deliver a full gigabit connection. A damaged cable, loose connector, USB adapter, docking station or laptop port can negotiate at a lower link rate. On a gigabit plan, confirm that the computer's Ethernet adapter and router port support gigabit Ethernet. On faster plans, check the router, adapter and cable capabilities too.

Before testing, stop large downloads, game updates, cloud backups and operating-system updates. Pause streaming on televisions and other devices where practical. Close unnecessary applications that transfer data. Disable a VPN or proxy for the baseline test if your security requirements and provider setup allow it; otherwise record that it remains active. Use a current browser or reputable testing application. Do not factory-reset the router or change several advanced settings just to obtain a better number. The aim is to document the service as normally installed while removing obvious competing traffic and avoidable device bottlenecks.

4. Run a consistent series of measurements

Use a recognised test service and note which one you used. If the ISP provides a recommended method or server, include it as one part of the record, but do not rely exclusively on a provider-hosted test when investigating access to the wider internet. Choose a nearby, stable server for the main comparison. A distant server can add routing distance, congestion or server-side limitations.

If server selection is available, run an additional test against another nearby server. Do not switch servers between every reading and then treat all results as directly equivalent. Run multiple tests at different times over several days. Include a relatively quiet period and the hours when you usually notice slowdowns. Repeat the same wired setup and server where possible. A practical home log might include a few readings in each session, repeated in the morning and evening on more than one day. This is a suggested diagnostic routine, not an official sample count or legal threshold.

Record every result, including unexpectedly high readings. Selecting only the worst results can distort the picture just as much as selecting only the best. Take screenshots that show the date, time, server and full metrics. If the service does not show the date, write it beside the screenshot or save the result link. Use TEZZ CONNECT's internet speed test as one repeatable measurement point and compare it with at least one independent service. Different tests can produce different readings because they may use different servers, connection methods, durations and algorithms. A difference is a reason to investigate the method, not proof of wrongdoing.

5. Measure download, upload and latency separately

Download speed describes how quickly data reaches your device from the test server. It affects activities such as loading large pages, downloading files and receiving video streams. A low result can be caused by the access connection, local Wi-Fi, device limits, test server capacity or other traffic.

Upload speed describes how quickly your device sends data to the test server. It matters for video calls, sending attachments, uploading photos, cloud backups and live video. A connection can have a strong download result but a weak upload result, so record both rather than assuming one represents the whole service.

Latency or ping is the round-trip time for a small message to travel to a server and return, usually shown in milliseconds (ms). Lower latency generally helps interactive applications feel responsive. The result depends on the selected server and route; a nearby test server will provide a different baseline from a distant game or application server.

Jitter describes variation in packet delay. Packet loss means some packets do not reach their destination. These quality measures can affect calls and gaming even when download throughput looks healthy. Not every basic test reports them consistently, so use a test that exposes these metrics if they are relevant to the complaint. Also look for loaded latency. A connection may have a low idle ping but experience a large delay when someone uploads a file or downloads heavily. That can point to queueing or bufferbloat in the router or network path; it is a responsiveness issue, not the same thing as a download-speed shortfall.

6. Compare wired and Wi-Fi results to locate the bottleneck

After the wired baseline, run a Wi-Fi test on the same device, using the same test service and a nearby server. Start in the same room as the router with a clear line of sight. Record the Wi-Fi band if the device shows it. Then repeat from the room where you normally experience poor performance.

If wired speed is close to the expected range but Wi-Fi is much lower, investigate wireless conditions before concluding that the ISP is responsible. Common causes include distance, concrete walls, metal furniture, neighbouring networks, interference, crowded channels, older client radios, weak mesh backhaul and a router placed inside a cabinet or behind a television. Higher-frequency bands such as 5 GHz or 6 GHz can offer more capacity over shorter distances, while 2.4 GHz often travels farther but is more exposed to congestion. Device and router support varies; do not assume a phone automatically uses the fastest band.

Compare with another capable device. If one laptop is consistently slow while another performs well in the same location, the first device may be the bottleneck. If all Wi-Fi devices struggle but Ethernet performs normally, focus on router placement, radio settings, mesh nodes and wireless interference. See our guides on strong Wi-Fi signal but slow internet, when to upgrade a Wi-Fi router and why Wi-Fi can be slower on a phone than on a laptop.

7. Check whether another device or application is using the connection

A speed test measures the capacity available to the test device at that moment. If a television is streaming, a console is downloading a game, a phone is backing up videos or a computer is synchronising files, those activities share the connection. Upload saturation can be especially disruptive because cloud backups and camera uploads may run quietly in the background.

Check the router's connected-device list and traffic page if available. Look for active transfers rather than assuming every connected device consumes substantial bandwidth. A device can remain connected while idle. Conversely, one computer can saturate a connection with a large transfer even when only a few devices are connected. Run a baseline when the network is quiet, then repeat during normal household activity. The difference helps answer two separate questions: whether the broadband can reach expected throughput under low load, and whether the household has enough capacity for simultaneous use. A plan upgrade may help the second problem, but it will not fix a damaged cable, faulty router or poor Wi-Fi coverage.

8. Investigate peak-hour slowdowns carefully

If results are consistently lower in the evening, record that pattern over several days. Compare the same wired device, server and test procedure during quiet and busy periods. Include dates and local times. This can reveal a recurring time-related difference worth asking the provider to investigate.

An evening slowdown does not automatically prove ISP congestion. The test server may be busy, the wider route may be congested, household usage may increase after work, or Wi-Fi interference may change as neighbours return home. Repeat the comparison against another nearby server and, where practical, a different testing service. Record whether the slowdown affects all services or only one website, game, streaming platform or download source. If one application is slow while several independent services perform normally, the issue may be specific to that service or its route. If multiple services and independent tests are slow on a wired connection, the case for a broader access or ISP-side issue becomes stronger. Read why internet can slow down at night for more diagnostic context.

9. Use TRAI's India-specific speed information correctly

In India, the Telecom Regulatory Authority of India (TRAI) publishes broadband guidance and quality-of-service regulations. TRAI's broadband FAQ states that it does not prescribe one universal minimum download or upload speed for every broadband service. It says service providers must indicate the typical download and upload speeds generally available to consumers in tariff offerings. The FAQ also describes a requirement that at least 90% of measured test samples meet or exceed the declared typical download and upload speeds.

This must be interpreted accurately. It is a provider-level measurement and disclosure framework, not a statement that every subscriber's individual speed test must equal the advertised figure at every second. A single low result does not establish that the provider has failed the regulatory test. Repeated, carefully controlled poor results can, however, be useful evidence when asking the provider to investigate your service.

The 2024 Standards of Quality of Service regulations describe how relevant provider-level measurements are assessed, including test calls and a percentile-based approach for declared typical speeds. That methodology is not identical to a consumer running one browser test at home. Read the applicable tariff, TRAI FAQ and consolidated regulation together rather than turning a summary sentence into a personal guarantee.

TRAI provides the MySpeed app and portal for consumers to measure broadband speed and view results. Use the official TRAI MySpeed portal and follow the app's instructions, including location access if requested for its reporting features. Treat its result as an additional data point and preserve your independent wired measurements too. Official references: TRAI broadband FAQ, 2024 Quality of Service regulations and TRAI QoS performance reports.

10. Build a useful evidence log

A clear record makes it easier for a support agent or network engineer to reproduce the issue. Use a spreadsheet, notes app or paper table. Keep original screenshots and avoid editing the figures. Record date and time, connection type, test service, server, download, upload, ping, device, router, Ethernet link speed or Wi-Fi band, VPN status and whether other traffic was paused. Note unusual events such as a router reboot, power cut or provider outage.

11. Contact your provider and request a technical investigation

Use the provider's official app, website, customer-care number or published complaint channel. State the plan name, problem period and tests performed. Ask the provider to check the access line, optical signal or modem/ONT readings where relevant, router configuration, provisioning profile, local node utilisation, outages and known area issues. Ask for a complaint or docket number and the expected resolution time. Save the SMS, email or app confirmation.

If support suggests a router restart, follow the instruction once and record the time and result. Repeatedly rebooting equipment without documenting the outcome can make the timeline harder to understand. Do not share passwords, one-time passcodes or full payment details in a public post. Use the provider's authenticated support channel for account identifiers. If a technician visits, note the date, checks performed, equipment replaced and whether wired speed improved afterwards.

Send a concise evidence package: your subscribed plan and tariff speed wording; a short summary of repeated results and dates; unedited screenshots or test links; confirmation that wired tests were performed if possible; router/ONT indicator status and error messages; troubleshooting already completed; and a clear request for a line and network-side investigation with a written response.

12. Escalate through the correct consumer grievance route

TRAI's published grievance mechanism uses a two-tier process. First register the complaint with your telecom service provider's complaint centre. The provider should communicate a docket number and expected resolution time. If you are dissatisfied with the response, or the complaint remains unresolved within the applicable period, you can approach the provider's Appellate Authority using the contact details published by that provider.

TRAI explains that it does not handle individual consumer complaints directly. Sending an ordinary slow-speed complaint to TRAI as the first step is therefore not the route described in its consumer guidance. Follow the provider complaint-centre and Appellate Authority process, retain complaint numbers and attach the evidence log to your appeal.

TRAI's consumer grievance FAQ describes complaint-centre redressal periods and the appeal mechanism. The exact deadline depends on the complaint type and applicable regulation. Check current official guidance and your provider's process before calculating an escalation date. See the TRAI Grievance Redressal Mechanism and TRAI consumer grievance FAQ. Keep your appeal factual: state the docket number, first complaint date, provider response, unresolved impact and remedy requested.

13. What should the ISP technician check?

Ask for checks that match your access technology. On fibre, a technician may inspect the optical network terminal, fibre connector, optical signal levels, patch lead and provisioning profile. On cable or DSL, relevant checks differ and may include line condition, signal levels, noise or modem synchronisation. Do not open sealed equipment or handle fibre ends yourself; let a qualified technician inspect the line.

For any connection, ask whether there is a known outage, a fault affecting your building or locality, a provisioning mismatch, capacity issue on the serving node, or a router supplied by the provider that needs replacement. If the ISP says the line is healthy, ask what measurement supports that conclusion and whether they can test from the provider side while you run a wired test at the premises. If the ISP's test is fast but independent tests are slow, ask which server and network segment were used. A provider-hosted server can help isolate access throughput, but it may not represent performance to every internet destination. Both measurements can be useful when their limitations are understood.

15. Avoid common broadband testing mistakes

  • Testing only over Wi-Fi: this mixes broadband performance with wireless conditions. Include Ethernet where possible.
  • Running one test and drawing a final conclusion: one result is a snapshot. Repeat the same method and retain all readings.
  • Comparing different units: Mbps and MB/s are not the same. Convert before comparing.
  • Ignoring upload speed: a strong download result does not tell you whether uploads meet plan terms.
  • Choosing a distant or overloaded server: server and route conditions affect measurement. Cross-check with a nearby alternative.
  • Leaving background transfers active: backups, updates and streaming can consume capacity.
  • Assuming a headline is a guaranteed minimum: read the detailed tariff and its exact speed disclosures.
  • Changing many router settings at once: keep a baseline and change one thing at a time.
  • Claiming a regulatory breach from one screenshot: consumer measurements can support a complaint, but regulatory assessment uses its own defined methodology.

16. A practical three-day verification routine

Day 1 — Establish the baseline. Save your plan terms. Check the computer, Ethernet adapter, cable and router port. Pause other traffic and run several wired tests against one nearby server. Save every result and note the time. If wired testing is impossible, record that limitation and keep the device in the same room as the router for all baseline Wi-Fi readings.

Day 2 — Compare time and server conditions. Repeat the same wired method during a quiet period and the period when you notice slowdowns. Add a second nearby server and note whether the result changes significantly. If you use TRAI MySpeed, record it separately and note the app or portal used.

Day 3 — Isolate the home network and prepare the complaint. Compare wired and Wi-Fi results, test a second capable device if available, and check whether other household traffic explains the difference. Summarise the pattern in a short table. If controlled wired results remain materially below the plan's disclosed typical speed, contact the provider and request a technical investigation. This is a practical evidence routine, not an official regulatory test protocol. If the connection drops completely or the provider has acknowledged an outage, report it promptly rather than waiting three days.

Frequently asked questions

How do I check whether my ISP is delivering the speed I pay for?

Check your exact plan terms, connect a capable computer to the router by Ethernet, pause other traffic, run repeated tests to more than one nearby server at different times, and record download, upload, latency, date and test conditions. In India, use TRAI MySpeed as an additional reference rather than relying on a single result.

Does TRAI guarantee that every speed test will match my plan speed?

No. TRAI says providers must disclose typical download and upload speeds in tariff offerings and sets a provider-level measurement requirement. A single household test is not by itself proof of regulatory non-compliance. Use the official guidance and exact tariff terms to interpret results.

Why is my Wi-Fi speed lower than my broadband plan?

Wi-Fi results can be limited by distance, walls, interference, band selection, router capability, device capability and other network activity. Compare with a wired Ethernet test before attributing the difference to the ISP.

How many speed tests should I run before complaining?

There is no universal number that proves a fault. As a practical evidence-gathering method, run several tests across multiple days and time windows, include wired tests where possible, and retain the full results rather than selecting only the lowest readings.

Can I complain directly to TRAI about slow broadband?

TRAI says individual consumer complaints are not handled by the Authority. First complain to your provider's complaint centre, obtain a docket number, and then appeal to that provider's Appellate Authority if the response is unsatisfactory.

What should I send my ISP when reporting slow speed?

Include your plan name and declared speed, dates and times, wired or Wi-Fi connection type, device and router details, test server, download and upload results, latency, screenshots and steps already attempted. Share account identifiers only through the provider's secure support channel.

Should I use my ISP's own speed-test server?

It can be useful because it may help assess the connection to the provider's network. Also test an independent nearby server to understand performance beyond that test environment. Record which server produced each result.

Can a VPN make my speed test lower?

Yes. A VPN adds another network path and encryption workload, and its server location or capacity can affect throughput and latency. Run a baseline without the VPN if your security requirements and provider setup allow it, then test with the VPN separately and label both results.

Conclusion: measure consistently, then escalate with evidence

The fairest way to check broadband delivery is to compare the correct plan terms with repeated measurements from a capable wired device, while recording the server, time, download, upload and latency. Use Wi-Fi tests to understand the home wireless experience, not as the only evidence of provider performance. Compare more than one server, include the periods when the problem occurs and retain all results.

For subscribers in India, TRAI's declared typical-speed guidance and MySpeed service provide useful context, while the provider's complaint centre and Appellate Authority are the appropriate route for individual grievances. A careful evidence log gives the provider something specific to investigate and helps you avoid blaming the wrong part of the connection.
