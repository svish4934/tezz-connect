What Is a CDN? How Content Delivery Networks Make Websites Faster

Learn how content delivery networks work, including edge servers, points of presence, cache hits and misses, origin shielding, cache invalidation, anycast routing and CDN security. Understand what a CDN can improve, what it cannot fix, and how website owners can configure caching safely.

By Suraj Vishwakarma · Published by TEZZ CONNECT

The internet has a distance problem

A website may be hosted in one country while its visitors are spread across many continents. When a browser requests an image, stylesheet, video segment or page, the data must travel through networks between the visitor and the server that can answer. Even when those networks have plenty of capacity, physical distance and the number of network exchanges add time. A Content Delivery Network, usually shortened to CDN, helps address this problem by distributing copies of selected content across servers in many locations. Instead of every visitor retrieving every file from one central origin, a nearby CDN edge location can answer requests for content it already holds. The result can be faster delivery, less repeated work at the origin and more room to absorb traffic spikes. A CDN is not a magic speed switch: its benefit depends on the content, cache rules, network paths, visitor location and application design.

What is a content delivery network?

A content delivery network is a geographically distributed system of servers and supporting network services that delivers web content to users. The servers are commonly called edge servers, and the locations where they operate are often called points of presence, or PoPs. A CDN provider places these PoPs across regions and connects them through its own network and upstream internet connections. When a visitor requests a resource from a website configured to use a CDN, the request is directed to an appropriate edge location. If that location has a valid cached copy, it can return the copy without asking the website's origin server for it again. If it does not have a usable copy, it may fetch the resource from the origin or from another cache tier, then store a copy according to the configured rules. CDNs commonly deliver images, fonts, CSS, JavaScript, downloads, software packages, audio, video segments and, when configured carefully, some HTML responses and API data.

The origin, edge and points of presence

The origin is the source from which the website's content ultimately comes. It might be a web server, cloud storage bucket, application platform or a group of backend services. The origin remains the authoritative place where the publisher updates files and where dynamic application logic may run. Edge servers sit between visitors and the origin. They receive requests, apply delivery and security rules, check whether a suitable cached response exists and either return it or obtain it upstream. A point of presence is a physical or logical location in the CDN network containing the equipment and connectivity needed to serve traffic. One PoP can contain many servers; it is not necessarily one server or one building. A provider may also operate regional or upper-tier caches that help smaller edge locations retrieve popular content without repeatedly contacting the origin. The exact design differs between providers, and the nearest PoP by geography is not always the fastest or best-performing one.

How a CDN request works, step by step

First, a visitor enters a website address or opens an app. DNS and the provider's traffic-steering system help direct the request toward the CDN service configured for that hostname. The browser establishes a connection to the selected edge location, usually using HTTPS. The edge evaluates the request: hostname, path, method, query string, cookies, headers, cache key and applicable security rules can all matter. It then checks its cache. If a fresh response matches the cache key, the edge returns it. If the response is absent, expired or not eligible for caching, the edge may contact the origin or a parent cache. The upstream server responds; the CDN can deliver that response to the visitor and, if the response and rules allow, store it for later requests. The next visitor whose request maps to the same cache key and reaches a cache with a valid copy may receive a cache hit. Dynamic pages, authenticated responses and personalised data often need different treatment from public static files.

Cache hit, cache miss and cache key

A cache hit means the CDN can satisfy a request using a stored response that is considered valid for that request. A cache miss means the required response is not available in the relevant cache, so the CDN must obtain it upstream or use another configured process. A miss is not necessarily an error; it is a normal part of cache filling, especially after a new file is published or a cache is cleared. The cache key determines which requests are treated as equivalent for storage and retrieval. It commonly includes the hostname and URL path, and may include query parameters or selected request headers. If a site varies content by language, device type or another signal, the cache key and response variation rules must represent that difference correctly. If the key ignores a meaningful variation, one visitor could receive content intended for another. If it includes unnecessary unique values, the cache may fragment into many rarely reused copies and hit rates can fall. Cache-key design is therefore both a performance and correctness decision.

What can be cached—and what should not be

Public static resources are usually strong candidates: versioned images, fonts, CSS, JavaScript bundles, icons and downloadable files. They tend to be identical for many visitors and change only when a new version is published. Public pages and API responses may also be cacheable when their content is shared and the site defines suitable freshness rules. Personal dashboards, account pages, shopping carts, payment steps, private documents and responses containing user-specific information require much more care. A response marked private or no-store should not be shared through a public cache. Cookies, authorization headers, request methods and origin cache-control directives can influence default behaviour, but exact rules differ by provider and configuration. Never assume that a file is safe to cache simply because its URL ends in .html, .json or .jpg. The publisher must understand whether the response contains private data, whether it changes by user and how long a stored copy can remain valid.

Freshness, TTL, revalidation and cache invalidation

A time to live, or TTL, defines how long a cached response may be considered fresh under a cache policy. HTTP caching uses response headers such as Cache-Control and Expires to communicate freshness and reuse rules. When a copy becomes stale, a CDN may contact the origin to revalidate it. With validators such as an ETag or Last-Modified value, the origin can indicate that the representation has not changed; the CDN may then reuse the stored body rather than download it again. Publishers also need a way to make updated content available before its normal freshness period ends. Cache purge removes matching stored copies so later requests fetch them again. Invalidation or soft purge marks content stale so it can be revalidated, depending on provider behaviour. Purging everything is often a blunt response: it can create a wave of misses and send a sudden burst of requests to the origin. Prefer versioned asset filenames and targeted purges where practical, and test cache behaviour after publishing changes.

Why CDNs use layered or tiered caching

A large CDN may have many edge locations, each serving a different group of users. If every edge location independently fetches a popular file from the origin on its first miss, the origin can receive many similar requests at once. Tiered caching introduces an intermediate cache layer. A local edge that misses can ask an upper-tier cache before going to the origin. If the upper tier already holds the object, it can provide it to the edge and avoid another origin fetch. The edge may then retain its own copy for nearby requests. This arrangement can increase cache efficiency and reduce origin traffic, especially when users are spread across many locations. It does not guarantee that every request will be served from a cache: uncached, personalised, rapidly changing or deliberately bypassed content may still need the origin. Cache hierarchy also introduces configuration and troubleshooting considerations, including where a miss occurred and whether an object is fresh at each tier.

How users are routed to CDN locations

CDN providers need a method to direct visitors to suitable edge locations. DNS-based steering can return different addresses depending on factors such as the visitor's resolver location, network conditions, service health and provider policy. One limitation is that the DNS resolver's location may differ from the actual user's location, particularly when public or centralised resolvers are used. Anycast is another approach. With anycast, the same IP address is announced from multiple network locations, and internet routing directs traffic toward one of the available announcements according to routing policy and network topology. Anycast can support resilient distribution and fast failover, but the route selected by BGP is not a guarantee of the geographically closest building or the lowest-latency path for every application. Some providers combine anycast, DNS steering, health checks and internal load balancing. CDN routing is a network decision, not simply a map lookup that always selects the nearest city.

CDN versus web hosting, cloud computing and edge computing

Web hosting provides the environment where a website or application is stored and runs. A CDN distributes and delivers selected content from locations closer to visitors, often while protecting and reducing load on the origin. Cloud computing offers broader on-demand infrastructure and services, such as virtual machines, databases, object storage, analytics and application platforms. Edge computing moves computation or data handling closer to devices, users or data sources; it can involve running application logic, filtering sensor data or making local decisions. A CDN may cache a response or execute limited logic at the edge, but caching content is not the same as moving an entire application workload to an edge computer. TEZZ CONNECT's separate guide to edge computing explains that distinction in more detail. A website can use all these approaches together: cloud hosting for its origin, a CDN for public assets and selected responses, and edge compute for specific request handling.

How a CDN can improve performance

A CDN can reduce the distance that content travels when an edge cache can answer locally or regionally. It can also reduce repeated origin requests, avoid some origin bottlenecks and make delivery more consistent for visitors in different regions. Large files such as images and video segments are particularly useful examples because transferring them from a nearby cache can reduce the amount of data that must cross long-distance paths. However, a CDN does not automatically improve every part of a page. If the HTML is dynamic and must be generated at the origin, the initial document request may still depend on the origin's processing time and network route. If the page loads dozens of third-party scripts, a slow database query or a heavy client-side application, caching images alone may not solve the main delay. A poorly configured CDN can even add an extra hop, create cache misses or introduce TLS and DNS setup overhead. Measure real user performance, not just the provider's marketing claims.

CDNs and video streaming

Streaming services often divide video into many small segments and deliver them as viewers play. A CDN can cache popular segments close to viewers, helping many users watch the same programme without every request reaching the streaming platform's origin. Adaptive bitrate streaming can select different segment qualities according to device capability and changing network conditions. The CDN helps deliver the segments, but it does not create extra bandwidth on a viewer's access connection or remove congestion inside the ISP network. A viewer may still experience buffering because of weak Wi-Fi, a busy access network, an overloaded device, a distant or unavailable cache, or problems in the streaming service. If you want to understand how data demand changes with video quality, see TEZZ CONNECT's guide to how much data 4K streaming uses.

CDN security: reverse proxy, DDoS protection and WAF

Many CDN deployments operate as reverse proxies: visitors connect to the CDN first, and the CDN forwards eligible requests to the origin. This arrangement can provide a control point for TLS termination, request inspection, rate limiting, bot controls, web application firewall rules and distributed denial-of-service mitigation. A distributed network can absorb and filter some traffic before it reaches the origin, reducing exposure to volumetric attacks. But a CDN is not a complete security programme. The origin should be configured so attackers cannot simply bypass the CDN and connect directly to the server, where appropriate. Security rules need careful testing to avoid blocking legitimate users or allowing harmful requests. Application vulnerabilities, compromised accounts, unsafe software dependencies and exposed secrets still need to be addressed. DDoS protection capabilities, WAF features and included limits vary by provider and plan; do not assume every CDN subscription includes every advanced security control.

Common CDN problems and how to investigate them

A page showing old content after an update may indicate a stale cached response, an overly long TTL, an incomplete purge or a cache key that differs from the one being tested. A sudden rise in origin traffic may mean cache hit ratio has fallen, a large purge caused widespread misses, content is not cacheable or traffic patterns have changed. A site that works in one region but not another may have a PoP, DNS, routing, firewall or origin connectivity issue. A broken login or shopping cart can result from caching a response that should have been private or from varying content incorrectly. Start with the exact URL, request method, response status, cache status and relevant response headers. Compare a normal request with a controlled cache-bypass test if the provider supports one. Check whether the origin itself is healthy, whether the hostname resolves as expected and whether a security rule is challenging or blocking the request. Avoid repeatedly purging the entire cache before identifying the cause.

How to choose a CDN for a website

Start with where the audience is located and whether the provider has useful connectivity and capacity in those regions. Check the content types you need to deliver, supported protocols, cache controls, purge options, origin protection, TLS management, logs, analytics, security features and support arrangements. Understand pricing units: requests, data transfer, cache egress, origin fetches, rules, image optimisation and advanced security may be charged separately. Review whether the CDN integrates with your hosting platform and whether you can configure cache headers without fighting the application. Test a small set of representative URLs before moving all traffic. Include dynamic pages, query strings, logged-in sessions, APIs, large downloads and content updates in the test. Review privacy, data processing and contractual requirements for your audience and business. A provider with the largest advertised network is not automatically the best choice for every site.

A practical checklist for website owners

Before enabling a CDN, identify which URLs are public and reusable and which are personalised. Set deliberate Cache-Control policies at the origin. Use versioned filenames for static assets so a new deployment can reference new files rather than relying on a global purge. Define the cache key and decide whether query parameters or selected headers change the response. Confirm that login, payment, account and private API responses bypass shared caching. Protect the origin so normal public traffic reaches it through the intended path. Test cache hit and miss behaviour from more than one region. Verify that a purge or invalidation updates content as expected. Monitor origin request volume, cache hit ratio, response time, error rates and bandwidth. Keep a rollback plan for DNS and CDN configuration changes. Most importantly, compare real visitor experience before and after the change; a CDN should be judged by measurable outcomes, not by the number of PoPs shown on a map.

What a CDN cannot guarantee

A CDN cannot guarantee that every request is served from a nearby cache, that all websites load instantly, or that an ISP's congested access network becomes uncongested. It cannot make a slow database query disappear, repair a damaged fibre route between a user and the CDN, or improve a device with poor Wi-Fi reception. It may reduce the distance to cached assets, but dynamic operations can still depend on a distant origin. A cache can also be cold, stale, unavailable or bypassed by policy. The best results come from a well-designed application, correct caching rules, a healthy origin, good internet routing and a CDN whose footprint matches the audience. Think of a CDN as one important layer in web delivery—not a substitute for sound hosting, network engineering, application performance and security.

Frequently asked questions

What does CDN stand for?

CDN stands for Content Delivery Network. It is a distributed network of servers that delivers website and application content from locations closer to users.

How does a CDN make a website faster?

A CDN can cache reusable content at edge locations. When a suitable copy is available, the edge can return it without fetching the same resource from the origin server each time.

What is the difference between a CDN and web hosting?

Web hosting stores and runs the original website or application. A CDN distributes selected content through edge servers and can reduce repeated requests to the origin.

What is a CDN cache hit?

A cache hit occurs when an edge location has a valid stored response that matches the incoming request and can serve it directly.

What is a cache miss?

A cache miss occurs when the needed response is not available in the relevant cache. The CDN may then retrieve it from the origin or an upper-tier cache.

Does a CDN cache every page?

No. Cache behaviour depends on response headers, provider defaults, cache rules and whether content is public and reusable. Personalised or private responses generally need to bypass shared caching.

What is a CDN point of presence?

A point of presence, or PoP, is a location in a CDN provider's network where its equipment and connectivity serve traffic. A PoP may contain many edge servers.

Is a CDN the same as edge computing?

No. A CDN primarily distributes and caches content. Edge computing runs application logic or processes data closer to users, devices or data sources. Some platforms offer both.

Can a CDN protect a website from DDoS attacks?

Many CDNs provide distributed traffic handling and DDoS mitigation, and some include web application firewall features. Protection varies by provider, configuration and service plan.

Does a CDN always reduce ping?

No. A CDN may improve delivery time for cached web content, but ping measures round-trip network latency to a particular endpoint. The CDN does not control every network segment or the user's access connection.
